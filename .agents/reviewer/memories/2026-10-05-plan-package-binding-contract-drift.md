# Plan-Package Review: Binding-Contract Drift Patterns (snapshot-uiux, 2026-10-05)

Review of the snapshot-uiux plan package (6 files, worktree `ensemble-src-wt-snapshot-uiux`) surfaced four reusable lessons for plan/architecture reviews:

1. **Declared supersession ≠ body conformance.** A reconciliation doc (sequencing.md §1) may correctly declare itself binding with a read-first rule, while the lane-plan *bodies* still carry the pre-reconciliation contract values (be-plan §4.1 example JSON + §7 skeleton; fe-plan §3/§5 with zero references to the reconciliation doc — both grep-verified by independent workers). Always dispatch a worker to grep each lane doc's *body* for the reconciled keys (envelope key, param names, enum values), not just confirm the supersession rule exists.

2. **SHA-pinned/frozen artifacts need their OWN amendment mechanics.** A frozen design-spec that says "changes ride `design-spec-amendment-<reason>.md`" (spec:747) is violated by prose supersession from a sibling doc. When a spec is immutable-from-SHA, verify the amendment file exists ON DISK whenever any sibling doc contradicts it. Also check whether acceptance criteria inside the frozen doc become unsatisfiable under the reconciliation (AC-8.4/AC-4.1 were — blocking the tester's sign-off).

3. **Deletion-range instructions must be verified against real file content.** A plan task specifying "delete spec lines 1346–1985" swallowed ~450 lines of an unrelated timezone test suite; actual target was 1344–1533 + 3 surgical jest.fn removals. For any plan-mandated deletion, a reviewer must diff the cited range against the file's real structure (describe blocks, classes) before the task is executable.

4. **Un-reconciled divergences outside the declared delta-table.** The reconciliation table covered D-1..D-5 but limit default/max and age-preset/default diverged 3-way (spec vs BE vs FE) with no D-row. Scan for contract dimensions present in ≥2 docs but absent from the reconciliation table.

Partition that worked: (a) cross-doc consistency+risks, (b) BE plan vs daemon/ code, (c) FE plan+mockup vs frontend/ code. Two workers independently discovered the §1 body drift — good signal the checklist-driven split avoids shared blind spots.


**Addendum (same day, re-verification pass):** Line-number calibration lesson — the original T13 finding measured the mock lines at `:1565-1568`; the re-verification against the real file showed `:1566-1570` (1565 is `setBlueprintPeakHours`, not snapshot content; the third mock spans 3 lines). The *fix lane* was right and the *first reviewer* was off-by-one on both ends. Rule: on any re-verification or deletion-range check, re-measure boundaries against the actual file every time — never inherit the previous reviewer's line numbers, even your own workers'. Also confirmed: the amendment-file mechanism (design-spec-amendment-contract-reconciliation.md @ 5cce3be3, back-referenced from sequencing §1, frozen body untouched per empty git diff) fully resolves the frozen-spec blocker class.


**Addendum 2 (pass-4, same day):** Executable-gate class caught by the adversarial-skim split — a plan's *dedicated e2e config* can be internally coherent and still be unbootable: it invented `ENSEMBLE_PORT` (dev.sh sets `PORT=8079` unconditionally — grep returned zero readers) and set `SNAPSHOTS_API_BASE`/`API_TARGET` env vars that nothing in `frontend/` consumes while `proxy.conf.json` hardcodes 8079 → webServer never boots / FE proxies to the live dev daemon. Rule: **for every env var, knob, selector, or config file a plan invents, grep the repo for a consumer before believing the gate runs.** Cheap full-tree greps ("does anything read this?") are load-bearing evidence. The two-worker split (claim-verifier vs fresh-eyes defect hunter) is what surfaced this — the claim verifier confirmed all 12 planner claims while the hunter found 2 boot-fatal defects the planner's fix lanes never touched. Also: verify plans against the *toolchain precedents that exist* (playwright.maintenance.config.ts + proxy.conf.e2e.json + boot script) rather than novel config shapes.


**Addendum 3 (pass-5, same day):** Two more executable-gate classes, both caught by composing the gate as a system rather than checking claims: (1) **canary targets a nonexistent endpoint** — the boot script polled `GET /availability`, but the daemon's route table is `/`, `/livez`, `/readyz`, `/api/*` + SPA catch-all; the namespaced availability routes live under `/api/migration/…` and `/api/maintenance/…`, and the new router added none. Rule: for any readiness probe a plan specifies, enumerate the actual route table (including the SPA catch-all that would serve index.html with 200 and break JSON parsing) and quote both sides. (2) **gate-required files authored by nobody** — config/boot-script/proxy/e2e-spec/teardown were specified in §4.3.1 but appeared in no new-file manifest, no phase's "What lands", and no commit row → the overnight run would have nothing to execute. Rule: every file a gate consumes must trace to a manifest row + a commit that carries it. Also minor: exec-bit on scripts Playwright execs directly (mirror was 100755); "mirrors X verbatim" claims deserve spot-diffs (the canary was the ONE line that deviated from the mirror — and it was the broken one).


**Addendum 4 (pass-6, same day):** Confirmed pattern across all four verification passes — **every edit round leaks exactly one stale artifact** (pass-4: trailing garble; pass-5: the canary line that deviated from its "verbatim mirror" claim; pass-6: `c0+c1–c7` left in a plan-overview deliverables-map row after the 9-commit amendment). Rule for future delta-verifications: after ANY value sweep (port, count, name), grep the ENTIRE package for the old value — including overview/summary docs and deliverables-map rows, not just the operative sections — and treat "mirror/verbatim" claims as the first place to spot-diff.
