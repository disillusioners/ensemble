# Phase 1: Backend storage + resolution + boot apply

## Objective

A greenfield `app_settings` table (migration + SQLModel), and a `SettingsService` that (i) owns the managed-key registry, (ii) resolves managed keys with explicit DB > env > yaml > default precedence, (iii) applies DB overrides onto the live `Config` at boot — so that `InstanceManager.__init__` (`daemon/manager.py:555`) reads the DB-backed value with zero downstream changes.

## Tests (authored in Phase 4 alongside; implementation must make them writable)

- Registry gate: unknown key refused everywhere.
- Tier ladder: each of the 4 tiers isolated + combined (Phase 4 task 1 is the authoritative list — the shadowing case lives there).
- Bootstrap read: temp SQLite, seeded rows, mutation assertion, failure postures.

## Coupling

- **Tight with Phase 2** — the service's public surface (registry shape, `resolve` return schema, override CRUD) IS the API layer's backend; freeze signatures in tasks 3-4 before Phase 2 task 1.
- **Tight with Phase 4** (unit tests consume these functions directly).
- **Independent of Phase 3** (FE never imports this layer).

## Risks

- ~~Task 4 yaml-tier extraction~~ — RESOLVED by the snapshot design (reconciled): the yaml tier is captured in the pristine pre-override snapshot (t5 step 3), so the ladder never reads a mutated field; GET's `source` re-resolves over (live DB > live env > snapshot yaml > default).
- Fail-open must not swallow real bugs: ERROR log must include the failure class (parse vs validation) + fallback tier (Phase 4 acceptance).

## Exit Criterion

`apply_db_settings_overrides` proven by temp-SQLite unit test to mutate `config.limits.llm_concurrency` from a seeded DB row and return the pristine snapshot (with the raw-literal `yaml_value` derivation); lifespan boots green with the one-call insertion + post-manager `set_settings_service(SettingsService(engine=manager.engine))` / `set_settings_resolution_snapshot(snapshot)` wiring. **Ownership invariant (iteration-002 Shape A):** every `daemon/api.py` edit is owned by THIS phase (t6), and this phase created every symbol its exit criterion references — the router-DI symbols (`_settings_service` / `set_settings_service()` + 503 getter, `set_settings_resolution_snapshot()` / getter) are created in t6 within `daemon/routers/settings.py`. No changes to `daemon/manager.py` beyond the t1 one-line late-import registration, and none to `daemon/services/instance_messaging.py`.
