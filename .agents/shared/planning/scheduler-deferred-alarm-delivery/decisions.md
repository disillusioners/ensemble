## DEC-1. [LEADER-RULED] C3 — the handoff target is `manager.enqueue_message_job` (NOT the send_message tool)

**Decision:** The deferred delivery is enqueued through `InstanceManager.enqueue_message_job` (`daemon/manager.py:9501-9515`), the same primitive the scheduler's normal reuse-mode path already uses (`scheduler.py:1118-1126`).

**Rationale:**
- A plain send to a RUNNING + live-graph target is **RAM injection** via `set_injection` (`daemon/tools/instance.py:4138`) — it would land *inside* the caller's live turn, not as a follow-up turn, and would be lost if the turn ended first.
- `enqueue_message_job` has **no busy guard and no status gate** — it always queues. The serialisation comes from the substrate: the per-instance claim gate (`daemon/repositories/task/repository.py:2983-2985`) makes a PENDING task for a busy instance un-claimable until the turn ends, so it fires as the next turn (pool re-attempt ≤3s, `daemon/services/worker_pool.py:1392-1443`).
- It reuses the whole existing machinery: MessageQueue + Task written in one transaction (`instance_messaging.py:2182-2210`, `:2311-2338`), JobItem mirror (`:3076`), the secret-scrub at `:2181`, and the retry/dead-letter machinery. **No new wake primitive, no new polling loop, no new table.**

**Rejected alternative(s):**
- **The send_message tool / `set_injection`** — RAM injection into a live turn; the alarm would be merged into whatever the caller is doing rather than delivered as its own turn. Rejected.
- **A new `schedule_deferred` table + a new dispatcher loop** — a new persistence class, a new failure mode, and a re-implementation of the queue the system already has. Rejected (violates the hard non-goals).

## DEC-2. [LEADER-RULED] The sibling defect — semaphore-timeout skip — is IN SCOPE — **AMENDED by ADR-10 (two-branch fix)**

**Decision:** The semaphore-timeout skip (`daemon/sources/adapters/scheduler.py:926-942`, `_acquire_execution_slot`) is in scope, with a **TWO-BRANCH** fix [LEADER-RULED, ADR-10]:
1. **Deferrable target** (reuse-mode with a resolvable mapping) → **defer to the pinned caller** — the identical mechanism as the busy branch.
2. **No deferrable target** (new_instance / no mapping) → **RE-ARM**: write the execution row via start→complete with `DEFERRED` + a reason, **NEVER consume the one-shot SILENTLY** (DEC-22: the 24h age cap converts this into a **visible** terminal consumption), and take a **MANDATORY `await asyncio.sleep(SCHEDULER_ERROR_RETRY_S)`** (5.0s, `daemon/constants.py:376`) — mirroring the `PAST_LATENESS_CAP` pattern at `:580-582`.

**AMENDMENT — W5 (semaphore branch structure; leader-ruled).** The deferrable-target test at the semaphore site is a **READ-ONLY mapping resolution performed at the call site** — it resolves the bound instance id **without** re-entering `mapper.get_or_create_instance` (whose mapping-miss branch is the only stranger-spawn surface, DEC-5). A resolution that would otherwise *create* or *spawn* is treated as **no deferrable target** → branch 2. The defer branch is additionally **gated to the SCHEDULED path only** (the manual-trigger twin at `:1239-1260` keeps its immediate-execution semantics, per DEC-3). **Manual-path delta, disclosed:** the manual path never reaches the semaphore defer branch, so it is **unchanged** — it is not routed through `_defer_delivery` and does not participate in the deferral episode state. This is consistent with the leader ruling L-G and DEC-3's non-goal; the delta is a **scope statement, not a behaviour change**.

**Rationale:**
- It is the **same** defect shape: the SKIPPED callback targets a never-INSERTed uuid (`source/repository.py:629-632`), the one-shot is consumed at `scheduler.py:624`, and the residue is invisible.
- **Scope correction folded in:** the semaphore site is called at `:1189-1190` — **BEFORE** the reuse check at `:1195` — so it is reachable for **EVERY** `instance_mode` (probe P5), not just reuse. The two-branch fix therefore covers every mode's no-target case, and my earlier "reuse-mode only" framing was too narrow.
- **The 5s sleep is NOT optional.** A re-armed past-due one-shot returns `now` from `_get_next_trigger_time` (`:753`) → `wait_seconds ≈ 0` → a **proven hot loop** when `one_shot_max_lateness_seconds` is unset (it is, live — `config.py:2667-2673`, default `None`): the cap branch is dead and only the exception handler sleeps. The architect proved the spin (architecture §3 alternative (iii)(b), §11).
- The re-arm branch **never consumes** the one-shot — there is nothing durable to carry the intent, so consuming would be the original defect (ADR-3).

**Rejected alternative(s):**
- **Out of scope ("the busy branch is the reported symptom")** — leaves a known silent-loss path one line away from the fixed one.
- **A separate semaphore-deferral mechanism** — duplicated state, duplicated keys, two shapes of the same artefact.
- **Re-arm without the sleep** — a proven hot loop (CPU spin, log flood). Rejected; the sleep is mandatory and pinned (architect R5).
- **Consume the one-shot on the re-arm branch** — the intent would be destroyed with no durable carrier. Rejected (ADR-3).

## DEC-3. [LEADER-RULED] The manual-trigger twin is DEFERRED — a disclosed non-goal

**Decision:** `scheduler.py:1239-1260` (`_execute_trigger` → `_execute_immediate`) is **not changed**. The manual trigger is unaffected by this commission. **RATIONALE CORRECTION (should-fix e — the earlier rationale here was FACTUALLY WRONG):** the manual twin does **NOT** "skip the busy check entirely" — it **DOES** busy-check and **drops**, exactly like the scheduled path (`scheduler.py:1239-1257`: the same `if self._instance_mode == REUSE_INSTANCE` guard, the same `_is_instance_active()` call at `:1240`, the same *"Skipping manual trigger … is still <status>"* log, the same `SKIPPED` execution callback, the same bare `return` at `:1257`). **The non-goal STANDS** — the manual path is not changed by this commission — but the *reason* is that the manual path is an **immediate** execution by design (the operator-triggered latency contract), **not** that it is blind to the busy state. The manual path's own drop is a **separate, pre-existing** defect (it is the same class as the scheduled path's, which this commission fixes) and is **out of scope here** — **disclosed**.

**Rationale:**
- The manual path is an *immediate* execution by design ("Manual triggers ALWAYS use immediate execution … deliberate design for immediate user feedback", `:1225-1231`). Routing it through the queue would change a user-facing latency contract for no defect.
- It is a different fire semantic (one operator-initiated fire vs. a schedule tick) — folding it in would enlarge the blast radius of the change.
- The deferral mechanism built here **makes it safe to route through later**: once the busy branch can hand off instead of drop, the manual path could adopt the same shape without re-inventing anything. That is the recorded follow-up path.

**Rejected alternative(s):**
- **Route manual triggers through `_defer_delivery` now** — changes immediate-feedback semantics, and the manual path never hits the busy branch, so it buys nothing for the reported defect. Rejected (deferred, not closed).

## DEC-4. [LEADER-RULED] The busy predicate stays as-is; the log level is raised

**Decision:** `_is_instance_active` (`scheduler.py:901-905` — the predicate tuple) keeps exactly `{RUNNING, WAITING, WAITING_CHILDREN}`. It is **not** swapped for `TaskRepository.has_instance_busy` (PENDING + RUNNING + PAUSED, `task/repository.py:1621`). The busy branch's `logger.info` is raised to **`logger.warning`**.

**Rationale:**
- The two predicates are **neither a subset nor a superset** of each other: `has_instance_busy` counts any PENDING task for the instance (including one this very adapter enqueued) and treats PAUSED as busy; `_is_instance_active` reads the *instance row* status. Swapping them would change which fires defer — an unrelated semantic change smuggled in as a "cleanup".
- With deferral in place **both over- and under-inclusiveness become safe**: the worst case of an over-inclusive predicate is *a deferral* (an extra queued turn), never a loss. The worst case of the current predicate is also bounded (it defers only on the three genuinely-active statuses).
- The predicate is **pinned by a test** so a future edit cannot silently change it, and the divergence from `has_instance_busy` is **documented** in the code comment (the design must not "fix" the divergence by accident).
- The log level: this branch is the exact place where a scheduled alarm does not happen. It was `info` — invisible in a default log view. `warning` makes the *cause* of a deferral visible; the *fact* of the deferral is separately durable (§DEC-12).

**AMENDMENT — L-F (traceability row + pin assertion; leader-ruled).** The log-level raise is a **first-class, traceable** requirement, not an incidental detail: the implementation site is the busy branch's `logger.info` at `daemon/sources/adapters/scheduler.py:1197-1201` (the `_is_instance_active()` call at `:1197`, the `logger.info(` at `:1198`), and it becomes `logger.warning`. **Traceability row:** the busy-log `info`→`warning` raise is carried in `plan-overview.md` §(d) under **D1** (the busy-caller requirement) and in §(e) **pin #1**'s GREEN assertions. **Assertion form:** either a `caplog` assertion inside pin #1 (assert the deferral is emitted at `WARNING` and that **no** `INFO`-level "Skipping scheduled execution" record is produced for the same `execution_id`) or, equivalently, folded into pin #1's GREEN set — the pin file's house shape already permits the assembled-surface exact-string needle, so the log-level expectation may be asserted on the record's `levelname` rather than on its text. **The busy branch is the ONLY deferral log at `info` today; after this amendment there is no `INFO`-level deferral record anywhere on the scheduled path.**

**Rejected alternative(s):**
- **Swap in `has_instance_busy`** — semantic change disguised as reuse; PAUSED would become blocking (contradicting DEC-11) and PENDING-task counting would make the adapter defer on its own queued work. Rejected.
- **Leave the log at `info`** — the defect was, in part, that the drop was invisible. Rejected.

## DEC-5. [LEADER-RULED] E1 scoping — refuse at the mapper; do not touch the repo upsert; preserve the binding keys — **AMENDED by ADR-11 (fail-closed on CONFIRMED absence ONLY) + CRIT-1 (the `refused_permanent` outcome)**

**Decision:** Three coupled changes in `daemon/sources/mapper.py::get_or_create_instance` (`:275-…`):
1. **Refusal** — in the `if not self._mapping_instance_exists(mapping):` branch (`:336-344`), **before** `delete_instance_mapping` + the spawn fall-through: if `mapping["metadata"].get("bound_to_caller")` is truthy → **raise a typed error**; do not delete the mapping, do not spawn; WARNING with `source_id` + `dead_agent_instance_id`. **The refusal fires on CONFIRMED absence only** — i.e. `_mapping_instance_exists` returned `False` **from a successful query**.
2. **`create_instance_mapping`'s global upsert merge semantics are NOT touched** (`daemon/repositories/source/repository.py:389`).
3. **Binding-key preservation** — at the metadata-construction site (`:368-377`), carry `bound_to_caller` / `caller_instance_id` / `source` from the prior mapping's metadata into the rebuilt mapping.

**Rationale:**
- The discriminator is **in hand before the deletion point**: `_bind_schedule_to_caller` (`daemon/tools/self_alarm.py:927-941`) stamps `{"source":"self_alarm","bound_to_caller":True,"caller_instance_id":…}` into `instance_mappings.mapping_metadata` (a JSONB **key**, not a column), and `get_mapping` returns it (`:226-238`) — **zero extra I/O**. `source_type` is **unusable** — every self-alarm row is `source_type="scheduler"` and the scheduler path does not even pass the parameter.
- The seam's error channel is **RAISE** (the docstring already says "Raises: Exception"; the tail `:396-401` logs then raises). The upstream re-raises (`:1145-1149`) → the outer handler (`:1028-1040`) records a **FAILED** `schedule_executions` row — the only user-visible artefact on this path, and it is **fail-closed**: a bound alarm whose caller is gone fails visibly instead of being handed to a stranger.
- **Uncertainty must NOT refuse (ADR-11).** The DB-error path inside `_mapping_instance_exists` (`except → return True`, `mapper.py:198-210`) is preserved **verbatim**: it routes to the return-existing branch (`:346-351`) and **never** reaches delete+spawn. The refusal is about **stranger-spawn**, not about liveness verification — so on a DB error we return the existing mapping and suppress the spawn, exactly as today. This is the amendment to my earlier framing, which read the refusal as unconditional on the branch.
- Touching `create_instance_mapping`'s upsert would have a **cross-source blast radius** — discord / slack / telegram all upsert through it. The preservation is achieved at the **mapper's own metadata-construction site**, which is the only place that rebuilds a mapping's metadata. Without (3), the `force_new` path would silently drop the binding, re-opening E1 for the next fire.
- **E1 one-shot: consume VISIBLY** (ADR-11). The bound instance row is gone and will not return; re-arm would spin against a dead target → the one-shot is consumed and the refusal reason goes into the execution row's `error_message` (surfaced by R4). Contrast: a busy deferral is **transient** → defer; E1 is **permanent** → consume + record.
  - **CRIT-1 amendment — the "consume VISIBLY" case now has its OWN `_fire_outcome` terminal value.** DEC-9's vocabulary is extended with the **fifth terminal outcome `refused_permanent`**, whose semantics are exactly this bullet: **consume the one-shot + a `failed` execution row carrying the refusal reason**. Without it, the mapper's typed refusal falls through to the generic `failed` outcome, which by DEC-9's rule does **NOT** consume → a permanent 5s re-fire spin against a dead target. The full amendment (vocabulary, the narrow typed catch site, and the consumption-gating table) is in **DEC-9's CRIT-1 amendment block** below; this bullet is the E1-side statement of the same rule and the two are **one rule, not two**.
  - **The refusal is now reachable from TWO surfaces** (traceability, amended per D-A): **(i) the fire-time mapper refusal** (this entry — `mapper.py:336-344`) and **(ii) the arm-time binding refusal** (`self_alarm.py::_bind_schedule_to_caller`, see **DEC-21**). Both produce the same agent-visible outcome — a **typed refusal** and **no stranger spawn** — and neither may be swallowed into a generic `failed` that silently spins. The **fire-time** surface additionally writes a `failed` row and **consumes the one-shot** (that is the `refused_permanent` outcome); the **arm-time** surface has **no fire and no one-shot** — it consumes **nothing** (DEC-21).

**Rejected alternative(s):**
- **Change `create_instance_mapping`'s merge semantics** — cross-source blast radius on a hot path used by every chat source. Rejected by the leader ruling and independently by the blast-radius argument.
- **Refuse on ANY failure to confirm the instance exists (including a DB error)** — a transient DB hiccup would turn every self-alarm into a hard failure. Rejected: fail closed on **confirmed** absence only (ADR-11).
- **Delete the mapping row and let the alarm die silently** — same observable outcome as the refusal (no stranger spawn) but with no FAILED row and no diagnostic. Rejected: fail *visibly*.
- **Key the refusal on `source_type == "scheduler"`** — not discriminating (all self-alarm rows match). Rejected.
- **Key the refusal on the agent id (`ari`)** — too broad; it would refuse legitimate spawns for ordinary scheduler mappings. Rejected.

## DEC-7. [PLANNER-DECIDED] The deferred idempotency key is GENERATION-SCOPED — **AMENDED by ADR-2 (role narrowed: one-shot keeps the EXISTING run_at key)**

**Decision:** The key roles are now split [LEADER-RULED, ADR-2]:
- **One-shot** → the **existing run_at-scoped key** `scheduler:{source_id}:{configured_run_at.isoformat()}` (`scheduler.py:1112-1116`), derived from the *configured* `run_at` — **never** `next_trigger`/`now` (the D4 trap). Per-occurrence at-most-once: a crash re-fire of the same occurrence dedups; a different occurrence gets a different key.
- **Recurring** → the **generation-scoped key** `scheduler:{source_id}:deferred:v{N}`, `N` = the per-schedule monotonic `_defer_gen` in `source_configs.config` (an atomic `jsonb_set`/`json_set` sibling of `_run_counter`). A new generation opens **exactly** when the current one is no longer a live pending delivery (the guarded update's rowcount 0).
- The **generation marker is the authoritative coalescing state**; the key is only the **dedup latch**. The terminal-bypass (P3) is a **safety net, never the mechanism**.
- The key changes **only at generation rollover** — never per-fire.

**AMENDMENT — optional (b), canonical generation-marker name.** The JSONB key is **`_defer_gen`** (alongside `_defer_count`, `_defer_message_id`, `_defer_since` — DEC-12). The architect's `architecture-recommendation.md` §3 spells it **`_deferred_gen`** (`:45`, `:46`); that spelling is **SUPERSEDED** and is the **single drift source** for the whole design. This entry, DEC-12, DEC-18, DEC-19, DEC-20, DEC-22 and `plan-overview.md` all use **`_defer_gen`**. The generation **number** `N` in the recurring key `scheduler:{source_id}:deferred:v{N}` is read from that same key — the key name and the key's *value* namespace are unrelated; do not rename the key to match the `v{N}` token.

**Rationale:**
- The design must be correct **regardless of the outcome of the in-flight pivot** (`probe_pivot`: *does a COMPLETED JobItem free the key?*). The generation makes the key's lifecycle explicit instead of inferring it from an index predicate.
- **The pivot is now RESOLVED and REFUTES the poisoning hypothesis** (see DEC-13): a DONE JobItem still occupies `idx_job_idempotency`, but `JobQueueService.enqueue` bypasses a terminal match with a synthetic key and delivers. A bare stable key would therefore *not* have silently lost the delivery. The generation is kept for two independent reasons: it does not depend on the substrate's terminal-bypass branch, and the synthetic key would make the new row's `idempotency_key` differ from the intended key — breaking the "is the current generation still live?" lookup (which is why `_defer_message_id` is persisted separately rather than derived from the key).
- **Amended by ADR-2 (my earlier text applied the generation key to ALL schedules):** a one-shot has exactly one occurrence, so the per-occurrence run_at key is both sufficient and *already correct* (it is the key the direct path uses — reusing it means a crash re-fire of the same occurrence dedups instead of double-delivering). Applying the generation key to one-shots would have been a needless divergence from the direct path's existing at-most-once guarantee.
- **Never reuse the run_at key for recurring coalescing** — per-occurrence keys would produce N deliveries, defeating the coalescing intent. **Never mint per-fire keys** — defeats coalescing outright.

**Rejected alternative(s):**
- **A bare stable per-schedule key** — pivot-dependent in its original motivation, and it collapses "the live delivery is still pending" together with "the live delivery is terminal", which is exactly the distinction the coalescing rule needs. Rejected.
- **The generation key for one-shots too** (my pre-ADR-2 position) — unnecessary divergence from the direct path's existing per-occurrence key; the one-shot has no recurring episode to coalesce. Rejected (amended).
- **A `run_at`-suffixed key for recurring** — a re-armed one-shot silently escapes dedup (today's defect class). Rejected.
- **A per-fire unique key** — defeats coalescing entirely (every fire becomes its own delivery). Rejected.

## DEC-8. [PLANNER-DECIDED] ~~Frozen-payload resolution — REPLACE-IN-PLACE coalescing~~ — **SUPERSEDED-BY-ADR-1** (kept visible; successor = **DEC-18**)

> **SUPERSEDED-BY-ADR-1** (leader adjudication, 2026-10-21). This entry is retained for the audit trail; it is **no longer the design**. The teardown-then-re-enqueue mechanism described below is **replaced** by the enqueue-once + guarded in-place update of **DEC-18**. **ADR-1 rationale:** teardown's "still PENDING" check-then-act race can produce a **DUPLICATE delivery**, which breaches the wake-the-caller doctrine's "**exactly one message**, never a spawn" guarantee (hard user ruling 2026-10-20, live v0.26.2). At-most-once is the invariant this commission exists to restore; trading it for count fidelity **inverts the priority**. A race that merely lags the count one occurrence behind is **cosmetic** and is covered by the authoritative `deferred_count` surface. Two further grounds: teardown performs **three** mutations of queue-owned rows per coalesced fire (cancel Task + delete MQ + soft-delete JobItem) versus **one** conditional single-statement update that can only land while the row is still `ready` — the "second writer" objection applies a fortiori to this entry; and the scrub-seam objection is **neutralizable** (the seam is a *function*, `scrub_enqueued_body`, not a location). The mechanism below is therefore **rejected in its entirety**, not amended.

**Decision (SUPERSEDED — historical):** On each additional busy fire, if the current window's deferred delivery is **still PENDING**, tear it down with the sanctioned primitives (`TaskRepository.cancel_task` + `SQLModelMessageQueueRepository.delete` + `JobRepository.soft_delete`) and enqueue a **fresh** delivery carrying the **current** deferred count, under the **same key** (the soft-delete frees the `idx_job_idempotency` partial index, so the re-insert is a genuine fresh row). If the delivery was already claimed/running, it is left to deliver and a **new generation** is opened. **Always ≤1 PENDING deferred delivery per schedule.**

**Rationale (SUPERSEDED — recorded for the audit trail):**
- The kept delivery's message payload is **frozen** — the compensation path (`instance_messaging.py:3079-3142`) deliberately does not update it. A pure dedup would therefore report a **stale** count ("1 occurrence" forever), which understates a recurring alarm's missed occurrences.
- Tearing down first and enqueueing second is the only ordering that yields a live body: enqueue-first would hit the dedup index (the old row still owns it), the compensation path would cancel the **new** Task, and the **old** frozen body would survive — the exact failure mode the commission exists to remove.
- The fresh enqueue goes through the **normal enqueue path**, so the secret-scrub at `instance_messaging.py:2181` stays intact. A body is **never** hand-written.
- The guard "only tear down if still PENDING at decision time" is what keeps the double-delivery window bounded — **but bounding is not eliminating**, and the architect proved the window cannot be closed (the claim UPDATE can land between the read and the cancel). **That concession is the supersede trigger.**

**Rejected alternative(s) (as evaluated at the time — RE-OPENED and re-decided by ADR-1):**
- **(A) Look up the kept delivery and UPDATE its body** — rejected here for needing "a new body-write path that bypasses the scrub seam". **ADR-1 re-opens this and ADOPTS it**, neutralized by calling the existing `scrub_enqueued_body` helper before the update. **This is the option that became DEC-18.**
- **(C) Frozen count** — understates a recurring alarm's missed occurrences (the leader's own ranking: weakest). Retained only as the documented **fallback** if the teardown/claim race proves unfixable in implementation — **and that fallback is now MOOTED** (see DEC-14 item 2), because ADR-1's shape reaches the same worst case **only inside a ms-scale claim race, never by design**.
- **Pure dedup, no teardown** — freezes the count. Rejected.

## DEC-9. [PLANNER-DECIDED] One-shot consume-at-defer is ACCEPTABLE — **AMENDED by ADR-3 (CONDITIONAL on durable evidence) + ADR-5 (explicit bounds) + CRIT-1 (FIFTH terminal outcome `refused_permanent`)**

**Decision:** The one-shot is consumed **only when the deferral produced durable evidence** [LEADER-RULED, ADR-3]. **THE NORMATIVE DEFINITION (Blocking 1, leader-ruled — singular, **per-DELIVERY**, and the ONE home of this rule):** `deferred_durable` requires **a PENDING Task whose `message_id` EQUALS the `message_id` returned by THIS enqueue** (the Task row carries `message_id` — `instance_messaging.py:2316-2320`), and the DEFERRED execution row must have been written. **The check is per-DELIVERY, NOT per-INSTANCE.** The per-instance claim gate excludes only `RUNNING` (`task/repository.py:2920-2935` — PAUSED is intentionally excluded), so a busy caller routinely holds **unrelated** PENDING tasks; a **DECOY** task would satisfy a per-instance form and re-open the stranded-generation hazard (census: all 3 live reuse rows are pinned to ONE instance, `decisions.md` DEC-20.3). **A real `message_id`/`job_id` alone is NOT durable evidence** — the id is what the PENDING Task must **match**, never what proves a delivery exists on its own. **Both** earlier forms are **WITHDRAWN**: the **disjunctive** form (a real enqueue id **OR** a pending Task) and the **loose per-instance** form (`EXISTS(pending Task)` for the bound instance) — each is **false on a live path** (the question-pause marker window — see the Blocking-1 amendment block below). The **per-delivery Task-match is THE definition**. The consumption write (`_is_one_time_executed=True` + `on_complete_callback`, `scheduler.py:624-629`) keeps its **location** but becomes **gated**. The **semaphore-no-target branch re-arms and NEVER consumes SILENTLY** (DEC-22, now **generalized to every non-consuming leg** — Blocking 3: after the 24h age cap it consumes **visibly** as a terminal `failed` row, reason **`nondelivery_age_cap`**). A per-fire flag on the adapter decides the consumption — see the **CRIT-1 amendment block** immediately below for the full five-value vocabulary and the gating table.
The bound is threefold:
(a) **counter cap** — `deferred_count` saturates at 16 and the overflow is **disclosed** (the body says "16+ occurrences coalesced"); the delivery is **never dropped**;
(b) **age cap — 24h default** [LEADER-RULED, ADR-5]: a NEW `SchedulingConfig` field, env-tunable, checked at **fire ticks only** (no polling loop). On breach the **non-delivery episode terminates VISIBLY under the ONE Rule-A outcome**: abandon any still-pending delivery with **ONE** guarded statement (`WHERE status IN ('ready','retrying')` → terminal abandoned); **if** it returns a **row** → **consume** the occurrence + a **terminal `failed` execution row** (reason **`nondelivery_age_cap`**) + a **WARNING**; **if** it returns **no row** → **no consumption, no failed row** (the in-flight delivery will land); the carrier **clears**; the breach **NEVER opens a fresh generation**. **[SUPERSEDED-BY-RULE-A]** the prior form stated here — close the generation and open a fresh one whose body carries `abandoned_prior=N` — is the **REJECTED Rule B** and **must not be implemented** (it re-opens the one-shot spin the cap exists to close, and it can double-deliver because it has no abandon step). **Never a silent loss** is preserved by the terminal `failed` row + WARNING, not by a fresh generation;
(c) **E1 refusal is the terminal failure** when the caller instance row is **confirmed** gone — fail closed, FAILED execution row, consume **visibly** (permanent condition; re-arm would spin against a dead target), no stranger spawn. **CRIT-1 amendment:** this case is the **`refused_permanent`** outcome — it is a **distinct terminal value**, not the generic `failed` (see the amendment block below).

## DEC-9 AMENDMENT BLOCK — CRIT-1 (leader-ruled, FINAL): the FIFTH terminal outcome `refused_permanent`

**The defect this closes.** DEC-9's original vocabulary was `direct | deferred_durable | rearmed | failed` — **four** values, with **no terminal value for the E1 "consume VISIBLY" case**. The mapper's typed refusal (DEC-5) is raised out of `_route_via_job_queue` (`:1145-1149`) and then **swallowed by `_execute_run`'s blanket `except`** (`scheduler.py:1028-1040`), which routes it to the generic `failed` outcome. Under the four-value vocabulary `failed` ⇒ **never consume** ⇒ the one-shot re-arms ⇒ the past-due `_get_next_trigger_time` returns `now` (`:753`) ⇒ **a permanent 5s re-fire spin against a dead target**, with a `failed` row per iteration. The refusal was therefore *recorded* but *not honoured* — the exact "visible row, invisible loss" class this commission exists to remove.

**Part 1 — the FIFTH terminal outcome `refused_permanent`.** The vocabulary becomes:

```
_fire_outcome ∈ { direct, deferred_durable, rearmed, refused_permanent, failed }
```

| outcome | meaning | one-shot consumption |
|---|---|---|
| `direct` | the delivery happened on the direct path (today's behaviour) | **consume** (unchanged) |
| `deferred_durable` | the deferral produced durable evidence — **a PENDING Task whose `message_id` EQUALS this enqueue's id** (Blocking 1's normative **per-delivery** predicate) + the DEFERRED row written | **consume** |
| `refused_permanent` | **NEW** — a typed refusal that is **permanent** (**fire-time only**: the E1 confirmed-absence refusal): consume + a `failed` row carrying the **refusal reason** | **consume** |
| `rearmed` | the fire was re-armed for a later attempt (no durable carrier) | **do not consume** — the non-delivery episode is **OPEN** |
| `failed` | an unexpected error — including the **`taskless_enqueue`** leg (Blocking 1) — the intent may still be alive | **do not consume** — the non-delivery episode is **OPEN** |

**THE CAP — ONE RULE, ONE TOKEN, ON EVERY LEG (Blocking 3 — leader-ruled; the token `defer_age_cap` is **SUPERSEDED** by `nondelivery_age_cap`).** **Every NON-DELIVERY outcome opens or continues the non-delivery episode** via the **`_defer_since` carrier**: **`defer`** (a durably-deferred occurrence is **consumed-as-armed but NOT delivered**) · **`rearmed`** · **`failed`** (including `taskless_enqueue`). The carrier tracks **non-DELIVERY**, not non-consumption: `deferred_durable` consumes the one-shot but delivers **nothing**, so it opens the episode too. **This is the ONE enumeration** — it is stated here and at DEC-22 and `plan-overview.md` C1, and must not be re-listed differently anywhere else. On the **24h breach** the episode terminates **visibly**, by this **single** rule:
1. **ABANDON any still-pending delivery** with **ONE guarded statement** — `WHERE status IN ('ready','retrying')` → terminal **abandoned**.
2. **If the guard RETURNS A ROW** → the delivery is **dead** → the occurrence is **CONSUMED** with a **terminal `failed` execution row** (reason **`nondelivery_age_cap`**) + a **WARNING**.
3. **If the guard returns NO row** (no pending delivery, **OR** it was already claimed and **will land**) → **do NOT consume, do NOT write a `failed` row** — the in-flight delivery will deliver it.
4. **The breach NEVER opens a fresh generation.** For a **ONE-SHOT** a fresh generation would re-open the unbounded spin this cap exists to close (a past-due one-shot re-triggers at `now`, `scheduler.py:753`, lateness cap unset live, `config.py:2667-2673`). For a **RECURRING** schedule the next occurrence is **cadence-driven** and opens its own episode naturally — the breach does **not** open one either.
5. **The carrier CLEARS** on a successful direct delivery **OR** on a terminal breach disposition — it is **NOT** cleared by a rollover, and it is **NOT inert**: the carrier needs a **CLEARING API SURFACE** (a `clear_since` / `clear_defer_state` parameter on the state method), not set-if-absent only — without it a recurring schedule re-trips the cap forever.

**Which fields the breach touches (exact):** **`_defer_since`** (cleared — the episode ends) · **`_defer_message_id`** (cleared — the delivery was abandoned, or was already gone) · **`_defer_count`** (reset to 0 — the generation is closed) · **`_defer_gen`** (**NOT** bumped by the breach — the breach never opens a fresh generation; the next occurrence bumps it naturally). This **generalizes DEC-22** from "re-arm episodes" to **"all non-consuming episodes"** and closes the **direct-path `failed`** leg, which was previously bounded **by accident** (today's blanket `except` at `scheduler.py:1028` swallows the error and `_run_schedule` consumes at `:624`; under the plan `failed → do NOT consume`, so a past-due one-shot re-triggers immediately — `:753`, lateness cap unset live, `config.py:2667-2673` → ~**17,280** `schedule_executions` rows/day **forever**).

**`_defer_since` semantics (normative — one carrier, all legs).**
- **Set-if-absent (COALESCE semantics, IN THE METHOD SIGNATURE).** The carrier's write must be **set-if-absent** — `apply_scheduler_defer_state(..., set_since=now)` uses **`COALESCE(config->'_defer_since', now)`**, not a plain overwrite. A plain overwrite **resets the age on every cycle** and the cap **never trips**. This is a **method-signature contract**, not a call-site convention.
- **Set at the FIRST non-consuming outcome of ANY kind**: defer · re-arm · direct-failure · taskless-enqueue.
- **Cleared ONLY on a successful direct delivery** — and by the **cap's own terminal transition** (the breach **is** the end of that episode: the terminal `failed` row + the consumption close it, and the carrier is cleared **in the same write**, so a later fire opens a fresh episode instead of re-tripping the breach forever — without this the recurring schedule would re-trip the breach on every fire, recreating the unbounded row-write this cap exists to bound). **The carrier needs a CLEARING API SURFACE** (Blocking 3): `apply_scheduler_defer_state(..., clear_since=True, clear_message_id=True, reset_count=True)` — set-if-absent alone can open an episode but never close one, so a recurring schedule would re-trip the cap on every fire.
- **NEVER literally reset to null by a ROLLOVER.** A generation bump (DEC-18 item 3) does **not** clear the carrier: a literal reset would **inert the cap** — the age would restart on every rollover and the bound would never be reached.

**`refused_permanent` semantics (normative):** **consume the one-shot** AND write a **terminal `failed` execution row** whose `error_message` carries the **refusal reason**. It is the only outcome that is *both* a terminal failure *and* a consumption. It is **not** a synonym for `failed` — `failed` means "we do not know, keep the intent alive"; `refused_permanent` means "the target is provably gone; keeping the intent alive is a spin, not a safety property."

**Part 2 — the typed-error catch site (normative).** `_execute_run` must add a **NARROW catch for the mapper's typed refusal exception**, placed **BEFORE** the blanket `except` (`:1028-1040`), so the refusal is classified rather than swallowed:

```
# NARROW catch — placed BEFORE the blanket `except Exception as e:` at :1028
except BoundCallerRefusal as refusal:      # the mapper's typed refusal (DEC-5 / DEC-21)
    self._fire_outcome = "refused_permanent"
    # complete the execution row as FAILED with refusal.reason
    # record_execution_complete(execution_id, FAILED, error_message=refusal.reason)
    # → and the one-shot consumption is then driven by the _fire_outcome gate
    ... (then re-raise or return, per the surrounding contract)
except Exception as e:                      # :1028 — UNCHANGED, still the catch-all
    self._fire_outcome = "failed"
    ...
```

- The **blanket `except` stays exactly where it is** and keeps its current behaviour for **unexpected** errors (its `logger.error(...)` + `_execution_callback(..., status=FAILED)` path is untouched). The narrow catch is **additive**, placed **above** it — Python matches the first applicable `except`, so ordering is the whole mechanism.
- The typed exception is a **dedicated type** (not a bare `Exception` subclass), raised by the mapper refusal site (`mapper.py:336-344`) and by the arm-time binding refusal (DEC-21). It must carry the **refusal reason** as its message/attribute so the row's `error_message` is populated without string-matching the exception type.
- **Invariant: the narrow catch must not be reachable for non-refusal errors.** A catch written as `except Exception` in the narrow slot is a **defect** — it would re-classify every unexpected error as `refused_permanent` → consuming one-shots on transient errors.

**Part 3 — `_run_schedule`'s one-shot consumption is gated on `_fire_outcome` (normative).** The consumption write at `scheduler.py:620-632` (`_is_one_time_executed = True` at `:624`, then `_on_complete_callback(..., completed=True)`) becomes **conditional** on the per-fire outcome:

```
direct             → consume   (today's behaviour, EXACTLY unchanged)
deferred_durable   → consume
refused_permanent  → consume   (NEW — consume + the failed row exists)
rearmed            → do NOT consume
failed             → do NOT consume
```

- `direct` must preserve today's behaviour **exactly** — the one-shot still stops + disables via the registry callback (`:514-525`), and no new condition may perturb it. This is the **regression floor** of the whole commission.
- The **consumption is the ONLY thing the outcome gates**; the re-arm + `await asyncio.sleep(SCHEDULER_ERROR_RETRY_S)` behaviour for `rearmed`/`failed` is unchanged.
- **One-shot consumption is permitted ONLY after confirmed durable evidence** (L-1, DEC-18 consequence (b)) — with one clarification this amendment makes explicit: `refused_permanent` is a **terminal refusal**, not a *durable delivery*, and it consumes **because the condition is permanent**, not because a delivery exists. The two consumption cases are therefore justified on **different grounds** and must be commented as such in the implementation, so a future edit does not "unify" them by re-deriving `refused_permanent` from the enqueue's return value.

**Part 4 — pin #5 GREEN gains the CONSUMPTION assertion.** `tests/unit/test_mapper_e1_stranger_spawn_refusal_pin.py::TestE1RefusesStrangerSpawn::test_bound_caller_confirmed_gone_refuses_instead_of_spawning` — in addition to its current assertions (raises, **no** `spawn_instance_with_mcp` call, the mapping row **not** deleted, the schedule's execution row `failed`) — now also asserts the **consumption**: on the refusal leg, the one-shot **IS consumed** (the source row is stopped / `enabled=False`, `_is_one_time_executed is True`) **AND** the `failed` execution row **exists** and carries the **refusal reason** in `error_message`. Without this assertion the pin cannot distinguish the four-value vocabulary from the five-value one.

**Part 5 — pin #5 RED mutation.** The RED mutation is **remap the refusal to `failed` instead of `refused_permanent`** — i.e. in the narrow catch site, set `_fire_outcome = "failed"` (or route the typed refusal into the blanket `except`). This must turn the pin **RED** because: the one-shot is then **not consumed** (the `failed` outcome forbids consumption) → the schedule stays armed against a **provably dead** target → the **5s spin** reappears, and the consumption assertion fails. The mutation is therefore **semantically meaningful**, not merely textual: it reproduces the exact CRIT-1 defect (a refused permanent target that re-fires forever) in miniature, inside the hermetic pin.

**Traceability.** DEC-5's "E1 one-shot: consume VISIBLY" bullet is the E1-side statement of this rule; DEC-12's visibility fields are the surface that shows the refusal; `plan-overview.md` §(c) **C1** carries the vocabulary + gating table, §(d) carries the E1 traceability row (mapper refusal + arm-time refusal), and §(e) carries pins #5 and the L-1 sibling.

**Rationale:**
- The intent of the one-shot is *"deliver this to me"*. Once a Task row exists for the caller, that intent is durable; the schedule row's `stopped`/`enabled=False` state (`registry.py:514-526`) stops a *re-fire*, not the delivery.
- **ADR-3's condition is what makes the change safe:** consuming on a *failed* deferral would destroy the intent with no durable carrier — i.e. the original defect. Consuming on a *successful* deferral cannot, because the Task/MQ/JobItem trio is already committed and survives restart (the boot sweeps target `running` orphans, not `pending`).
- **The residual duplicate window is bounded and disclosed** (architect R2): the delivery may *complete* inside the enqueue→consumption window, and a crash landing between → the re-fire terminal-bypasses → a visible duplicate. Mitigation: consume immediately after the enqueue returns, plus the once-per-`run_at` guard pattern (`scheduler.py:544-556`).
- **`one_shot_max_lateness_seconds` is NOT reused** for the age cap: it measures *fire lateness* (`now - run_at`), is consumed only in the ONE_TIME past-due branch (`:725-752`), and is unset live (default `None`, `config.py:2667-2673`) — the live recurring alarm (`self-alarm:nest-patrol-recurring`, cron `0 */2 * * *`) is structurally outside it.

**Rejected alternative(s):**
- **Do not consume the one-shot when deferring (keep it armed)** — the schedule would re-fire, producing duplicate alarms and re-introducing the very duplicate-fire class G3 is meant to handle separately. Rejected.
- **Re-arm the one-shot after the deferred delivery completes** — requires observing delivery completion, which the adapter cannot do (it only observes enqueues). Rejected.
- **Consume unconditionally at the defer instant (my pre-ADR-3 position)** — consumes the intent when the deferral produced nothing durable. Rejected (amended).
- **Reuse `one_shot_max_lateness_seconds` as the age cap** — wrong measurement, unset live, structurally excludes the recurring alarm. Rejected (ADR-5).

## DEC-9 AMENDMENT BLOCK — BLOCKING 1 (leader-ruled): the Task-existence predicate, the `taskless_enqueue` leg, and the stranded-generation hazard

**The mechanism this closes (a live, currently-unguarded window).** The `_deferred_question_pause` marker (set at `daemon/graph.py:10579-10595`; the PAUSED status commits **later**, and the marker is popped at `daemon/services/instance_messaging.py:5183-5201`) makes `_prepare_enqueued_message` **SKIP PROCESS_MESSAGE Task creation** (`instance_messaging.py:2246-2249` + the skip branch `:2301-2309`) while the instance's DB status is **still RUNNING**. The `MessageQueue` row is created **unconditionally** (`:2182-2210`) — the code's own warning says *"MessageQueue row preserved as audit/record"*. In that window the **busy branch fires** (`scheduler.py:1194-1213`; the predicate itself is `:901-905` — the instance reads as RUNNING), the enqueue returns a **REAL `message_id` with NO Task**, and the plan would record `deferred_durable`, **consume the one-shot**, and persist `_defer_message_id` → a **stranded `ready` row with no resume drain** (`:2221-2222` — *"READY MessageQueue rows have no resume drain"*). The generation then **NEVER rolls over** (DEC-18's rollover keys on `rowcount == 0`, and the stranded row still matches the coalescing guard) → a **RECURRING alarm absorbs every future busy fire into a dead delivery** — **worse than today's self-healing drop**, in exactly the D6 scenario.

**Part (a) — the predicate is NORMATIVE, SINGULAR and PER-DELIVERY.** `deferred_durable` requires **a PENDING Task whose `message_id` EQUALS the `message_id` returned by THIS enqueue** (the Task row carries `message_id`, `instance_messaging.py:2316-2320`). The rule is stated **once**, here and in DEC-9's Decision line, and **cited everywhere** (DEC-12, DEC-18, DEC-19, DEC-22, `plan-overview.md` C1/D1/E1).
**Why per-instance is NOT sufficient (the DECOY hazard).** The per-instance claim gate excludes only `RUNNING` (`task/repository.py:2920-2935` — PAUSED is intentionally excluded), so a busy caller **routinely** holds unrelated PENDING tasks — and the live census shows all 3 `reuse_instance` rows pinned to **ONE** instance (DEC-20.3). A per-instance form is therefore satisfied by a **DECOY** task: the marker-window enqueue (no Task of its own) would classify `deferred_durable` → `_defer_message_id` persisted → a stranded `ready` row that **never drains** (`cleanup_old` deletes only completed/failed, `message_queue/repository.py:979-1002`) → a recurring alarm **permanently absorbed** into a dead delivery. The per-delivery match is immune: a decoy task carries a **different** `message_id` and does not match.
**Both earlier forms are WITHDRAWN** — the **disjunctive** form ("a real enqueue id **OR** a pending Task exists", formerly `plan-overview.md` §(c) C1) and the **loose per-instance** form (`EXISTS(pending Task)` for the bound instance). A real `message_id` alone is **not** evidence of a delivery.

**Part (b) — the `taskless_enqueue` leg (a Task-less enqueue is `failed`, never `deferred_durable`).** Any enqueue that returns a `message_id` but leaves **no PENDING Task whose `message_id` matches that id** is classified **`failed`** (NOT `deferred_durable`), and the adapter MUST:
1. **Best-effort clean up** the just-created `MessageQueue` row — **delete by `message_id`**. *If the cleanup itself fails, log and CONTINUE* — and **name the stranded-row residue** in the log (the row id / `message_id`), because a row that survives here is a **live generation-pin** (Note 1 below).
2. **Complete the execution row to `failed`** with the reason **`taskless_enqueue`** (the reason token is the operator-visible tell for this class). **The actual call shape (should-fix b — `reason=` DOES NOT EXIST and would be a TypeError):** `record_execution_complete(execution_id, status, error_message=…)` — the real signature is `(self, execution_id: str, status: str = ExecutionStatus.COMPLETED.value, error_message: str | None = None)` (`daemon/repositories/source/repository.py:618-624`). The reason token therefore goes in **`error_message=`**, and the status is passed **positionally** as the 2nd argument (or as `status=`).
3. **NOT consume** the one-shot — there is no durable delivery, so the intent is still alive.
4. **Re-arm** on the existing 5s loop (`await asyncio.sleep(SCHEDULER_ERROR_RETRY_S)`) — no new loop.
5. **Open the non-delivery episode** (Blocking 3's generalized carrier — `_defer_since` set-if-absent), so this leg is **bounded** like every other non-consuming leg.

**The async seam at the deferred enqueue (should-fix c — the actual call pattern).** The adapter's repository work is **synchronous** and is reached through the manager facade's thread-offload, following the house pattern of the message pipeline: `await asyncio.to_thread(self._queue_repository.claim_specific, message_id)` (`daemon/services/message_processing_pipeline.py:676-679`) and `await asyncio.to_thread(self._manager._job_queue_service._repository.stamp_message_id, job_id, ctx.message_id)` (`daemon/services/instance_messaging.py:3292-3296`). The deferred path's own calls follow the same shape — **await** the facade's coroutine for the enqueue (`await manager.enqueue_message_job(...)`), and **await `asyncio.to_thread(<sync repo method>, <args>)`** for the synchronous repository work (the state write, the guarded update, the Task lookup). The **Task existence check itself is read-only and needs NO new repository method**: `TaskRepository.get_by_message(message_id)` already exists (`daemon/repositories/task/repository.py:664-670`) and answers it — so the predicate stays implementable without a new source file.

**Part (e) — the DECOY case is part of the same leg (pinned).** An **unrelated PENDING task for the SAME instance** (a decoy — different `message_id`) must **NOT** satisfy the predicate: the enqueue still classifies as **`taskless_enqueue`**, still cleans up, still does **not** consume, still re-arms. Only a Task whose `message_id` **equals this enqueue's id** is evidence. This case is pinned in `TestTasklessEnqueue` (the DECOY leg) — a per-instance implementation would pass the plain case and fail the DECOY.

**Part (f) — a Task-less enqueue leaves NO JobItem either — the deleted MQ row is the attempt's SOLE residue.** The JobItem creation sits **inside** the same guarded branch as the Task (`instance_messaging.py:3000-3030` — the JobItem create is skipped together with the Task, precisely to avoid *"an item that has NO Task to claim"*). So a Task-less enqueue leaves: **no Task**, **no JobItem** → the **idempotency key is NOT occupied** (the key is free for the next attempt) → after the MQ cleanup, **the deleted `message_queue` row is the attempt's only residue** (plus the terminal `failed` execution row, which is the deliberate, visible audit trace). This is why the cleanup is safe to attempt and why the stranded-row residue is worth naming in the log.

**Part (c) — the coalescing target and `_defer_message_id` persistence are gated on the SAME check.** The `_defer_message_id` is persisted **only after** the per-delivery Task-match passes. **[LEADER-RULED — iter-003 B3] PRECEDENCE, now explicit:** the **coalescing LIVENESS** test is the **MQ status guard** (`status IN ('ready','retrying')` — W9); the **Task check is the STRANDED-DELIVERY test, used at ENQUEUE TIME** for durable evidence (Blocking 1 — **UNCHANGED**, `PENDING` stays verbatim there). The **coalescing gate's** Task condition therefore widens from `pending` to **non-terminal** (exclude `COMPLETED|FAILED|CANCELLED`): the Task flips to **RUNNING at claim** (`task/repository.py:2801-2804`) **before** the MQ row leaves `ready` (`message_processing_pipeline.py:464` → `:678`; `message_queue/repository.py:325-375`), and a `PENDING`-only gate fails inside that code-verified window → branch C → a **SECOND LIVE DELIVERY while the first is in flight** (W9's forbidden outcome, an at-most-once breach, and a count reset to 1). Without this gate a **Task-less `ready` row would pin the generation** (Note 1) and the recurring alarm would keep absorbing fires into a dead delivery.

**Note 1 — the stranded-generation hazard is GENERAL, not marker-specific.** The question-pause marker is the **known instance** of the hazard, but the **class** is: **ANY `ready` MessageQueue row with no PENDING Task pins the generation.** The marker window is one path; any other Task-less enqueue path (or a Task that is claimed-and-lost between the enqueue and the classification) produces the same stranded row. The Blocking-1 predicate closes the **class**, because it is stated on the **Task's existence**, not on the marker's presence.

**Note 2 — regression asymmetry vs today, disclosed.** Today a busy fire that cannot be delivered is **dropped**, and the schedule **self-heals on the next fire** (the drop leaves no pin, so the next fire re-evaluates). Under the **pre-Blocking-1** plan a stranded generation would have **absorbed recurring fires silently** — converting today's **self-healing** loss into a **permanent, silent** loss. Blocking 1 restores the self-healing property, but the **hazard class** is disclosed here and in `plan-overview.md` §(f): any implementation that reintroduces "a real `message_id` ⇒ a live pending delivery exists" re-opens it.

**Note 3 — a stranded `triggered` row has NO reconciler, BY DESIGN.** The **no-polling-loop** constraint (hard non-goal) means there is **no sweeper** that would notice an execution row left at `triggered` and repair it. The **complete-write-fails-after-enqueue case** is therefore specified explicitly: if `record_execution_complete(...)` raises (or the process dies) **after** a successful enqueue, the execution row is left at **`triggered`** (the start row was INSERTed, the complete write never landed). Consequences: (a) the row is **visible** — `last_execution_status == 'triggered'` is the **named crash TELL** (DEC-12 / optional d) — so the operator sees an open audit trail; (b) there is **no automatic repair**; (c) the **generation is not pinned** by this, because the pin comes from a persisted `_defer_message_id`, and the `_defer_message_id` write happens **before** the complete write — so a stranded `triggered` row leaves a **possibly** stranded `ready` MQ row, which is exactly the Note-1 class and is caught by the **Blocking-1 predicate on the next fire** (the next fire's Task-existence check fails → `taskless_enqueue` → cleanup + visible `failed` row). The stranded `triggered` row itself remains for the operator — that is the intended, disclosed trade.

**The 24h-cap terminal-transition pin (Blocking 3).** `tests/unit/test_scheduler_deferred_delivery_pin.py::TestNonDeliveryAgeCap::test_age_cap_breach_consumes_only_when_the_abandon_guard_returns_a_row` — plants a 24h-old non-delivery episode with a **pending** delivery → the breach **abandons** it and **consumes** the occurrence with a terminal `failed` row (reason `nondelivery_age_cap`) + WARNING; the **no-row** leg (nothing pending, or already claimed and in flight) → **no consumption, no failed row**; and the breach **does not** open a fresh generation. RED mutation = **consume unconditionally on breach** (Rule A without the guard) → the no-row leg wrongly consumes a delivery that was about to land.

**The sixth pin (Blocking 1(d)).** `tests/unit/test_scheduler_deferred_delivery_pin.py::TestTasklessEnqueue::test_marker_window_enqueue_without_task_is_failed_not_deferred_durable` — the enqueue returns a `message_id` but **no PENDING Task** ⇒ classified **`failed`**, the execution row is `failed` with reason **`taskless_enqueue`**, the one-shot is **NOT consumed**, the **MQ cleanup is attempted**, and the leg **re-arms**. RED mutation = **classify on `message_id` alone** (the pre-Blocking-1 behaviour) — that reproduces the stranded-generation shape exactly.

## DEC-10. [PLANNER-DECIDED] The deferred delivery matches the direct path's priority

**Decision:** The deferred delivery passes `priority=self._priority` (default 5, `daemon/constants.py:379`), identical to the direct path (`scheduler.py:1122`). The manager default of 1 is **not** used.

- **Priority 1 (the manager default)** — the fresh-episode attestation reset fires on `priority == 1 and type == HUMAN` (`instance_messaging.py:2419-2422`), clearing the instance's `attestation_denied_count`. A deferred alarm is **not** a fresh episode — it is a continuation of the same intent — so priority 5 keeps the attestation state intact. The coupling is **documented and pinned** (architect §10). Rejected.

**Amendment note (architect §10).** `priority=self._priority` (default 5) is also what keeps the deferred delivery out of the fresh-episode attestation reset; the coupling must be stated in the code comment so a future "harmonise the priorities" edit does not silently reset the attestation state on every deferral.

## DEC-11. [PLANNER-DECIDED] A PAUSED caller stays NON-blocking — the alarm is queued behind the pause gate — **AMENDED by ADR-7 (mechanism named, not assumed)**

**Decision:** PAUSED is **not** in the busy predicate. The alarm **is delivered**: the Task is written PENDING and sits behind the claim statement's pause gate (`task/repository.py:3008-3030` — the clause excludes `instances.status IN (:status_paused, :status_terminated)` for **all** task types, sole carve-out `heartbeat_emit_stuck`); it lands when the user resumes. **ADR-7 names the mechanism:** while paused the PENDING deferred Task **persists unchanged** (the pause cascade touches only `status='running'` rows, `instance_lifecycle.py:3762-3768`) and the gate refuses it; on resume the instance flips to RUNNING and `resume_instance_cascade` fires an **explicit `safe_notify_all_pools`** (`instance_lifecycle.py:4456-4459`; the comment at `:4386-4396` notes queued-during-pause tasks are "immediately reconsidered"), with the worker-pool 3s poll (`worker_pool.py:371`) and the `EligiblePendingSweepService` (90s, `eligible_pending_sweep.py:29-30`) as fallbacks that heal a lost notify. **"Delivery survives pause" therefore means exactly:** trio persists → gated while PAUSED → delivered on the **first turn after resume**.

**Rationale:**
- The pause is the user's **explicit hold**. Queueing behind it preserves the alarm's intent without waking a session the user deliberately parked — waking mid-pause is precisely what the pause is asking us not to do.
- The deferral is observable through the visibility fields (DEC-12), so a queued-behind-pause alarm is visible, not silent.
- Widening the busy predicate to include PAUSED would make the alarm **never** land for a parked caller (the pause gate would hold it, and the busy branch would keep deferring) — a strictly worse outcome than the current drop.
- **ADR-7 answers U1** (the one previously-unverified item): the PENDING task is not lost to the pause, is not dropped by the cascade, and is delivered on resume — verified in the e2e pack with a real pause/resume.

**Rejected alternative(s):**
- **Treat PAUSED as busy (defer-and-retry later)** — the alarm then never lands while the caller stays paused; and "later" has no trigger. Rejected.
- **Deliver into a paused instance immediately (bypass the pause gate)** — overrides the user's explicit hold. Rejected.

## DEC-12. [PLANNER-DECIDED] Visibility semantics — `deferred_count` and `last_execution_status`

**Decision:**
- `deferred_count` = occurrences coalesced into the current-or-last deferral generation **since the last DIRECT dispatch**. **Reset points (no delivery-executed callback needed):** (a) inside `_execute_run`'s reuse-mode dispatch path — the only place the adapter observes a direct delivery; (b) at generation rollover (set to 1). Saturates at 16 with in-body "16+" disclosure.
- `last_execution_status` = `get_latest_execution(schedule_id).status` (now including the new `DEFERRED` value). **`schedule_executions.status` is TEXT with only a NOT NULL constraint → the enum member is pure Python, NO migration** (architect §9, verified live PG).
- **Storage:** `source_configs.config` JSONB keys (`_defer_count`, `_defer_gen`, `_defer_message_id`, `_defer_since`) via the atomic `jsonb_set`/`json_set` pattern (`source/repository.py:147-196`) — the same substrate `_run_counter` already uses. **Single-writer discipline:** the DEFERRED row is written **adapter-direct** (2-call, `deferred-`-prefixed id); under ADR-1 the deferred path calls `manager.enqueue_message_job` **directly**, so the registry's `QUEUED` callback is **never fired** for a deferred enqueue (DEC-16) → the status is deterministic; a racing executor-thread callback would otherwise flip the row between `queued` and `deferred`.
- **`_run_counter` stays SEPARATE and is NOT incremented at defer** — it counts `_execute_run` dispatches (`:975`); deferred deliveries are queue-routed and never pass `_execute_run`. Keeping them separate preserves "counter = adapter dispatches" semantics and avoids racing the counter from the busy branch. The **divergence** (a deferred delivery does **not** advance the `#N [CONTINUATION]` numbering) is **documented and pinned** (architect §9).

**AMENDMENT — W8 (fire-time visibility semantics; leader-ruled).** After a deferred delivery **lands**, the surface reads **`deferred`** — and keeps reading `deferred` — **until the next DIRECT dispatch**. There is **no delivery-completed callback** in the design, and none is added: the adapter observes **enqueues**, never delivery completions. The status therefore reflects the **last fire's** outcome, not the delivery's fate — **BY DESIGN**, and this is the honest reading of the field's name (`last_execution_status`, not `last_delivery_status`). The **`deferred_count` resets to `0`** on the next **direct** dispatch (the reset point (a) above; the reset **value** is `0`, not `1` — `1` is the value at generation rollover, reset point (b)). Consequence to state plainly: a `deferred` reading with `deferred_count == 0` is the **normal** post-delivery shape (the delivery landed, the next fire was direct, the count was cleared) and must not be read as "a deferral is pending". The **authoritative** pending-delivery indicator is the generation marker (`_defer_message_id` present + `_defer_gen`), not the status string.

**AMENDMENT — optional (d) (the crash TELL).** `last_execution_status == 'triggered'` is the **named TELL for a crash between the start row and the complete row** (the L-1 invariant's middle leg: `record_execution_start` INSERTed, `record_execution_complete` never reached). A `triggered` reading on a schedule that should have deferred is the operator-visible signature of exactly that window — it is the one status value that means *"the audit trail is open"* rather than *"the fire ended"*. This is why the field is worth surfacing: `deferred`/`failed`/`completed` are all **closed** states, while `triggered` is the only **open** one.

**AMENDMENT — W9 (coalescing-guard widening; leader-ruled, ADOPTED — not disclose-only).** The guarded in-place update's `WHERE` clause is widened from `status='ready'` to **`status IN ('ready','retrying')`** (DEC-18's single-statement conditional update, `daemon/repositories/message_queue/repository.py::update_ready_content`). **Why:** a rollover on a **RETRYING** row would otherwise create a **second live delivery while the first is still in flight** — exactly the duplicate-delivery breach the wake-the-caller doctrine forbids ("exactly one message, never a spawn"). The `ready` row is the *normal* live case; `retrying` is the *live-but-not-yet-claimed* case, and both are legitimately "a live delivery exists". **Count semantics (documented, per W9):** the counter is the number of occurrences coalesced into the **current generation**; a row in `retrying` is **still live**, so a coalescing update against it **increments the count and commits it** exactly as against a `ready` row — the guarded update landing on a `retrying` row is a **coalesce**, not a rollover. **Rollover** remains the `rowcount == 0` outcome (the row was claimed / consumed / gone). The **`retrying` state must not be counted as terminal** anywhere in the coalescing logic; `status='ready'` alone would under-count and, worse, would leave a second delivery creatable while the first was still retrying.

**AMENDMENT — W4 (meta provenance; leader-ruled).** `update_ready_content(message_id, content, message_metadata)` — the **`message_metadata` argument is OPTIONAL**: passing `None` means **the column is left untouched** (it is not overwritten with `NULL`, and it is not re-serialised). The delivered metadata on a coalescing update must carry the **SUBSTITUTED `deferred-`-prefixed execution id** — i.e. the id of the DEFERRED row this commission writes — and **NEVER the busy fire's own `execution_id`**. Reason: the busy fire's `execution_id` belongs to a row that was **never INSERTed** (the pre-`_execute_run` skip path returns before the `triggered` INSERT at `scheduler.py:964`); stamping it into the persisted metadata would point the delivered message at a **non-existent** audit row — the same class of lie L-1 exists to prevent, one layer deeper. The `deferred-` id is real: it is INSERTed by `record_execution_start` before the enqueue (row-first, DEC-18) and completed to `DEFERRED` after it.

**Rationale:**
- The residue of a drop is currently **identical to a successful delivery** (`ScheduleDetail` has no execution-status field; `last_run_at` reads `triggered_at`). Without these two fields the fix would be invisible to the very operator it serves.
- `get_latest_execution` is **already used** by `_last_run_at`, so `last_execution_status` is nearly free — one more read on an existing query path.
- The adapter-direct write avoids touching `registry.py:489`'s routing (a shared callback path used by every source type) and makes the status **deterministic**: the registry's callback runs in an executor thread, so reusing the same execution id would let a racing `queued` callback flip the row between `queued` and `deferred`.

**Rejected alternative(s):**
- **A separate `deferred_count` table** — a new table for one integer on an existing JSON column; the counter is schedule-scoped state that already has a home. Rejected.
- **Routing the DEFERRED row through the registry callback tuple** — shared routing for a source-specific status, plus the executor-thread race. Rejected.
- **A status-enum migration** — `schedule_executions.status` is TEXT and `ExecutionStatus.is_valid` is additive-safe; a migration would be pure cost. Rejected.

## DEC-13. [WORKER-DECIDED] The pivot is RESOLVED — and it does not change the key shape

**Decision:** The in-flight `probe_pivot` question — *does a COMPLETED JobItem free the idempotency key?* — is **answered**, and the answer is recorded here so the design is not left depending on it:

- **Index level:** a **DONE** JobItem with `deleted_at IS NULL` **still occupies** `idx_job_idempotency` — the partial index's predicate (`idempotency_key IS NOT NULL AND deleted_at IS NULL`, DDL at `manager.py:7199-7205`) carries **no status filter** → completion does **not** free the key. A repository-level `create_or_get_by_idempotency_key` returns the DONE row with `created=False`.
- **Service level:** `JobQueueService.enqueue` (`daemon/services/job_queue_service.py:1459-1481`) detects a **terminal** match (`admission_state ∈ {done, dead}`) and **bypasses** the index with a synthetic key `f"{idempotency_key}#{uuid.uuid4().hex[:8]}"`, then falls through to `self._repository.create(..., job_id=job_id, idempotency_key=synthetic)` → a **fresh** JobItem is created carrying the **caller's** `job_id`.
- **Messaging layer:** the dedup detector (`instance_messaging.py:3093-3099`) compares `enqueue_returned_job.job_id != job_id` → they are **equal** → **no** phantom compensation → **the delivery proceeds**.

⇒ The commissioning hypothesis ("a stable per-schedule key kills the schedule after the first fire") is **REFUTED**. The generation-scoped key (DEC-7) is retained for the two independent reasons recorded there, and the pivot outcome does **not** need to be awaited.

**Amendment note (ADR-2).** ADR-2 affirms this entry with the **role narrowed**: the key is the **dedup latch** only; the **generation marker** (`_defer_gen` + `_defer_message_id` in `source_configs.config`) is the **authoritative coalescing state**, and the terminal-bypass is a **safety net, never the mechanism**. The happy path therefore never relies on `key#uuid8` synthetic-key semantics. One-shot deferrals use the **existing run_at key** (DEC-7, amended) — the bypass's key-minting is not part of the design at all.

**Rationale:**
- The whole point of a generation-scoped key was to be pivot-proof; with the pivot answered, the design's correctness argument strengthens rather than weakens, and the developer is unblocked from implementing without waiting for the probe to land.

**Rejected alternative(s):**
- **Reverting to a bare stable key now that the pivot is friendly** — it would collapse the "still PENDING" vs "terminal" distinction the coalescing rule (DEC-8) depends on, and would make the audit trail depend on a substrate branch that is not part of the key contract. Rejected.
- **Blocking implementation on the probe** — unnecessary: the design no longer depends on the outcome. Rejected.

## DEC-16. [WORKER-DECIDED] The DEFERRED execution row is written by exactly one writer

**Decision:** The DEFERRED execution row is written by **exactly one writer**: adapter-direct, 2-call, `deferred-`-prefixed `execution_id` — `record_execution_start` (INSERT) → the enqueue → `record_execution_complete(..., DEFERRED, ...)` (UPDATE).

**Amendment note (ADR-1, shape (ii)).** Under the adopted mechanism the deferred path does **not** route through `_route_via_job_queue` at all — it calls `manager.enqueue_message_job` **directly** with the **pinned** `instance_id` (architect §3.1, §15.10: the mapper's mapping-miss branch is the only stranger-spawn surface, so the mapper is never re-entered at defer or delivery time). Consequently the registry's `QUEUED` callback is **never fired** for a deferred enqueue, and the "suppress the callback" kwarg this entry originally required on `_route_via_job_queue` is **not needed** — `_route_via_job_queue` is **not modified**. The determinism argument is unchanged and now stronger: there is exactly one writer and no second writer can exist.

**Rationale:**
- The registry's callback runs in an executor thread (`registry.py:503-512`), so its UPDATE lands **unordered** relative to ours. Sharing one execution id would let the row's final status be `queued` or `deferred` **by scheduling luck** — a 50/50 flake, and a pinned test would be unwriteable.
- Suppressing/avoiding the callback keeps the change **local to the scheduler adapter** — `registry.py`'s routing (shared with every source type) is untouched, exactly as the planner's adjudication required.
- The `deferred-` prefix follows the `skipped-` precedent (`scheduler.py:793`) and makes the row's provenance legible in `list_schedule_executions` output.

**Rejected alternative(s):**
- **Sharing the enqueue's execution id and writing DEFERRED last** — subject to the executor-thread race described above. Rejected.
- **Changing `registry.py`'s routing to understand `deferred`** — a shared path for a source-specific status; blast radius across every source type. Rejected.
- **Writing the DEFERRED row through the registry callback tuple** — same race, plus a shared-path edit. Rejected.
- **Routing the deferred delivery through `_route_via_job_queue`** (my pre-ADR-1 shape) — it would re-enter the mapper (the stranger-spawn surface) and would require the callback-suppression kwarg. Rejected under ADR-1.

**Decision:** The change set is **additive-only with an empty migration delta** → `rollback_safe = true` (source=explicit), and the rollback is a **single revert commit**. The G3 seam is recorded so the two commissions cannot collide silently.

## DEC-18. [LEADER-RULED — L-1, ADR-1] Coalescing = enqueue-once + guarded in-place update (successor to DEC-8)

**Decision:** The coalescing mechanism is **shape (ii)**: **enqueue once**, then coalesce subsequent fires by a **SINGLE-STATEMENT conditional UPDATE of the still-pending delivery's `message_queue` row** — guard **`WHERE message_id=:id AND status IN ('ready','retrying')`**. *(The narrow `status='ready'` form previously stated here is **SUPERSEDED** — leader ruling W9: a rollover on a **RETRYING** row would create a **second live delivery while the first is still in flight**.)* **No teardown. No re-enqueue while a delivery is live.** Concretely, in `daemon/sources/adapters/scheduler.py`:

1. **Pin the target** — use the `instance_id` the busy check already resolved; **never** re-enter `mapper.get_or_create_instance` at defer or delivery time.
2. **First deferred fire of a generation** — write the generation marker (`_defer_gen`, `_defer_count`, `_defer_since` — atomic JSONB siblings of `_run_counter`), write the DEFERRED execution row (**row-first**, see the residual-disagreement note below), then `await manager.enqueue_message_job(instance_id=<pinned>, message=<body with count=1>, source="scheduler", priority=self._priority, metadata=…, idempotency_key=<key per ADR-2>)`; capture the returned `message_id` into `_defer_message_id`; log WARNING.
3. **Later fires while the delivery is live** — **do not enqueue**. Recompose the body with the incremented count, **re-scrub** it with `scrub_enqueued_body(message, *, actor=instance_id)` (`daemon/services/secret_persistence_scrub.py:1250`), and issue the guarded update. **Rowcount 1** → the count is committed to config. **Rowcount 0** (the row was claimed/consumed/gone) → **generation rollover**: bump `_defer_gen`, enqueue fresh under the new generation key, reset the count to 1.
4. **Marker-miss fallback (crash self-heal)** — if `_defer_message_id` is absent but a live deferred delivery may exist, enqueue under the generation key; a non-terminal predecessor produces a **dedup hit that returns the KEPT `message_id`** (verified: `instance_messaging.py:3266-3306` returns `original_message_id` from `JobItem-A.metadata.message_id`, never the phantom's) → persist it → the next guarded update corrects the kept body's count. The dedup path that freezes payloads becomes the **recovery** mechanism: no loss, no duplicate.
5. **One-shot consumption** — only after the **per-delivery** durable-evidence predicate passes (DEC-9: a PENDING Task whose `message_id` EQUALS this enqueue's id) **and** the DEFERRED row was written. **NOT** "the enqueue returned real ids" — that id-form is a **false equivalence** (see MANDATORY CONSEQUENCE (b) below).

The single new repository method is `update_ready_content(message_id, content, message_metadata) -> bool` in **`daemon/repositories/message_queue/repository.py`** (`SQLModelMessageQueueRepository`, class `:120`), modeled on the existing status-guarded updater in that file (the `status='ready'` guard + `RETURNING` pattern at `:290-300`, `MessageStatus.READY` `:296-297`). The scrub is applied by the **caller** before the call.

**Rationale:**
- **At-most-once is the invariant this commission exists to restore.** The wake-the-caller doctrine (hard user ruling 2026-10-20, live v0.26.2) guarantees "**exactly one message**, never a spawn". DEC-8's teardown-then-re-enqueue is a **check-then-act** sequence: the claim UPDATE (`task/repository.py:2920`) can land between the "still PENDING" re-read and the `cancel_task`, so the mitigation *narrows* but cannot *close* the window → a **duplicate delivery** = a doctrine violation. A race that merely lags the count **one occurrence** behind is **cosmetic** and is covered exactly by the authoritative `deferred_count` surface. Trading at-most-once for count fidelity inverts the priority.
- **Teardown is the bigger "second writer".** DEC-8 rejected in-place update as "a second writer on a row the queue owns" — but teardown performs **three** mutations of queue-owned rows per coalesced fire (cancel Task + delete MQ + soft-delete JobItem), versus **one** conditional single-statement update that can only land while the row is still in its pre-claim `ready` state. The objection applies a fortiori to DEC-8.
- **The scrub-seam objection is neutralizable.** The seam is a **function**, not a location: calling the same `scrub_enqueued_body` helper on the recomposed body before the guarded update keeps the pre-persist scrub invariant (`instance_messaging.py:2181`).
- **The cost is bounded and disclosed** (architect R1): the delivered body can lag one occurrence in a ms-scale update-vs-claim window; the authoritative counter is exact. This is a *fidelity* cost, not a *safety* cost.
- **Never re-enqueue under a colliding key while a delivery is live** (P3): a non-terminal predecessor → the loser Task is CANCELLED, the loser MQ DELETED and the kept payload FROZEN (`instance_messaging.py:3089-3190`) — the exact silent-loss the commission exists to remove. The terminal-bypass (`job_queue_service.py:1459-1481`) is a **safety net, never the mechanism**.

**RESIDUAL DISAGREEMENT — RESOLVED BY LEADER RULING L-1 (audit trail retained).** Architect §3 step 2 orders the steps *marker → enqueue → capture → DEFERRED row*; architect §15.8 says *"audit-row-write failure fails CLOSED (no dispatch)"*. Those cannot both hold: under the architect-literal order a row-write failure would leave a **dispatch without an audit row**. This plan writes the `record_execution_start` **INSERT before the enqueue** (so a row-write failure prevents the dispatch) and completes the row to `DEFERRED` afterwards. **The fail-closed rule wins; the deviation from §3's literal ordering was flagged here for the leader rather than silently resolved.** *(This paragraph is the record of what was flagged and how it was resolved — it is deliberately kept visible.)*

**RULING L-1 — §15.8 GOVERNS; the literal order is SUPERSEDED.** Where architect §3 step-2's literal order conflicts with §15.8's fail-closed principle, **§15.8 governs**. The literal order *(marker → enqueue → capture → DEFERRED row)* is **SUPERSEDED** by the invariant ordering **start row → enqueue → complete row (DEFERRED | FAILED)**.

**Rationale (verbatim per leader ruling L-1):**
> "the two failure modes are not symmetric. Under the enqueue-first order, an enqueue that SUCCEEDS followed by a row-write that FAILS produces a delivered-but-unaudited fire — acceptable in isolation. But the *other* leg is fatal: an enqueue that FAILS followed by a row-write that SUCCEEDS leaves a `DEFERRED` row asserting 'a delivery is pending' when NOTHING is pending. That is an audit-trail LIE, and R4's entire purpose is that a deferred fire is never misrepresented. Row-first makes both failure legs honest: INSERT-fails → no dispatch, no consumption, loud (re-arm for recurring; a one-shot stays armed and retries on the existing loop rather than being consumed); INSERT-succeeds-then-enqueue-fails → complete the row to FAILED (visible), do NOT consume, re-arm/report. So the invariant ordering is: **start row → enqueue → complete row (DEFERRED | FAILED)**."

**MANDATORY CONSEQUENCE (a) — the enqueue-failure path MUST complete the row to a FAILED/terminal status and MUST NOT consume a one-shot.** The named path is the **`_defer_delivery` failure branch**: on an enqueue exception it MUST call `record_execution_complete(execution_id, FAILED, ...)` (the same `deferred-`-prefixed id that was INSERTed), MUST **not** consume the one-shot, and MUST re-arm / report. An unfinished `started`/`triggered` row left behind would be a **stale-audit defect of its own** — the row must always reach a terminal status (`DEFERRED` on success, `FAILED` on failure).

**MANDATORY CONSEQUENCE (b) — one-shot consumption is permitted ONLY after confirmed durable evidence** — and **"the enqueue returned a real id, i.e. a pending Task exists" is a FALSE EQUIVALENCE** (Blocking 1): the id is **necessary but not sufficient**. The evidence is a **PENDING Task whose `message_id` EQUALS this enqueue's id** (DEC-9's per-delivery predicate) — a per-instance pending task (or none at all) is **not** evidence. This matches the conditional-consumption rule of DEC-9 / ADR-3; the **failure-path behaviour is now explicit rather than implied** — the failure path never consumes, and the success path consumes only after the enqueue returned real ids **and** the DEFERRED row was written.

**AMENDMENT — optional (a) (the `content=` kwarg typo — DO NOT COPY IT).** Architect §3 step 2 (`:45`) writes the enqueue as `manager.enqueue_message_job(instance_id=<pinned>, content=<composed with count=1>, priority=5, idempotency_key=…)`. **`content=` is a TYPO in the architect's prose** — the real keyword is **`message=`** (`daemon/manager.py:9504`, `async def enqueue_message_job(self, instance_id: str, message: str, source: str = "api", priority: int = 1, …)`, `:9502-9516`). Passing `content=` raises `TypeError: enqueue_message_job() got an unexpected keyword argument 'content'`. **Every enqueue in this design uses `message=`.** (The SQL column genuinely *is* `content` — `UPDATE message_queue SET content=:c` — which is almost certainly where the confusion came from; the **column** is `content`, the **kwarg** is `message`. Do not let the two collide in the implementation.)

**AMENDMENT — W7(iii) (the marker-miss pin gets a home).** Item 4's crash self-heal is now **instantiated as a named pin**: `tests/unit/test_scheduler_deferred_delivery_pin.py::TestMarkerMissFallback::test_marker_miss_after_enqueue_self_heals_via_dedup_hit_kept_message_id`. It plants the crash window (the enqueue commits, the `_defer_message_id` marker write does not), asserts that the next fire's enqueue produces a **dedup hit returning the KEPT `message_id`** (never the phantom's), that the persisted marker is the kept id, and that the **next guarded update corrects the kept body's count** — no loss, no duplicate. The RED mutation removes the marker-miss fallback branch → the assertion fails.

**Rejected alternative(s):**
- **(i) Teardown-then-re-enqueue** (DEC-8) — duplicate-delivery race = doctrine violation; three queue-owned mutations vs one guarded statement; superseded.
- **(iii) Armed re-check (lateness-cap style)** — (a) conflicts with R1: no durable pending artifact, the intent stays in an in-memory adapter loop; (b) **proven hot loop**: a re-armed past-due one-shot returns `now` from `_get_next_trigger_time` (`:753`) → `wait_seconds ≈ 0` and, with `one_shot_max_lateness_seconds` unset live, the cap branch is dead → tight spin; (c) crash/restart past the cap converts to a SKIPPED row (lost intent) — relocating the defect.
- **Guarded update with the `status` guard removed** — an unguarded content update can rewrite a row mid-claim (architect §15.6). Rejected; the guard is mandatory and is the RED mutation of pin #3. **W9 note:** the guard is now **`status IN ('ready','retrying')`** (DEC-12's W9 amendment) — removing the `retrying` half is *also* a RED mutation, because it re-opens the second-live-delivery breach on a rollover against a retrying row.
- **A teardown that is "safe enough" because it re-reads the Task status immediately before cancelling** — narrows, does not close, the race. Rejected.

## DEC-19. [LEADER-RULED, ADR-5] The deferral is bounded by two NEW `SchedulingConfig` knobs (count 16, age 24h) — visible on breach

**Decision:** Two **new** fields on `SchedulingConfig` (`daemon/config.py`, class `:2645-2673`, env prefix `ENSEMBLE_SCHEDULING_`): `defer_max_count: int = 16` (env `ENSEMBLE_SCHEDULING_DEFER_MAX_COUNT`) and `defer_max_age_seconds: int = 86400` (env `ENSEMBLE_SCHEDULING_DEFER_MAX_AGE_SECONDS`). Both are **env-tunable**; the adapter reads them from `SchedulingConfig` (**no re-declared defaults in the adapter**). Checks run at **existing fire ticks only — no polling loop**. On a cap/age breach the outcome is **VISIBLE**: a DEFERRED/abandonment row + a WARNING log + a counter — **NEVER a silent loss**.

**Rationale:**
- **Count cap 16** mirrors `PENDING_WAKE_COALESCE_MAX` (`daemon/tools/upgrade_journal.py:1101`) and the `_coalesce_wakes` shape (`daemon/services/upgrade_journal_sweep.py:533-582`) — but the **storage** differs (JSONB config keys, not a journal file). On saturation: **keep coalescing into the SAME delivery** (the guarded update continues — Blocking 4: the `count < cap` gate is **REMOVED** from C1's coalescing branch, so a saturated generation can never fall through to a second enqueue while a delivery is pending), **pin the count at the cap**, disclose "**16+ occurrences coalesced**" in the body (a saturating display — **not** `min(count+1, cap)`, which would write "16"), and **never drop the delivery**.
- **Age cap 24h** bounds a non-delivery episode that would otherwise sit forever. On breach at the next fire tick the episode terminates **visibly** under **Rule A**: abandon any still-pending delivery with **ONE** guarded statement (`WHERE status IN ('ready','retrying')` → terminal abandoned); **if** it returns a row → **consume** the occurrence + a terminal `failed` execution row (reason **`nondelivery_age_cap`**) + a **WARNING**; **if** it returns no row → **no consumption and no failed row** (the in-flight delivery will land); the carrier **clears** and the breach **never opens a fresh generation**. **[SUPERSEDED-BY-RULE-A]** the prior form here (2-call row with `error_message="deferred episode abandoned: N occurrences over Thh"`, then a **fresh generation** whose body carries `abandoned_prior=N`) is the **REJECTED Rule B** — it re-opens the one-shot spin and can double-deliver.
- **`one_shot_max_lateness_seconds` is NOT reused**: it measures *fire lateness* (`now - run_at`), is consumed only in the ONE_TIME past-due branch (`:725-752`), and is unset live (default `None`) — the live recurring alarm (`self-alarm:nest-patrol-recurring`, cron `0 */2 * * *`) is structurally outside it.
- **Both fields are pydantic-settings, not DDL** → the **migration delta stays EMPTY** and the rollback-safe posture of DEC-17 holds (architect §16).
- This supersedes my earlier "liveness bound" phrasing in DEC-9 (which leaned on the caller's liveness and the retry/dead-letter machinery) with an **explicit, tunable, visible** bound.

**Rejected alternative(s):**
- **Hard-code 16 and 24h in the adapter** — not env-tunable, and the house `SchedulingConfig` precedent (`one_shot_max_lateness_seconds` `:2667-2673`) exists precisely for this. Rejected.
- **A new table for the episode state** — architect §16: "NO". Rejected.
- **A background sweeper enforcing the age cap** — a new polling loop, forbidden by the hard non-goals. Rejected; fire-tick checks only.
- **Silently dropping the delivery on a breach** — the original defect. Rejected explicitly.

## DEC-20. [LEADER-RULED, ADR-8/ADR-9/ADR-12] Ordering + counter-divergence pins, and the per-schedule coalescing scope

**Decision:** Three architect folds are adopted into the plan and pinned:
1. **Blocking-set / queue-side divergence (ADR-9).** The adapter defers on `{RUNNING, WAITING, WAITING_CHILDREN}`; the queue serializes only against **RUNNING**. Under the fix a deferred delivery to a **WAITING** caller is claimable immediately and **WAITING_CHILDREN** is auto-resumed to RUNNING then claimable — i.e. these states now **receive** the alarm (as the next serialized turn) instead of being dropped. Turn-safety is preserved by the gate; **only timing changes**. This is a **semantic delta** and is **pinned** as a test. The blocking set itself is **unchanged** (DEC-4) and separately pinned.
2. **`_run_counter` divergence (ADR-8).** `_run_counter` counts `_execute_run` dispatches only and is **NOT incremented at defer** (deferred deliveries are queue-routed and never pass `_execute_run`). The consequence — a deferred delivery does **not** advance the `#N [CONTINUATION]` numbering — is **documented and pinned**, so a later "make the counters consistent" edit cannot silently change the continuation numbering.
3. **Per-schedule coalescing is sufficient (ADR-12).** Claim ordering is FIFO by `created_at` per instance, so N deferred deliveries for one caller land in fire order. Live census (prod PG, read-only): **14 scheduler sources; exactly 3 `reuse_instance` — all three `self-alarm:*`, all carrying `bound_to_caller`, all pinned to the same instance**; worst case today = 3 FIFO wake messages, each labelled with its own schedule + count. **Per-caller coalescing is rejected** — it would couple independent schedules' generations for marginal benefit and has no substrate support.

**AMENDMENT — W7 (the three promised-but-absent pins are now INSTANTIATED).** Items (1) and (2) above were stated as "pinned" but named no file::test. They now do — all three live in the existing commission pin file (`tests/unit/test_scheduler_deferred_delivery_pin.py`), house shape unchanged (class per pin, assembled-surface exact-string needle, header docstring naming the defect, mutation cycle plant → RED → restore → GREEN):

| # | Pin (file::class::test) | What it locks | RED mutation |
|---|---|---|---|
| **W7(i)** | `::TestBusyPredicate::test_busy_predicate_is_exactly_running_waiting_waiting_children` | the busy predicate stays **exactly** `{RUNNING, WAITING, WAITING_CHILDREN}` (DEC-4) — asserted as an **exact set**, not a subset | add `PAUSED` (or drop `WAITING_CHILDREN`) to the predicate tuple → RED |
| **W7(ii)** | `::TestRunCounterDivergence::test_run_counter_counts_direct_dispatches_only_and_is_blind_to_deferrals` | `_run_counter` counts **DIRECT dispatches only** and is **blind to deferrals by design** (ADR-8) — a deferred fire leaves `_run_counter` unchanged and the `#N [CONTINUATION]` numbering un-advanced | increment `_run_counter` on the defer path → RED |
| **W7(iii)** | `::TestMarkerMissFallback::test_marker_miss_after_enqueue_self_heals_via_dedup_hit_kept_message_id` | architect **R3** crash-window: a marker-miss after a committed enqueue self-heals via the dedup-hit's **returned kept `message_id`** → the guarded update corrects the body (DEC-18 item 4) | remove the marker-miss fallback branch → RED |

**AMENDMENT — optional (c) (the ADR-9 ordering-delta pin gets a home).** The WAITING/WAITING_CHILDREN ordering-delta test, named but homeless in the previous draft, is now pinned at `tests/unit/test_scheduler_deferred_delivery_pin.py::TestWaitingOrderingDelta::test_waiting_and_waiting_children_receive_alarm_as_next_turn` — it asserts that a deferred delivery to a **WAITING** caller is claimable immediately and to a **WAITING_CHILDREN** caller is auto-resumed to RUNNING and then claimable, i.e. both states **receive** the alarm as the **next serialized turn** (the semantic delta of ADR-9 — previously dropped). RED mutation: restore the old "drop on busy" behaviour for those two states → RED.

**Note on the W7(ii) pin's phrasing.** "Blind to deferrals" is the **intent**, not an accident: the two counters answer **different questions** (`_run_counter` = adapter *dispatches*; `_defer_count` = occurrences coalesced into the current *deferral generation*). A future edit that tries to "make the counters consistent" would change the `#N [CONTINUATION]` numbering semantics — this pin exists to make that edit **fail loudly** instead of silently renumbering every continuation message.

**Rationale:**
- (1) is a **behaviour delta** the reviewer must see: the fix makes previously-dropped states receive the alarm, and the timing of that delivery differs by state.
- (2) is the classic silent-semantic-drift risk: two counters that look interchangeable but answer different questions.
- (3) bounds the blast radius of the whole commission: the live population of affected schedules is **3**, not 14 — the change is small in production terms even though the mechanism is general.

**Rejected alternative(s):**
- **Widen the adapter's busy set to match the queue's RUNNING-only gate** — would change which fires defer and would re-open DEC-4. Rejected; the divergence is **pinned**, not erased.
- **Increment `_run_counter` at defer time** — it would make the counter mean "adapter attempts" rather than "adapter dispatches", and would race the counter from the busy branch. Rejected.
- **Per-caller coalescing** — couples independent schedules' generations; no substrate support; marginal benefit over the count-in-message labelling. Rejected (ADR-12).

## DEC-21. [LEADER-RULED — D-A] **REFUSE-TO-ARM** — a binding-write failure must not leave an ARMED-UNBOUND alarm

**Decision:** `_bind_schedule_to_caller` (`daemon/tools/self_alarm.py:873-957`) currently fails **best-effort**: its `except Exception` block (`:942`, comment *"the binding is best-effort"*) logs a WARNING and returns **`None`** (`:950`) — while the schedule row has **already been created/updated** and the arm proceeds. The result is an **ARMED but UNBOUND** reuse-mode alarm (`wake_target_bound:false`). **FIX (leader-ruled D-A): adopt REFUSE-TO-ARM** — a binding-write failure ⇒ **REFUSE to arm** and surface a **clear TYPED error naming the binding failure** to the agent. It is **NOT** `return None` + armed-unbound. **Schedule-row disposition (leader ruling F1):** the already-created/updated row is left **DISABLED AND UNARMED — NOT deleted** — `status='stopped'` + `enabled=False`, the codebase's own sanctioned not-armed transition (the same one `_on_complete_callback` applies to a consumed one-shot, `daemon/sources/registry.py:522-523`).
**EVICTION-FAILURE DISPOSITION (should-fix a — the seam is best-effort BY CONSTRUCTION).** `_evict_and_stop_adapter` catches and swallows both failure modes (`scheduling_service.py:539-549`: `registry.unregister` → WARNING on failure, `await adapter.stop()` → WARNING on failure), so a refusal **can** leave the adapter live. **Specified outcome when eviction ITSELF fails:** **(1)** the arm-time refusal **still raises the typed error to the caller** (the arm did not succeed — the caller must not be told it did); **(2)** the **row flags are retained** (`status='stopped'` + `enabled=False`) — they are the durable, always-applicable half of the disarm; **(3)** the failure is logged at **ERROR** (not WARNING) with the reason code **`adapter_evict_failed`** and the `source_id`, because the **adapter may still be live** — that is the operator-facing signal that a running adapter may still fire the unbound alarm; **(4)** the **doctrine invariant is restated**: the alarm must **never** be left armed-unbound **silently** — an eviction failure is **loud**, typed and logged, never a quiet success. The implementer must therefore **not** treat the seam's internal `except` as "the eviction succeeded".

**ADAPTER DISPOSITION (leader ruling Blocking 2) — the row flags are NOT sufficient; the adapter must be EVICTED + STOPPED.** `enabled` is consulted **only at boot** (`registry.py:291`), the adapter is **already running** when the binding fails (create path: `scheduling_service.py:768` registers + starts **before** `_bind_schedule_to_caller` at `self_alarm.py:1036`; reuse path: `:1026` evict+stop → `:1062` rebuild + start → bind at `:1151`), and the adapter loop **never re-reads `enabled`** (`scheduler.py:519-520`). So row flags alone leave a **running** adapter whose next tick fires the unbound alarm. **The refusal path MUST therefore also evict + stop the adapter** through the **existing seam** — `_evict_and_stop_adapter` (`daemon/services/scheduling_service.py:527-549`: `registry.unregister(source_id)` then `await adapter.stop()`) — **IN ADDITION to** the row flags. (F1's `registry.py:522-523` precedent transfers only for a **consumed** one-shot, whose loop **breaks itself** at `scheduler.py:631`; an arm-time refusal has no such self-termination.)

**Rationale:**
- **The armed-unbound alarm is the stranger-spawn door.** An unbound reuse-mode alarm fires with no pinned caller. **BRANCH CORRECTION (Blocking 2 — the earlier text here cited the WRONG branch):** an arm-time binding failure leaves **NO mapping row** for the caller, so the historical spawn path was the **NO-MAPPING fall-through** (`mapper.py:352-360` — *"No valid mapping exists - create new instance"* → `spawn_instance_with_mcp`), **not** the stale-mapping branch (`mapper.py:336-344`) — that branch is the **stale**-mapping case (a mapping that exists but whose target is gone). Either way the outcome is the same: **a fresh `ari` is spawned** — a **stranger** — which is precisely the breach the wake-the-caller doctrine forbids (hard user ruling 2026-10-20, live v0.26.2: "**exactly one message, never a spawn**").
- **E1's two surfaces cover DIFFERENT branches — and only one of them is the fire-time one (Blocking 2 disclosure).** **Fire-time E1 (DEC-5) covers the STALE-MAPPING branch ONLY** (`mapper.py:336-344`: a mapping exists, its target is confirmed gone → refuse, never delete+spawn). The **no-mapping fall-through** (`:352-360`) is closed by the **arm-time** refusal here (DEC-21) — an unbound alarm has no mapping to go stale. **That split is exactly why the adapter must ACTUALLY STOP** (the eviction above): if the row flags left the adapter running, the next tick would take the no-mapping fall-through and spawn the stranger, and **no fire-time E1 check would ever see it** (there is no mapping row to check).
- **Refusing loudly is strictly better than arming unbound.** An unbound arm produces, in the best case, a **wake to nobody** and, in the worst case, a **stranger spawn**. A refusal produces an **agent-visible typed error** naming the binding failure — the agent can re-arm (the row may already exist; the refusal says exactly what to fix). Refusing is the *recoverable* outcome; arming unbound is the *dangerous* one.
- **The doctrine already exists in the same file.** `daemon/tools/self_alarm.py:318` carries the comment *"a degraded alarm is REFUSED, never armed"* for the degraded-alarm path. DEC-21 applies **the same doctrine to the binding path** — this is a **consistency fix**, not a new policy.
- **Blast radius ≈ 0.** `self_alarm.py` is **already touched** by this commission for D4 (the `deferred_count` / `last_execution_status` response fields, §(c) C4). The change is confined to the binding helper's failure path and its two call sites (`_create_arm` `:1036`, `_reuse_alarm` `:1151`), both of which must treat the refusal as a refusal.
- **Same doctrine, two times.** The arm-time refusal (here) and the fire-time mapper refusal (DEC-5) produce the **same agent-visible outcome** — a typed refusal, no stranger spawn — at two different moments. The **traceability table is updated accordingly**: **E1 = mapper refusal (fire-time) + arm-time binding refusal**. Neither may be swallowed into a generic failure.

**NAMED ASSERTION — "a refused arm cannot fire." (RESTATED against the STOPPED/UNREGISTERED adapter, Blocking 2).** After a refused arm **ALL** of the following hold: the schedule is **NOT enabled** (row flags, `enabled=False`, status='stopped'); the schedule is **NOT running** — the adapter is **evicted from the registry and stopped** (`registry.unregister` + `adapter.stop()`, `scheduling_service.py:527-549`); **NO mapping exists** for the caller (the binding write failed); a **forced fire attempt** on that row yields **no delivery** (no Task, no MessageQueue row, no JobItem, no `schedule_executions` row asserting a delivery); and **no spawn** occurs (neither `spawn_instance_with_mcp` nor the no-mapping fall-through `mapper.py:352-360` is reached). **Why the restatement was necessary:** the F1 row flags alone **cannot** deliver "cannot fire" — `enabled` is read only at boot (`registry.py:291`) and the running loop never re-reads it (`scheduler.py:519-520`) — so the pre-Blocking-2 wording asserted something the live code could not satisfy. The assertion is pinned by `tests/unit/test_mapper_e1_stranger_spawn_refusal_pin.py::TestE1RefusesStrangerSpawn::test_binding_write_failure_refuses_to_arm_and_leaves_the_schedule_unarmed` (F3), which now also asserts the **adapter is unregistered**.

**Interaction with the `refused_permanent` outcome (DEC-9's CRIT-1 amendment).** The arm-time refusal fires at **arm** time, not **fire** time — there is no fire, hence no `_fire_outcome` and no one-shot consumption to gate. It surfaces as a **tool-level typed error** to the agent. The `refused_permanent` outcome is the **fire-time** analogue. The **shared invariant** is: *a refusal is never downgraded into a silent success or a generic failure*. **The arm-time path leaves the intent for the agent to retry and does NOT silently consume or delete the created row** — the row is retained, stopped and disabled (the F1 disposition), so the agent can re-arm it once the binding condition is fixed.

**BEHAVIOR CHANGE — disclose at promote.** **RETROSPECTIVE ONLY (under-disclosure, Blocking 2):** this fix governs **arms that happen after it lands**; **pre-existing armed-unbound rows are NOT swept** — the live census shows **no armed-unbound row** today (all live `self-alarm:*` reuse rows carry `bound_to_caller`, DEC-20.3), so live exposure is **nil**, and no backfill is in scope. A `self_alarm` whose **binding write fails** is **no longer armed unbound**. Previously: the arm succeeded with `wake_target_bound:false` (the alarm existed, would never wake its caller, and could spawn a stranger on a later fire). Now: the arm is **refused loudly** with a typed error naming the binding failure. A caller that previously saw a successful arm response may now see a **refusal** — this is the intended fail-closed direction, and the failure it prevents (a stranger spawn) is worse than the friction it creates. The refusal is **retryable by the agent**: re-arming after the binding condition is fixed succeeds.

**Rejected alternative(s):**
- **Keep `return None` and mark the alarm unbound (`wake_target_bound:false`)** — preserves the stranger-spawn door at the arm-time edge. Rejected (leader ruling D-A).
- **Fail the whole `self_alarm` call on any binding error** — broader than needed; the refusal is scoped to the **binding write**, and the agent-visible error names that specifically so unrelated failures are not conflated with it.
- **Defer the binding to fire time (bind lazily)** — moves the failure later and leaves the arm-time window unguarded; it would also duplicate DEC-5's fire-time refusal path for a condition that is knowable at arm time. Rejected.
- **Refuse only when the schedule is `reuse_instance` mode** — the binding is only meaningful in reuse mode, but the helper is the single seam; keeping one failure policy is simpler than a mode-dependent one, and the mode check is already implicit in the binding path.

## DEC-22. [LEADER-RULED — D-B, **GENERALIZED by Blocking 3**] EVERY non-consuming leg is under the 24h age cap — `_defer_since` is the **NON-DELIVERY EPISODE carrier**

**Decision (as originally ruled, D-B):** the re-arm branch (DEC-2 branch 2 — the semaphore **no-deferrable-target** leg) never opened a deferral episode: it did **not** set `_defer_since`, so the 24h age cap (DEC-19) **could never trip there**. D-B required `_defer_since` to be set at the first re-arm deferral, and the 24h breach to **consume VISIBLY** — a terminal `failed` execution row, a **WARNING** log, and the counters surfacing it — **amending L-B** from *"never consume"* to *"**never consume SILENTLY** — after the age cap, consume visibly as failed"* (consistent with **L-E**: a breach is **visible**, never a silent loss).

**GENERALIZATION (Blocking 3, leader-ruled) — this entry now covers EVERY non-consuming leg, not just the re-arm leg.** The carrier **`_defer_since` is the NON-DELIVERY EPISODE carrier**: it is set (set-if-absent) at the **FIRST non-consuming outcome of ANY kind** — **defer** · **re-arm** · **direct-failure** · **taskless-enqueue** — and the **24h breach terminates the episode visibly on every leg**, by the **ONE** rule (DEC-9's cap block): abandon any still-pending delivery with **ONE** guarded statement; **if** it returns a row → **CONSUME** the occurrence + a **terminal `failed` execution row** (reason **`nondelivery_age_cap`**) + **WARNING**; **if** it returns **no row** → **do not consume and do not write a failed row** (the in-flight delivery will land); the breach **never opens a fresh generation**; and the carrier **clears** (via a **clearing API surface**, not set-if-absent only). **The reason token `defer_age_cap` is SUPERSEDED by `nondelivery_age_cap`** (the cap is no longer re-arm-specific). This closes the **direct-path `failed` leg**, which the approver found **unbounded**: under the plan's `failed → do NOT consume` a past-due one-shot re-triggers immediately (`:753`, lateness cap unset live, `config.py:2667-2673`) → ~**17,280** `schedule_executions` rows/day **forever** — today that leg is bounded **by accident** (the blanket `except` at `scheduler.py:1028` swallows the error and `_run_schedule` consumes at `:624`), which is exactly the kind of accidental bound a design must not rely on. The carrier's write is **set-if-absent (COALESCE semantics, in the method signature)** — a plain overwrite would reset the age each cycle and the cap would **never trip**. **`_defer_since` is cleared ONLY on a successful direct delivery** (and by the cap's own terminal transition) and is **NEVER literally reset to null by a rollover** — a literal reset would **inert the cap**. The full carrier contract is stated once in the **DEC-9 amendment block** above.

**Rationale:**
- **The unbounded loop.** A saturated semaphore (every acquire times out) + a **past-due `new_instance` one-shot** = the re-arm branch on every tick, and the mandatory sleep (`SCHEDULER_ERROR_RETRY_S` = 5.0s) sets the cadence at **0.2 Hz**. Because the branch never opened an episode, `_defer_since` was never set ⇒ **the 24h cap was unreachable there** ⇒ the loop is **unbounded**: one **DEFERRED row per re-arm** ⇒ **~17,000 rows/day** (`0.2 Hz × 86,400 s = 17,280`) of `schedule_executions` churn, on top of the CPU/log cost of the spin itself.
- **Visible termination is the correct ending.** After 24h the condition is **still** failing, so re-arming is still futile — but an *infinite* re-arm is not a safety property either. The right ending is a **terminal, explained outcome**: consume the one-shot (only when the abandon guard actually returns a row — DEC-9's one rule), write the `failed` row with reason **`nondelivery_age_cap`** (the `defer_age_cap` token is **superseded**), log WARNING, surface the counter. The operator sees *why* the alarm stopped, instead of finding a silent hole.
- **The 5s cadence is KEPT.** The sleep is not the problem — the problem was the **unbounded episode**. DEC-22 bounds the **episode** (24h), not the **cadence**: the re-check stays at 5s, and the episode terminates visibly at the cap. Removing the sleep would be a *regression* (it reintroduces the hot-loop CPU spin, architect R5).
- **The bound is honest.** R5's real bound is therefore: **the semaphore is released** (the re-arm succeeds) **OR** the **24h cap terminates the episode visibly** — not "the age cap eventually helps", which was never true for this branch. **After the Blocking-3 generalization the same bound applies to EVERY leg**: a direct failure, a taskless enqueue and a deferral are all bounded by the **same** carrier and the **same** 24h termination — there is **no leg left unbounded**.

**BEHAVIOR CHANGE — disclose at promote.** A one-shot that has been **re-armed for ≥24h** under a permanently saturated semaphore is now **consumed with a visible `failed` row** (reason **`nondelivery_age_cap`** — the `defer_age_cap` token is **superseded** by the one-token rule) instead of re-arming **forever**. Previously (and under the intermediate "never consume" reading) the intent would have been retried indefinitely — and, for a past-due one-shot, **~17k DEFERRED rows/day** would have accumulated. The alarm is **lost**, but it is lost **visibly and with a reason**, exactly once, instead of being retried silently forever. **THE ABANDONMENT CASES (widened — this is NOT the only case):** **(i)** a one-shot re-armed for ≥24h (the case above); **(ii)** a **durably-deferred** occurrence whose delivery is still pending when the 24h cap trips — because a `deferred_durable` occurrence is **consumed-as-armed but NOT delivered**, the **defer** leg opens the non-delivery episode too (the ONE enumeration, DEC-9's cap block), so at the breach the still-pending delivery is **abandoned** by the guarded statement and the occurrence is **consumed** with a terminal `failed` row (reason `nondelivery_age_cap`) + WARNING. **Both are visible terminations, not silent losses**, and both are disclosed here and in `plan-overview.md` §(f).

**ADDENDUM — [LEADER-RULED — Q1 refinement] the breach rule's no-row case SPLITS BY IN-FLIGHT-NESS.** This **refines** (and does **not** replace) the one-rule text above: the rule's "the guard returns **no row**" leg is **two** legs, and the distinction is whether a **non-terminal Task exists for the episode's `_defer_message_id`**:
- **(i) a PENDING delivery exists** → the guarded abandon **returns a row** → **abandon + consume + a terminal `failed` row** (reason `nondelivery_age_cap`) + WARNING.
- **(ii) NO pending delivery, BUT one is IN-FLIGHT** (a **non-terminal** Task exists for the episode's `_defer_message_id`) → **no consume**, **carrier retained** — the delivery **will land**.
- **(iii) NEITHER** (no pending delivery and no in-flight non-terminal Task — the **delivery-less leg**) → **TERMINATE VISIBLY**: **consume** + a terminal `failed` row (reason `nondelivery_age_cap`) + WARNING + **carrier cleared**.
**Why (iii) is required:** legs (i) and (ii) both end the episode — (i) by consuming, (ii) by the delivery landing — but the **delivery-less** leg has **no** terminal event of its own, so under the two-leg rule it would **re-arm indefinitely** (the delivery-less-leg spin this refinement closes). Leg (iii) gives that leg the same **visible termination** the other two have. **The carrier is cleared ONLY on (i) and (iii)** — leg (ii) **retains** it, because the episode is not over: the delivery is still coming.

**Rejected alternative(s):**
- **Leave the re-arm branch outside the age cap** (the pre-D-B state) — an unbounded 0.2Hz loop writing ~17k rows/day. Rejected (leader ruling D-B).
- **Bound the re-arm by the COUNT cap instead of the age cap** — the count cap is a **body-disclosure** cap (the body says "16+ occurrences coalesced"), not a termination cap; it does not stop the loop. Rejected.
- **Consume immediately on the first re-arm** — that is the original silent-loss defect (the intent is destroyed with no carrier). Rejected (ADR-3).
- **Remove the 5s sleep and rely on the age cap** — re-introduces the CPU/log hot loop; the cap bounds the episode, the sleep bounds the rate. Rejected.
- **Keep today's consume-on-first-failure semantics for the DIRECT leg** (the pre-Blocking-3 alternative) — the one-shot is consumed the moment a direct failure occurs. Rejected (leader ruling, Blocking 3): a **transient** failure would **kill the alarm on the first hiccup** (a single DB blip, one timeout) — the alarm's intent is destroyed with no carrier, which is the **original defect class** this commission exists to remove. The **generalized cap** preserves **bounded retries** (the intent survives up to 24h of continuous failure) while **guaranteeing termination** (a visible `failed` row, never a silent spin). Consume-on-first-failure trades a bounded-retry problem for an unbounded-loss problem.

## DEC-23. [LEADER-RULED — Q3] The routing-gate widening — project-less scheduled reuse fires route via the job-queue path

**Decision:** The **routing-gate widening is KEPT**: a **project-less** scheduled reuse fire routes via the **job-queue path** (`daemon/sources/adapters/scheduler.py:1869-1877` — the `if` now admits `self._instance_mode == SchedulerInstanceMode.REUSE_INSTANCE` **in addition to** `self._project_id`, and routes through `await self._route_via_job_queue(...)`). The live `self-alarm:*` population carries **no `_project_id`** on its source rows, so before the widening such fires were left **UNROUTED** — i.e. **dead**: no MessageQueue row, no Task, no delivery, and no audit row.

**Rationale:**
- **The widening is LOAD-BEARING for D1.** DEC-1/DEC-9's whole mechanism is the deferred-delivery path: a busy caller must still **receive** its alarm (D1), and the durable-evidence predicate (a PENDING Task whose `message_id` equals the enqueue's id) can only ever be satisfied by a fire that actually **routes** into the queue. A project-less `self-alarm:*` fire that is left unrouted never reaches the deferral logic at all — so **reverting the widening would leave the deferred-delivery fix inert for exactly the bindings it protects** (the `self-alarm:*` population is the live population the fix exists for). The job-queue route is also the **only** route that produces a **durable** delivery (MessageQueue + Task + JobItem); routing through the immediate path hands the alarm to a handler that may never enqueue it.
- **The live population is project-less.** The `self-alarm:*` source rows carry **no `_project_id`**, so the `_project_id`-only gate excluded precisely the schedules this commission is about — the fix would have been correct in the abstract and inert in production.
- **It is consistent with the reuse-mode contract.** A reuse-mode schedule **always** has a pinned caller to wake, so taking the durable route (rather than the immediate path) is the semantically correct choice for it, independent of project scoping.

**Consequences (all disclosed):**
- **(a) Load-bearing for D1** — as above: reverting the widening **disables** the deferred-delivery fix for the live `self-alarm:*` population. The widening and the fix land and stand **together**.
- **(b) Blast radius (disclosed).** Any **project-less non-self-alarm reuse schedule** (if one ever exists) would **also** route via the job-queue path. The population is today **3 `reuse_instance` rows, all `self-alarm:*`** (DEC-20.3), so the live blast radius is **nil** beyond the intended population — but the gate is **mode-based, not source-based**, and that is stated rather than assumed.
- **(c) Promote disclosure.** The widening is a **behaviour change** for project-less scheduled reuse fires (previously **unrouted/dead**, now a **durable queued delivery**) and **must appear in the promote disclosure** (`plan-overview.md` §(f), R15).

**Rejected alternative(s):**
- **Revert the widening and keep the `_project_id`-only gate** — rejected (leader ruling, Q3): it re-breaks D1 for the live population, leaving the entire deferred-delivery mechanism inert for exactly the `self-alarm:*` bindings it protects. The fix would ship green and deliver nothing.
- **Keep the widening but scope it to `self_alarm` sources** (a source-type check in the gate) — a narrower blast radius, at the cost of a second, source-specific routing rule beside the mode-based one; it also couples the scheduler adapter to one source's identity. Not adopted; the mode-based gate is the general rule and the blast radius is disclosed instead.
- **Give the `self-alarm:*` rows a `_project_id` instead of widening the gate** — a **data** change to the live population (and a product decision about which project these alarms belong to), not a routing change. Out of scope for this commission, and it would make the fix depend on a data migration that has not been agreed.
