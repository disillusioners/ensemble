# Phase 3 — D3: Logging that survives anything

**Deliverable:** D3 — LOGGING THAT SURVIVES ANYTHING.
**Depends on:** P0, P2 · **Blocks:** P5.

---

## 1. Objective

Make the executor's own narrative **durable and per-run**, and make phase transitions visible **mid-phase**,
so that a stall is never a 37-minute black box.

Three concrete gaps in today's logging, all verified at TIP:

| # | Gap | Evidence | Consequence |
|---|-----|----------|-------------|
| **G1** | **One shared log file.** `executor_log_path()` (`daemon/tools/upgrade_journal.py:2179`-`:2180`) returns `<install>/data/upgrade.log` for **every** run. | `daemon/tools/upgrade_tools.py:208` (`_UPGRADE_LOG_REL`), the daemon-side reader `_upgrade_log_tail` (`:941`-`:966`). | Per-run correlation is impossible; the 2026-10-28 investigation had to date the run by **file mtime** (`evidence/FORENSICS.md` §3.2). Concurrent runs interleave. |
| **G2** | **Write failures are structurally invisible.** `_log` (`lib.sh:222`) and `_warn` (`lib.sh:224`) both carry `2>/dev/null` ⇒ they **cannot report a write failure**. | `lib.sh:222`, `:224` (verified at TIP). | A full disk, a closed stdout or a read-only log silently swallows the narrative — precisely the "lost log lines" shape the board item described. |
| **G3** | **No per-line timestamps.** The aggregate log's lines carry no time prefix. | `evidence/FORENSICS.md` §6-9 (verbatim: *"data/upgrade.log carries no per-line timestamps"*). | A 37-minute window cannot be delimited inside the file; only the journal rows (4 of them) and the file mtime bound it. |

Plus two **latent** hazards in the same family:

| # | Hazard | Anchor | Consequence |
|---|--------|--------|-------------|
| **H1** | The daemon's **client stderr PIPE** is drained only on the fast-fail path; a long-lived client can fill the 64 KiB pipe and block the **client**. | `daemon/tools/upgrade_journal.py:2743`-`:2759` | A daemon-side stall of the same family as the incident (not this incident — the payload's stdio is a file). |
| **H2** | The benign `\| head -1` early-close race in `_supervision_owned_pids` produces `printf: write error: Broken pipe` lines that masquerade as a dead-parent symptom. | `lib.sh:4583` (tip) / callers `:4734`, `:4790`; HUNG `:4413`/`:4439` / `:4563`, `:4619` | 64 historic EPIPE lines in the aggregate log (lines 3–585) — all from earlier attempts, none from the Oct-28 run (`evidence/FORENSICS.md` §3.2). The forensic cost of the red herring is already paid once. |

**What must be true after this phase**

* **O1** — The executor's narrative for one run lives in a **per-run pair of files** — the narrative file
  (`<env>/<run_id>.log`) and the payload stream (`<run_id>.payload.log`) — and survives the death of the parent
  (the daemon) and of the client. **[fold: W4 — the single-file-era wording is retired]**
* **O2** — The shell's log lines are written **directly to that file** (the primary sink), *not* dependent on
  stdout being connected to anything.
* **O3** — stdout/stderr become **best-effort mirrors**: never load-bearing, never blocking, never fatal.
* **O4** — Phase transitions are visible **mid-phase** (a timestamped marker per preflight step).
* **O5** — A write failure is **reported**, not swallowed.
* **O6** — The existing daemon-side reader and the human entry point (`data/upgrade.log`) keep working.

## 2. Decisions

| ID | Decision | Rationale | Rejected alternatives |
|----|----------|-----------|---------------------|
| **D3-1** | **A per-run log file** at `<install>/data/upgrade/<run_id>.log` becomes the **primary** sink; the systemd unit's `StandardOutput`/`StandardError` are pointed at it (`daemon/tools/upgrade_journal.py:2536`-`:2537`), and the **shell writes to it directly** via an env-carried path. | The payload's stdio is **already** systemd-owned `append:` (a real file) — so the *file* is the durable sink and stdout is only a conduit. Making the file per-run solves G1 without changing the transport model. | Keeping one aggregate file — rejected: it is the direct cause of G1 and of the mtime-dating forensic cost. A **symlink** `data/upgrade.log` → newest per-run file — rejected: two concurrent runs race the symlink, and a reader that opened the aggregate earlier follows a moving target. | **[SUPERSEDED by D3-12 — fold: A22]** |
| **D3-2** | The **shell writes the file itself** (`_log`/`_warn` append to `$ENSEMBLE_UPGRADE_LOG_FILE`) and, when that variable is set, **does not also write to stdout** (no duplication with systemd's `append:` capture of the same file). When the variable is **unset** (manual/legacy runs), `_log`/`_warn` behave exactly as today (stdout/stderr). | Makes the file the **primary** sink (O2) and the transport a mirror (O3). Avoids double-writing the same line into the same file. | Shell writes to stdout only, systemd captures — rejected: that is today's design and it makes the narrative depend on the stdout plumbing (the exact fragility D3 exists to remove). Shell writes to **both** file and stdout while systemd also captures stdout — rejected: every line appears twice in the same file. |
| **D3-3** | **`data/upgrade.log` is preserved as the human entry point** via a **pointer line** appended per run (`run_id=<id> log=data/upgrade/<id>.log`), and `_upgrade_log_tail` is extended to follow the pointer. | O6 (no break for the daemon's reader or for the operator's habit). A pointer line is auditable and does not race, unlike a symlink. | Dropping the aggregate — rejected: it breaks `_upgrade_log_tail` (`daemon/tools/upgrade_tools.py:941`) and every runbook that points at it. | **[SUPERSEDED by D3-12 — fold: A22]** |
| **D3-4** | **Per-line timestamps** are added to the shell's own log lines (ISO-8601 UTC, second precision). The aggregate file's legacy untimestamped lines stay as they are. | G3. Second precision is enough to delimit a stall window and matches the journal's own granularity. | Sub-second timestamps — rejected: noise; the journal rows carry the precise instants. Leaving the log untimestamped — rejected: G3 is the reason the 37-minute window was hard to delimit. |
| **D3-5** | **A write failure is reported**: when the file append fails, `_log`/`_warn` fall back to an **unredirected** stderr write (no `2>/dev/null` on that path) and to a best-effort **journal row**. The blanket `2>/dev/null` on `_log`/`_warn` is narrowed so that a *failure to write* is visible even though a *failure of the transport* is tolerated. | G2/O5. The house already journals observability events (`journal_history_append` is the sanctioned path and is fast — a splice). | Removing `2>/dev/null` entirely — rejected: a broken stdout must not abort the pipeline (the historic EPIPE class). |
| **D3-6** | **H1 is closed by redirecting the daemon's client stderr to a file** instead of a `PIPE` (or by draining it continuously). | The client's stderr is only *read* on the fast-fail path (`daemon/tools/upgrade_journal.py:2743`-`:2759`), so a long-lived client can fill the 64 KiB pipe and block. A file removes the drain obligation entirely. | A drain thread — rejected: more moving parts than a file redirect; the same outcome, less risk. |
| **D3-7** | **H2 is closed** by redirecting `_supervision_owned_pids`'s stderr (`2>/dev/null` on the helper) so the benign `head -1` EPIPE stops appearing as a "broken pipe" symptom. | The EPIPE is **self-inflicted and benign** (`evidence/CODE-PATHS.md` §5: `head -1` exits after one line ⇒ the next write gets EPIPE ⇒ the script continues). Suppressing the helper's stderr removes the red herring without hiding a real failure (the helper's *stdout* is unaffected). | Rewriting the helper to avoid `head -1` — rejected: larger diff, same outcome; the `head -1` idiom is load-bearing for "take the first pid". |
| **D3-8** | **Mid-phase visibility** is delivered by a **phase/step marker** written to the per-run file at every preflight step boundary — the same boundaries the D2 watchdog uses (so a budget trip and the step markers are one coherent narrative). | O4. The markers are cheap (one append each) and they turn the 37-minute blind window into a readable sequence. | Timestamping only — rejected: timestamps alone cannot tell you *which step* the run was in when it stalled; the marker can. |
| **D3-9** | The per-run log path is **journalled** (a `run_id → path` row) at the start of the run and referenced by the D2 budget-trip rows and by the daemon's `executor_still_running` row (`daemon/services/upgrade_journal_sweep.py:2281`-`:2291`). | Correlation by construction: the operator who reads the journal row can go straight to the file. This is what makes the D4(b) "correlate with data/upgrade.log" instruction actually actionable. | Leaving the correlation to the operator's filename arithmetic — rejected: that is the mtime-dating anti-pattern. | **[EXTENDED by D3-12/D3-14 — fold: A22, A24]** |
| **D3-10** | **Retention rule** (the plan's R5 gap): owner = **the shell at ceremony end, under the lock**, mirroring `retention_evict`'s seat (`promote.sh:722`). Rule: **count cap keep-newest 20 + age cap 14 d**, computed with **portable primitives only** (`find -name '*.log' -mtime +N -delete` or python `os.stat`) — **never** `stat -f '%m'` (MEASURED: on GNU it prints filesystem info, not mtime, rc=0 silent garbage — the exact input `lib.sh:5567` feeds it today **[fold: W4 — anchor corrected: the `stat -f '%m'` site is `lib.sh:5567`, re-verified at TIP]**) and **never** `_iso_to_epoch` + ISO sorting. **Five fences**: never delete the current run's file, the `in_flight.run_id` file, the last pointer's file, **any file modified < 6 h** (protects a *stalled* live run whose mtime is stale — the incident class), or anything while the lock is held by a live owner. The daemon-side sweep is an optional second line. **[fold: A20, R-D]** | A stalled run's file has a **stale mtime** while systemd holds it open ⇒ the narrative vanishes into an unlinked inode exactly when the post-mortem needs it. The `< 6 h` fence is the incident-class guard. | `stat -f '%m'` — rejected (MEASURED silent garbage on GNU; the existing `lib.sh:5567` call is a pre-existing bug this lane must not propagate **[fold: W4 — anchor corrected, re-verified at TIP]**). `_iso_to_epoch` + ISO sort — rejected (the house's BSD-only epoch helper is on the P2.1 GNU-debt list). Age-only retention — rejected (no count cap ⇒ unbounded files). |
| **D3-11** | **Atomicity contract**: one log line = one `write(2)` to an O_APPEND fd; lines **< 8192 B are atomic** against a concurrent writer, **≥ 8192 B corrupt** (the break is stdio `BUFSIZ`, not `PIPE_BUF`). Therefore: a **hard 4 KiB line cap** (2x margin) in the sink; longer payloads emit a **header + `payload elided, N bytes`**; **embedded newlines are sanitized** (`_logv "$LIVEZ_JSON"` / `"$READYZ_JSON"` at `promote.sh:448`/`:456`, `rollback.sh:245`/`:250`, `restart.sh:263`/`:273` are unbounded — today 1,258 B / 73 B, latent, and a degraded readyz grows). **Per-line fsync is REJECTED** (page-cache durability covers parent/process death — the stated objective; a host crash loses everything else too). The subshell rule is recorded: writes inside `$( )` land in the file (MEASURED), so stdout-mirror suppression is also the anti-pollution rule (no caller captures `_log`/`_warn` stdout today — verified). **[fold: A21, R-B]** | MEASURED: the ≥ 8192 B corruption is a real interleaving hazard; the 4 KiB cap gives a 2x margin. Per-line fsync would cost an fsync per line on a minutes-scale ceremony for durability the objective does not need. | No line cap — rejected (corruption under the concurrent writer). Per-line fsync — rejected (cost without benefit). Multi-line payloads raw — rejected (breaks the one-line-atomicity invariant and the 'exactly one copy' property). |
| **D3-12** | 🔴 **The sink is TWO files per run** (architect's call on the open question): `<install>/data/upgrade/<env>/<run_id>.log` = the shell's timestamped, strictly-ordered narrative (**direct writes**); `<run_id>.payload.log` = systemd's `StandardOutput/StandardError=append:` target for the payload's **raw** stdout/stderr. The pointer line in `data/upgrade.log` names **both** files, resolved **by `run_id` from the journal** (never "last pointer line"), and degrades gracefully when retention evicted the file. **AC1's 'exactly one copy' is scoped to successful writes**; **AC2 must assert journald visibility** on the write-failure fallback (systemd's `append:` open of the unwritable file fails ⇒ the payload stream goes to the journal), and the fallback line carries a distinct `logwrite_failed` marker (a partial write yields one truncated + one full copy). **[fold: A22, R-C]** | MEASURED: a child's stdout to a regular file is libc **block-buffered** ⇒ the `append:` capture is durable but **not real-time**, and its bytes can land *after* later markers — in a single file that is an **ordering illusion** that would mislead exactly the post-mortem D3 exists for. | One file for narrative + payload — rejected (ordering illusion). Two files with the payload stream into the narrative file — rejected (same illusion). |
| **D3-13** | **In-op progress markers**: the step-boundary markers (D3-8) stay, and an **in-loop marker every N = 500 files** is added inside `integrity_verify`'s walk and `stage.sh`'s manifest-checksum walk. **NO background heartbeat subshell.** **[fold: A23, R-C]** | Post-D1 the journal read is sub-second, but the checksum walks remain **minutes-scale** (measured: plugins ≈ 330 s/pass) and are exactly where a D2 budget trip needs attribution. A background heartbeat subshell is **rejected**: an extra writer with orphan risk that may write after the run ends. | A background heartbeat subshell — rejected (orphan risk; may write after the run ends). Markers only at phase boundaries — rejected (a minutes-long walk has no internal attribution). |
| **D3-14** | **Change-surface additions** (both missed by the plan): `daemon/services/upgrade_journal_sweep.py:2224`-`:2241` (`_log_tail` reads the **aggregate** — after D3-12 the aggregate is pointer-only ⇒ the `executor_exit` row loses the run's tail at exactly the wrong moment; it must read the per-run path **via `run_id`**), and `daemon/tools/upgrade_journal.py:2725`-`:2726` (the new `data/upgrade/<env>/` parent needs its own `mkdir`). **Reuse `_log_tsl`** (`lib.sh:349`-`:353` — BSD/GNU-portable, write-failure-signalling, already test-exercised) rather than a second writer, and fix the **inverted stream description** at `lib.sh:358`-`:360` in the same hunk. **[fold: A24, R-E, R-H]** | A second writer is a second bug surface; `_log_tsl` already exists, is portable and already failure-signalling. The sweep's aggregate read would lose the run's tail at exactly the wrong moment. | A new writer for the file sink — rejected (`_log_tsl` exists and is tested). Leaving the sweep on the aggregate — rejected (the `executor_exit` row loses the tail). |
| **D3-15** | **Env scoping**: per-run logs live under `data/upgrade/<env>/` — a **sandbox** ceremony resolves the **live install root** via the frozen-binary path derivation (`daemon/tools/upgrade_tools.py:687`-`:695`) and must not pollute the live tree's audit/retention domain. Redaction: the DB name + port in the per-run file are **status quo** (today's aggregate already carries them). **[fold: A22, A24, R-F]** | MEASURED deployment truth: a sandbox ceremony resolves the LIVE install root ⇒ an unscoped per-run log would write into the live tree's audit domain and its retention would delete live files (or vice versa). | A single unscoped `data/upgrade/` directory — rejected (cross-env mixing; the sandbox would pollute the live domain). |
| **D3-16** | **T3.10 additions**: (i) **no cross-env mixing** (a sandbox ceremony's files never appear in the live env's directory or retention set); (ii) **no secrets** in the pointer / provenance rows; (iii) the **≥ 8 KiB corruption pin** — plant a long line ⇒ the pack **REDs** (a corrupt line is detected, not absorbed). **[fold: A25]** | The atomicity contract (D3-11) is only as good as its pin: an 8 KiB+ line must be detected as corrupt, and the two cross-env/secrets properties must be asserted, not assumed. | Asserting the properties in prose only — rejected (unpinned properties decay). |

## 5. Acceptance Criteria

| ID | Criterion |
|----|-----------|
| **AC1** | With `ENSEMBLE_UPGRADE_LOG_FILE` set, each log line appears **exactly once** in the per-run **narrative** file; without it, the legacy stdout behaviour is byte-identical to BASE. **[fold: W4]** |
| **AC2** | A read-only / full log file produces a **visible** stderr line and a journal row; the pipeline continues; nothing is silently swallowed. |
| **AC3** | A preflight run produces **≥ 6** timestamped phase/step markers, each carrying the phase, the step and the elapsed seconds. |
| **AC4** | The unit argv's `StandardOutput=append:`/`StandardError=append:` targets the **per-run PAYLOAD file** (`<run_id>.payload.log`); the shell receives `ENSEMBLE_UPGRADE_LOG_FILE` = the per-run **narrative** file (`<env>/<run_id>.log`); the two streams land in **separate** files (D3-12). **[fold: W4 — the single-file-era wording is retired]** |
| **AC5** | `data/upgrade.log` gains exactly one pointer line per run; `_upgrade_log_tail` returns the per-run content when the pointer exists, and the aggregate content otherwise (**no regression** for existing readers). |
| **AC6** | The client no longer uses a `PIPE` for stderr; a long-lived client cannot block on an undrained pipe. |
| **AC7** | The benign EPIPE class no longer appears in any log produced by the pipeline. |
| **AC8** | Every run writes exactly one run-identity row naming the per-run **narrative** log path (and, per D3-12, the payload path); the `executor_still_running` row names the same narrative path. **[fold: W4]** |
| **AC9** | After SIGKILLing the parent mid-run, the per-run **narrative** file contains the full narrative up to the kill (including the last phase marker) — no truncation at a pipe boundary. **[fold: W4]** |
| **AC10** | A sandbox-produced per-run log contains **no** secret-shaped strings (grep-asserted). |
| **AC11** | Retention: ≤ 20 files kept, none older than 14 d, **all five fences** enforced (each with a negative leg); the `stat -f '%m'` idiom appears nowhere in the lane. |
| **AC12** | A 10 KiB payload yields a header + an elision marker + a ≤ 4 KiB physical line; a multi-line JSON payload yields **one** line; no per-line fsync is added. |
| **AC13** | The two-file sink holds: the narrative is strictly ordered and real-time, the payload stream is in its own file, the pointer resolves **by `run_id`** (not "last pointer"), and an unwritable narrative file surfaces in **journald** with a `logwrite_failed` marker. |
| **AC14** | A 2,000-file walk emits in-op markers every 500 files; **no** background writer process is spawned. |
| **AC15** | The sweep's `executor_exit` row carries the **run's** tail (resolved via `run_id`); the env-scoped parent is created before the first write; exactly one writer implementation (`_log_tsl`); `lib.sh:358`-`:360` no longer inverts the stream description. |
