## 1. Objective

After a hard machine/VM power-loss reboot — where the kernel SIGKILLs every process and the host loses power mid-flight — the ensemble daemon comes back into a state indistinguishable from a clean startup except that it transparently continues every `RUNNING` instance from its last LangGraph checkpoint, with `PAUSED` instances still parked, terminal instances still terminal, and the bus/queue/checkpoint secrets already wired. The PG-wait burden rides the existing `_boot_db_preflight` + launcher exit-75 lane (no new retry helper, no new env-knob); `Wants=postgresql.service` is deliberately dropped (RAM-cost hazard on remote-PG hosts); and the task-less RUNNING-instance class is named D13 with a MANDATORY tracked follow-up commission (both 2026-10-19 RCAs — leader turn `897011bb` and rcc mission `6b1630e7` — are this class; a third occurrence is plausible before the follow-up lands).

**Testable completion sentence:** a power-loss-struck host that restarts brings the daemon back within ~14s (systemd `RestartSec=10` + boot), runs through the existing `_boot_db_preflight` exit-75 lane (budget-exempt, infinite) until PG accepts connections (now bounded by `connect_timeout=BOOT_DB_TIMEOUT_S=10` — `daemon/repositories/factory.py:232-284` previously had only `pool_pre_ping`, so a firewall-DROP was hanging 75–130s per attempt; one-line addition), rehydrates the existing AutoContinue + DependencyBus + StaleTaskRecovery passes without code change, and clears any stuck `message_queue` `processing` rows via the new `recover_stuck_messages_on_startup` service — proven by the Phase-4 demo E2E.

Empirically re-measured 2026-10-21 with SQLAlchemy's `make_url` against the exact preflight URL shape (which appends NO query string): a password containing `?` is **UNAFFECTED** here — host / database / password all parse intact, and the bound arrives via the preflight's own `connect_args={"connect_timeout": 10}` (`daemon/__main__.py:237-240`), because there is no appended query string for the `?` to eat; a password containing `@` mangles the **HOST** (e.g. `db.internal` → `ss@db.internal`, password truncated) while the **DATABASE name is NEVER corrupted** — the host is unresolvable → `OperationalError` → **exit 75 fail-closed** (the daemon does not boot; the launcher retries with capped backoff). The rendered URL is **byte-identical to the pre-change string form in the normal case** (no URL-special characters), so the fix changes the escaping of a pathological password, not the probe's target; the libpq bound still rides the preflight's own `connect_args` (NOT the URL query — the mechanism difference from the factory is deliberate and unchanged). Pins: `tests/unit/test_connect_timeout.py` pack (h1) byte-identity, (h2) the intended target under a special-char password — **MUTATION-VERIFIED RED** against the old f-string, (h3) no `connect_timeout` on the preflight URL query.

That wording is **over-broad** and is **NOT** the fact pattern: `?` does NOT affect the preflight, and the preflight's DATABASE name is never corrupted — only the HOST can be. The commit message is **deliberately left unamended** (no history rewrite, no rebase, no amend); the corrected fact pattern is the one recorded in the bullet above, which supersedes it. The **residual itself is closed** by the B3.1 fix recorded in the bullet above (the preflight probe URL is now built with `URL.create`): what remains true is the historical fact pattern (the `?` never affected the preflight; the DATABASE name was never corrupted — only the HOST could be), not an open follow-up.
