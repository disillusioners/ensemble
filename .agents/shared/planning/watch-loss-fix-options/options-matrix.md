## 3. Option A's hidden depth — stated honestly

The user's instinct is **sound** — "store the watch, recover it on retry" is the right shape — but it is not a one-line change. Four real depths, all verified:

1. **Where the hook lives (the critical one).** The re-arm must execute **inside the F6 transaction** (`turn_transitions.py:691-700`), not beside the cancel in `worker_pool`. Reason: the re-key is transactional SQL; worker-pool-side actions travel on a fire-and-forget bridge with **no ordering guarantee** — a worker-pool re-arm races both the re-key commit and the child's later settle-notify CAS. Post-commit re-arm variants must UPSERT against a possibly-already-claimed row — splitting the exactly-once invariant across two writers. The in-txn hook makes cancel→persist→re-arm **atomic by construction** (daemon death = all-or-nothing).
2. **Survival semantics on the re-armed row.** A plain transport-only re-arm gets re-eaten at the retry's own settle (that IS the defect). The re-armed row must carry `mission_terminal` in its event set — verified admissible within current C1 bucket rules (`work_notifier.py:773-803`): mid-mission it is delivered-but-kept; at true mission terminal it is claimed exactly once. **Policy nuance for you:** this arms an event class on the watcher's *behalf*, per-watch. The M2 **default** stays opt-in — but it is the system opting a re-armed row into `mission_terminal`, not the watcher. Far smaller than C's reversal; still worth your explicit nod.
3. **Storage seam.** Cleanest: a small **quarantine table** (`stored_watch` capturing original work_id, retry work_id, watcher instance, event set, mission linkage; 1 SQL migration file per repo convention + one repo method). Alternative: two columns on `job_watchers` (`origin_work_id`, `rearm_status`) — same migration cost, but splits row lifecycle across three writers (CAS-claim, S15 compensation UPSERT `work_notifier.py:1090-1114`, re-arm) — more contention. Piggybacking S15's UPSERT alone fails structurally (fires post-claim, wrong moment; loses origin linkage).
4. **The retry-never-arrives leg.** If the deferred retry never lands (quota window expires, child purged), the stored watch needs a carrier: a small GC leg (or extension of the existing sweep) that ages orphaned stored watches past the mission-live orphan window (6h, `mission_live_guard.py:110`) and fires or rehydrates them. Structurally simple, but it is new code with its own invariants.

Residual edge cases (all enumerated, none critical once the in-txn hook + survival events are in): duplicate deferrals on one parent (first-store-wins fence), late child arrival after re-arm (fence marker on `retry_work_id`), mission-instance vs work-instance linkage (store both). Estimated **~150–200 LOC** for A; **+~100–150** for E.
