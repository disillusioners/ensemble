## Q2. JobItem↔Task LINKAGE

- **Key**: `Task.work_id == JobItem.job_id` (dispatch contract; comment at `job_recovery_service.py:2428-2435`). `Task.work_id` is UUID4 **unique=True** on the Task model — at most ONE Task row per work_id (`daemon/repositories/task/repository.py:671-696`, `get_by_work_id` returns `.first()` on the unique index).
- **Multiple backing Tasks accrue via RETRY CHILDREN**: `schedule_retry` marks the parent CANCELLED (retry_scheduled=True) and inserts a NEW PENDING child with **incremented retry_count and a FRESH work_id**, single transaction, guarded UPDATE (rowcount==1 race gate) (`task/repository.py:5095-5169`; fresh-work_id + instance_id-inheritance lineage documented at `job_recovery_service.py:2554-2571` — the retry child inherits the parent's `instance_id`, so retry lineage is keyed by `instance_id`, NOT work_id). `rearm_watchers=True` exists ONLY for the usage-limit deferral lane (`:5158-5164`).
- **JobItem on retry vs supersede**: RETRY decision → `active→queued` via the retry engine (`job_state_machine.py:57`, `job_queue_service.py:3047-3049`). In the usage-limit supersede shape (deferral cancels the task; retry Task under a NEW work_id), the ORIGINAL JobItem's own work_id Task is terminal while the live retry child is invisible to work_id linkage — exactly why pattern-(f) carries the W1 retry-child conjunct (`job_recovery_service.py:2588-2631`, `_pattern_f_instance_has_inflight_task`).
- **"ALL backing Tasks terminal" in query terms**:
  - `task` table: the row `WHERE task.work_id = job_queue_items.job_id` has `status IN ('completed','failed','cancelled')` (terminal set `task/repository.py:2108-2112`; NON_TERMINAL = pending/running/paused + legacy `processing`, `mission_live_guard.py:498-504`), AND
  - no retry-child escape hatch: `NOT EXISTS (SELECT 1 FROM task t2 WHERE t2.instance_id = job_queue_items.instance_id AND t2.status IN ('pending','running','paused','processing'))` (the instance-scoped inflight probe, `_pattern_f_instance_has_inflight_task` `job_recovery_service.py:4779`).
  - Caveat: terminal-instance terminate cascades HARD-DELETE tasks (`instance_lifecycle._terminate_instance_db_sync`), so "no Task rows at all" is a third terminal-ish shape (f1 territory / `orphaned_no_task` arm).
