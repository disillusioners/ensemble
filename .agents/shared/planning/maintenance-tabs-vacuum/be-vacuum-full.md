# Phase 2: BE VACUUM FULL — schema, service, method, guard (Part 2 backend)

> **Cluster 2 of 6** — the BE additive change: extend the execute request schema with `vacuum_full: bool | None = None`, thread the flag through `MaintenanceApiService.execute` to `CheckpointCleanupJob.run_checkpoint_prunes(..., vacuum_full=...)`, add the new private method `_run_vacuum_full_after_cleanup(*, vacuum_full: bool)`, add the new constants, and update the constants.py policy comment to reflect the new split. The structural guard (Cluster 4) is the load-bearing piece.

## Objective

Add a one-flag-deep escalation path: when the manual destructive path (`POST /api/maintenance/checkpoint-cleanup/execute`) receives `vacuum_full: true`, AFTER the destructive prune completes successfully, run `VACUUM FULL checkpoints, checkpoint_writes, checkpoint_blobs` on a dedicated autocommit NullPool engine with longer timeouts. The scheduled path (`CheckpointCleanupJob.execute()` called from `MaintenanceService._run_pending_jobs`) is STRUCTURALLY INCAPABLE of escalating — it does not accept a `vacuum_full` parameter and the new method's only definition site is the manual-only `CheckpointCleanupJob` (enforced by AST pin in Cluster 4).

### N7(a) — Dry-run request type does NOT exist (no body sent)

The "dry-run ignores `vacuum_full`" contract is STRUCTURALLY ENFORCED by the absence of a request body, not by a runtime check. The `MaintenanceApiService.dry_run` method (per `daemon/services/maintenance_api_service.py:239`) does not even read the payload — it just runs the destructive-preview. The `test_dry_run_ignores_vacuum_full` test in `test-plan.md §2.5` is now redundant (the FE simply never sends the flag); the test is retained as documentation of the contract but its core assertion is "the dry-run never reads `vacuum_full` from the request".

### N7(d) — `reltablespace=0` → `pg_default` mapping (Plan Review 2026-10-12 N5')

```sql

  pg_tablespace_location(c.reltablespace),

  pg_relation_size(c.oid) AS table_bytes
FROM pg_class c
```
