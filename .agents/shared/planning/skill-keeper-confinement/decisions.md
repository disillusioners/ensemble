**Why OFF:**

3. Default OFF **is** the durable post-promote off-switch — an operator opting in (config field or env) is a deliberate, visible act. Default ON would mean "the ungated status quo's successor" ships enabled, and the incident's own quiet-period history (10-20 20:32, 10-21 10:15/10:43 pre-burst FIX runs) shows the lane fires unattended.

## D2 — FIX abuse controls: idempotency_key + per-(project,skill) cooldown (commission item 2)

- **`idempotency_key = "skill_fix:<normalized_project>:<skill_id>"`** on every FIX admission (HANDOVER §8 rec 2 "set idempotency_key" — implemented). Non-terminal duplicate collapses onto the live job at the DB layer (`JobQueueService.enqueue` → `create_or_get_by_idempotency_key`). Closes the concurrent re-file class.
- **In-process FIX cooldown**, keyed `(normalized_project_id, skill_id)` → monotonic timestamp of last ACCEPTED admission; default 1800s (`SkillEvolutionConfig.fix_cooldown_seconds`, 0 disables). Refusal → `None` + warning log. Stamp on BOTH outcomes (fresh row or dedup-hit). RAM-only by design — a rate limiter, not durable state; the idempotency key covers the non-terminal window across restarts. Kills the L4 amplifier (2026-10-21: same skill re-FIXed 3× in 38 min — 1800s ≥ the whole observed burst).
- Cooldown/idempotency are **FIX-only**: DERIVED/CAPTURED admissions via `enqueue_evolution` are gated by the kill-switch but not cooldown-keyed (the amplifier class is FIX re-filing; DERIVED creates a distinct variant row). Disclosed scope cut.

## D3 — Allowlist confinement: read-only surface chosen (commission item 1)

**ACCURACY CORRECTION (review iteration 2, M-5 ruling):** the earlier
version of this section claimed repo-source was unreachable and read
reach was bounded. Both overclaims are corrected below. **Execution is
closed; READ reach is open.**

**New `tools.allow`:** `["read_file", "list_directory", "glob_files", "grep_files", "self", "help", "knowledge", "dynamic-skill", "skill-evolution", "shared_meta_kv"]`
**New `tools.deny`:** `["bash", "proc", "service", "write_file", "edit_file", "inner_soul"]`
**meta version:** 0.1.0 → 0.2.0.

- Granular-tool spelling is the supported mechanism (critic precedent: `agents/critic/meta.json` mixes literal tool names + categories; `resolve_tool_filter` (`daemon/tools/instance.py:392`) expands category entries and adds unknown entries as literal tool names). The four granted names are the complete read half of the `filesystem` category (`list_directory`, `read_file`, `glob_files`, `grep_files` at `filesystem.py:584/657/748/1040`); `write_file`/`edit_file` are its only mutating tools — both denied.
- **M-1 ruling (IMPLEMENTED): `inner_soul` is denied.** `daemon/tools/inner_soul.py:449` (`_atomic_write_memory`) writes `agents/skill-keeper/memories/**` — on live installs that path is `releases/<ver>/agents/**`, i.e. the standing 3x-recurring agent-self-mod incident class. With `inner_soul` denied, the keeper holds NO tool that writes any file. **Memory READ is preserved**: `access_memory` is a DIFFERENT tool in the same `self` category, and the deny is name-scoped (deny wins, exact names) — verified end-to-end by `test_memory_read_preserved_after_inner_soul_denial` against the PRODUCTION registry map (`inner_soul` absent, `access_memory` present in the resolved set).
- **DEVIATION from the commission's literal text (disclosed):** also stripped **`service`** (and denied it). `service_start(name, command: argv)` (`service_tools.py:198`) executes arbitrary argv — a bash-equivalent escape hatch (`git add/commit`, `python3 -c`, `bash -c` all work argv-shaped). A confinement that leaves an argv-execution primitive is not confinement; soul.md never granted a service duty (the tool section at :142 never mentioned it). Also denied **`proc`** (background-process spawn — same argv-execution class) for the same reason.
- **Deny list rationale:** `resolve_tool_filter` applies deny AFTER allow (deny wins), so the deny entries are structural: a future allow-list regression re-adding `"service"` would still not restore `service_start`, and re-adding `"self"` would still not restore `inner_soul`. `filesystem` is NOT in deny (that would strip the four read tools too — category-level deny) — instead the two write tools are denied by literal name.
- **HANDOVER §8 rec 3 (widen `_check_prompt_artifact_write` to ALL files under `agents/<name>/`) — DEFERRED, not implemented.** The widening itself is small (extend `_depth2_match` past the `VERSIONED_PROMPT_ARTIFACTS` check), but it changes a fleet-wide shared guard for every agent holding `filesystem`, with refusal-message and drift-baseline (`agents/.prompt-artifacts.sha256`) implications, and it guards NOTHING for skill-keeper now that (a) write tools are absent from the allowlist, (b) bash is gone and (c) `inner_soul` is denied — defense-in-depth for a surface the agent no longer holds is pure scope. The incident's actual bypass (`skill-set.yaml` via bash) is dead at the allowlist layer. Routed as a standalone follow-up (its own review lane: all 40+ agents' write_file flows re-audited).

**READ REACH IS OPEN (M-5 correction — the overclaim, now stated accurately):**
`daemon/tools/filesystem.py:207-208` (`_resolve_within_workdir`) applies the workdir boundary to RELATIVE paths only — "For absolute paths the boundary check is intentionally skipped". So `read_file("/abs/path")` reads any file the daemon process can read: `~/.ssh/*`, the install-dir `.env`, `/proc/self/environ`, another agent's directory, anything. The four read tools are READ-ONLY, but they are NOT project-scoped. The accurate statement of the containment is **execution closed, read open**:
- CLOSED: no file write of any kind (no `write_file`/`edit_file`/`inner_soul`), no shell, no process spawn, no service start.

The charter (`soul.md`) was corrected to say so explicitly (the read-reach note + the "no tool I hold can WRITE any file" line), and the pin `test_charter_states_read_reach_is_not_workdir_fenced` keeps the prose honest.
