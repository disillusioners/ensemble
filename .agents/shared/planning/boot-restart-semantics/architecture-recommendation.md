### 0.2 "swept (orphaned pre-flip txn cleared)" is a **display label**, not a journal fact

- The label is a static per-event string: `_OUTCOME_LABELS["sweep"] = "swept (orphaned pre-flip txn cleared)"` (`daemon/tools/upgrade_tools.py:1493`).
- It is applied to the **newest terminal-class row** found by a reverse scan of `history`: `_terminal_outcome` (`upgrade_tools.py:1480-1485`) over `_TERMINAL_OUTCOME_EVENTS = uj._TERMINAL_EVENTS + ("restart",)` (`upgrade_tools.py:1456`).
- `"sweep"` is in `_TERMINAL_EVENTS` (`daemon/tools/upgrade_journal.py:2556-2565`; the literal `"sweep"` at `:2561`) — and **FIVE unrelated writers emit that event name** *(revision 2 / BLK-6 and round-2 F3 — the previous count of three was wrong; both extra sites were opened this revision)*:
  1. the launcher's boot sweep of a stale **pre-flip** txn (`launcher.sh:4147`),
  2. the promote preflight adopting a stale pre-flip txn (`lib.sh:11328`),
  3. the **daemon's** `reconcile_pending_op` closing a `pending_op` because a terminal event exists (`upgrade_journal.py:2776`),
  4. the daemon's **`reclaim_stale_txn`** disposing an orphaned txn — "reason=heartbeat-stale+owner-dead" (`upgrade_journal.py:654`; the function at `:500`; reachable from `upgrade_tools.py:2273`),
  5. the daemon's **`reconcile_pending_op` EXPIRY closure** — "genuine orphan: executor produced zero journal evidence — neither refusal nor executor_exit" (`upgrade_journal.py:2811`).
- **Writers 3, 4 and 5 are all benign rows written AFTER a committed promote**; each is later than the `commit` row, so the reverse scan (`upgrade_tools.py:1480-1486`) returns *it*, and the static label (`upgrade_tools.py:1493`) renders the whole promote as "swept (orphaned pre-flip txn cleared)". **Writer 5 is the worst case**: it fires on the *expiry* path, i.e. only after the txn is long gone — the label then survives for the entire retention window of the journal.
- **⇒ A committed promote can be labelled as an orphan sweep.** The raw journal is truthful; the derived label is not. The commission's requirement "a release's journal must never label a committed promote as orphaned" is therefore a **display-derivation** defect, not a journal-write defect.

### 0.3 The stop overrun is ONE janitorial step, ordered before every durability step (premise refined)

- `manager.shutdown()` (`daemon/manager.py:17591`) runs three kill phases **before** the `steps` list that carries every durability-relevant step:
  - proc-tool `cleanup_all` (`manager.py:17666-17680`),
  - bash `cleanup_all` (`manager.py:17687-17699`),
  - the **durable spawn-registry sweep** `sweep_open_rows_for_shutdown` (`manager.py:17710-17728` → `bash_spawn_reaper.py:1466-1507`), which is wrapped in `asyncio.wait_for(..., timeout=LANE_SWEEP_DEADLINE_SECONDS)` with `LANE_SWEEP_DEADLINE_SECONDS = 60.0` (`bash_spawn_reaper.py:140`, `:1396-1407`).
- Only **after** those three does the ordered list run: `stop_sources` → `cancel_active_requests` → `wait_inflight` → `shutdown_worker_pool` → event bus → maintenance service → maintenance API → room locks → snapshot drain → `dispose_db_pools` → `close_checkpointer` → MCP pool drain → MCP service close (`manager.py:17730-17758`), then `cleanup()` → engine dispose (`manager.py:17766-17771`) and the `"Graceful shutdown complete"` line (`manager.py:17773`).
- The durable sweep is **explicitly janitorial and non-fatal by its own contract**: on deadline it logs "remaining rows left OPEN (non-fatal; the next sweep/lane retries them)" and returns 0 (`bash_spawn_reaper.py:1400-1407`). It therefore consumes the whole budget while producing **no durable value at stop** — the same rows are re-scanned at the next boot reconcile.
- **Gate asymmetry (revision 2 / N-f — opened this revision).** The **shutdown** sweep is gated by **ONE** switch — the master kill-switch (`bash_spawn_reaper.py:1485`, `kill_switch_from_env()`) — and returns 0 with **zero repository access** when it is OFF. The **boot** reconcile (`reconcile_stale_bash_spawns`, `bash_spawn_reaper.py:1517`) is gated by **TWO** — the master switch (`:1538`) **and** the boot-sweep leg knob (`:1544`, `boot_sweep_leg_from_env()`). **⇒ The stop path and the boot path are not symmetric: a host with the leg knob OFF performs the janitorial sweep at stop and skips the reconcile at boot.** This matters for §2 (EC-7.2 defers the durable-row work to the boot reconcile — that deferral is only sound if the boot reconcile actually runs).
- Per-row cost inside the sweep: rows are processed serially, each through `asyncio.to_thread(verify_and_kill, …)` (`bash_spawn_reaper.py:1279-1285`), and the TERM→KILL ladder burns the **full 5.0 s grace** for any group that stays signalable (`DEFAULT_TERM_GRACE_SECONDS = 5.0`, `bash_spawn_reaper.py:128`; `_grace_wait_for_death` bails early **only** on `ESRCH`, `bash_spawn_reaper.py:713-741`; `_kill_ladder` `:744-797`).
- **⇒ Root cause of the 70 s overrun: an explicitly non-fatal janitorial sweep, capped at 60 s, scheduled ahead of the durability sequence.** The measured live log lines quoted by investigator A (02:57:36 "Starting graceful shutdown..." → 02:58:40 "sweep exceeded its 60s aggregate deadline" → launcher SIGKILL ≈02:58:46) are **UNVERIFIED by me** (live log not opened), but the *mechanism* above is code-proven.

## 1. THE PRESERVATION CONTRACT

### 1.1 The invariant, stated once

> **PC-1 (Preservation).** A row is *doomed* at boot **only** if the boot-wipe predicate — evaluated as ONE shared SQL boolean over the `task` alias — says it is not preserved. The predicate is **the same boolean on both sides**: the task side deletes `NOT predicate`; the message side deletes a message whose task does **not** satisfy `predicate`.
>
> **PC-1a (Quantifier asymmetry — stated, not hidden).** The two sides do **not** share a quantifier. The **task side is row-level** ("this task row satisfies the predicate"); the **message side is ∃-quantified over that message's task rows** ("there EXISTS a task row of this message that satisfies the predicate" — the `NOT IN (SELECT message_id FROM task WHERE <predicate>)` shape). Because `task.message_id` is indexed but **NOT unique** (`daemon/repositories/task/models.py:207`), one message may own **several** task rows. **⇒ Two consequences, both intentional and both stated here:** (i) a **message can survive while one of its tasks is deleted** (the message is kept because *another* task of the same message is preserved) — this is allowed; (ii) the converse — **a surviving task whose message was deleted** — is the *dangerous* direction (it is the incident shape) and is prohibited by **PC-1c**. PC-1c is therefore one-directional on purpose: *no surviving non-terminal task may point at a vanished `message_queue` row.*
>
> **PC-2 (Safe default).** If the predicate **cannot be evaluated** (probe error, SQL error, dead connection, unresolvable schema), the purge **does not run**: zero rows are deleted on that side, the failure is raised as a typed error, and the boot continues.
>
> **PC-3 (Fail loud).** A PC-2 event is not a log line. It must produce: an **ERROR** log, a **metric**, a **readyz degraded field**, and an **anomaly record** — and the anomaly must be visible to the operator without reading logs.
>
> **PC-4 (One carrier).** The predicate has exactly **one** implementation — the in-flight lane's `boot_wipe_preserve_predicate_sql(engine, *, arm3_active)` (`daemon/repositories/message_queue/repository.py:117-153` on `origin/fix/boot-purge-predicate-failclosed`). No second copy may exist in either repository.
>
> **PC-1b (One evaluation outcome per boot — revision 2 / BLK-7).** One predicate *definition* is not one predicate *evaluation*. The lane has **four evaluation sites — three LIVE and one DEAD** (§0.18: the message-side `clear_all` has no production caller), each with its own probe and its own guard (§1.5(a) enumerates them). **PC-1b requires that the predicate be evaluated ONCE per boot and that the OUTCOME be published boot-scoped and sticky**: every later site (task wipe, delete-time re-check, `clear_all`) consults the published outcome instead of re-evaluating. An unevaluable first evaluation disables **all** sides for that boot (zero rows deleted **on either side**) and fires PC-2/PC-3 exactly once; a successful first evaluation means a later site **cannot** degrade to a different (legacy) predicate shape. ⇒ The evaluations can no longer disagree about *evaluability*. **This closes the EVALUABILITY entry to the half-purge — it is the only way the *evaluability* half-purge can begin. It is NOT the only entry: a second, row-state TOCTOU entry exists (§0.15 / §1.5(a), revision 3 / reviewer M-1) and is closed for the `pending` population only by the lane's orphan belt, not by PC-1b.**
>
> **PC-1c (Cross-side delete invariant — revision 2 / BLK-7, defence in depth).** Independently of PC-1b, the delete-time re-check **refuses** to delete a message whose task row still exists and satisfies the preserve predicate. Stated as a **post-condition with its own test**: after the boot purge, *no surviving non-terminal task points at a vanished `message_queue` row* — i.e. `SELECT count(*) FROM task t WHERE t.status IN (<non-terminal>) AND t.message_id IS NOT NULL AND NOT EXISTS (SELECT 1 FROM message_queue m WHERE m.message_id = t.message_id)` = 0.
>
> **Revision 3 (reviewer M-1) — the wording is narrowed, and the refusal test changes.** The post-condition above is the *cross-side delete invariant*; it is **not** a closure of the half-purge class. Two corrections: **(i)** the delete-time re-check is evaluated against **live** task state at delete time, and the shared predicate contains **existence arms that can CLOSE** between the capture and the delete (the JobItem arm and the receipt/event arm — §0.16/§0.17 and §1.5(a)) ⇒ the "still … satisfies the preserve predicate" test is **non-monotone** and can be false at the re-check although it was true at the capture; **(ii)** therefore PC-1c's refusal must be keyed on the **task-wipe's published outcome** — a **monotone floor**: *any non-terminal task row that survived the wipe* ⇒ refuse — rather than on a re-evaluated existence predicate (or, alternatively, the delete re-check must consume the *same single snapshot* with the row-state carve-out removed). **⇒ The guarantee is "closed against evaluability divergence", NOT "closed".**

The lane already delivers PC-4 and most of PC-2. **PC-1's semantics (what "preserved" means) is the Emperor's call** — see EC-1/EC-2. **PC-3 is not yet delivered anywhere** — the lane logs ERROR only.

> **Status of PC-2 / PC-3 (revision 1, M-2).** PC-2 and PC-3 state the **recommended contract**, pending the Emperor's ruling on **EC-3**. They are *not* an invariant the way PC-1, PC-1a, PC-1b, PC-1c and PC-4 are: EC-3.1 (abort boot) would make the boot **not** continue, which **conflicts with PC-2 as written** — choosing it requires amending PC-2; and EC-3.4 (delete with a degraded predicate) is flatly incompatible with PC-2. PC-1, PC-1a, PC-1b, PC-1c and PC-4 are structural and are unaffected by EC-3.
>
> **The second, previously unlisted conflict (revision 2 / N-h): EC-4 is the same kind of ruling as EC-3, and the two interact.** EC-4.2 makes *a genuinely absent backing table* count as "unevaluable ⇒ skip the purge" — which is PC-2's semantics applied to a **different** trigger. Under EC-4.2, a legacy host skips the purge entirely (the backlog is never cleared); under EC-4.1 the missing arm is dropped and the legacy predicate is in force; under EC-4.3 the predicate narrows to the provably-safe target. **PC-2 as written does not say which of these applies, so EC-3 and EC-4 must be ruled together** — a PC-2 ruling of "skip" (EC-3.3) only produces a safe system if EC-4.2 is also chosen; EC-3.3 + EC-4.1 leaves the incident shape permanently in force on a legacy host. This document presents them as two rulings of one question and does not pre-empt either.

### 1.5 The four cases the commission names — the design

#### (a) A message whose task is PENDING on a checkpoint-less instance (the `0d54db6d` shape)

**Current behaviour (code-proven — but see the execution caveat, revision 1 / m-6):**

> **Two different failure mechanisms, two different log lines.** (i) **The probe throws** on PostgreSQL because raw driver SQL sends `:tname` literally under psycopg's `pyformat` paramstyle — this is the mechanism the lane fixes (`message_queue/repository.py:50-55` on the branch) and it is **UNVERIFIED BY EXECUTION** (read-only fence; the lane pins it with `test_probe_uses_psycopg_bound_params_not_literal_colon`). Its log line is the **WARNING at `message_queue/repository.py:64-70`** ("receipt-arm table probe failed … degrades to the legacy running/paused predicate"). (ii) **The probe succeeds but a table is genuinely absent** — that is a different branch, with a different log line, the **WARNING at `:72-75` / `:76-79`**. They are not interchangeable, and the design treats them differently (EC-3 vs EC-4). The §8 **item 5** discriminator tells them apart: grep the live `ensemble.log` for "receipt-arm table probe failed" (i) versus "table absent" (ii).
- The task side is preserved only if one of the arms holds; the receipt arm (`task.status='pending' AND EXISTS(event … message_received)`) is evaluated **unconditionally and inline** on the task side (`task/repository.py:5897-5906`), so a receipt-backed PENDING task survives the task wipe.
- The message side evaluates the same two arms **only through the table-presence probe** (`message_queue/repository.py:81-102`), and on PostgreSQL the probe throws (`:57-63`, raw driver SQL with `:tname`) ⇒ the arms are dropped and the legacy predicate (running/paused only) is in force ⇒ **the PENDING task's message is doomed while the task survives**.
- The result is the divergence the commission describes: a surviving PENDING task whose message row is deleted. The claim path then raises `ValueError("Message … not found in message_queue …")` (`daemon/services/task_processor.py:418-422`) before the `try` block, and the worker pool's `except Exception` (`daemon/services/worker_pool.py:646`) routes to `_handle_task_failure` (`:653`, `:1084`) → `fail_task` (`:1088`) — the task becomes permanently FAILED.

**Design:**
- **PC-1/PC-4 fixes the divergence of the PREDICTION, not the divergence of the EVALUATION.** *(Revision 2 / BLK-7 — the previous draft said "fixes the divergence mechanically"; that was an overclaim, and the approver is right.)* The lane has **one predicate definition** but **four evaluation sites, of which THREE are live and ONE is dead** (§0.18 — `MessageQueueRepository.clear_all` has no production caller), each with its own probe and its own guard. All four sites were opened this revision on the branch tip `f78907d10`:

  | # | Evaluation site | Call chain (branch `f78907d10`) | Its own guard |
  |---|---|---|---|
  | 1 | message-side **capture** | `daemon/manager.py:1682` → `message_queue/repository.py:1489` (`boot_wipe_preserve_predicate_sql`) | none of its own — a failure aborts the capture |
  | 2 | **task-side wipe** | `daemon/manager.py:1818` → `task/repository.py:5787` (the shared builder; `doomed_sql = f"NOT {preserve_sql}"` at `:5790`, the DELETE at `:5814`) | `_boot_task_wipe_fail_closed` (`daemon/manager.py:657`) — ERROR, **0 task rows deleted**, boot survives |
  | 3 | **delete-time re-check** | `daemon/api.py`'s deferred DELETE → `message_queue/repository.py:1627` | the deferred-DELETE except arm |
  | 4 | `clear_all` | `message_queue/repository.py:1761` (lane; definition `:1576` at `origin/latest`) | none of its own — **and it has NO production caller** (`git grep '\.clear_all(' origin/latest -- daemon/` ⇒ only `task_repo.clear_all` at `manager.py:1751`; on the lane the same single hit is `manager.py:682`) ⇒ **3 live + 1 dead** (revision 3 / §0.18) |

  PC-2 as written is **per-side** ("zero rows are deleted *on that side*"), and PC-2's per-side wording is exactly what permits the half-purge.
- **⇒ The half-purge is reachable, and it is the incident shape re-derived.** Capture evaluates OK ⇒ the doomed ids are stashed ⇒ the **task-wipe** evaluation fails ⇒ `_boot_task_wipe_fail_closed` deletes **0** task rows ⇒ the **delete-time** evaluation succeeds ⇒ the doomed **messages** are deleted. **Under the lane the consequence is the BELT, not the `ValueError` (revision 3 / approver item 1).** The DELETE and the orphan belt are **one transaction** (`message_queue/repository.py:1652` DELETE, `:1679-1690` belt `UPDATE … error='orphaned_by_boot_purge: …'`, `:1700` the single `session.commit()`), so every surviving PENDING task is **failed in the same transaction** ⇒ **PC-1c holds** and the `ValueError` path is never reached. **Without the belt** — the pre-lane shape, or a host where the belt is disarmed (§0.15) — the chain continues: the surviving PENDING task points at vanished messages ⇒ `task_processor.py:418-422` raises `ValueError("Message … not found in message_queue …")` ⇒ `worker_pool.py:646` → `:653` → `:1084` → `:1088` `fail_task` → the watcher is notified (`:1094-1095`). **⇒ The one-sided failure destroys committed work through the BELT, not through the `ValueError`.** The lane's own PC-2 guard is what *enables* the partial success in the first place: it converts a failure into a **partial** success rather than a global one.
- **The design closes it with two mechanisms, and names which is load-bearing:**
  - **PC-1b (primary — one evaluation outcome per boot).** The predicate is evaluated **once per boot**; its **outcome is published boot-scoped and sticky**; every later site consults the published outcome instead of re-evaluating. An unevaluable first evaluation ⇒ **all** sides disabled for that boot (zero rows deleted anywhere) + one PC-2/PC-3 event. A successful first evaluation ⇒ a later site **cannot** degrade to a different predicate shape (a later *row-state* re-check is still allowed — that is not a predicate evaluation). ⇒ The evaluations can no longer disagree about evaluability, which is the only entry point to the half-purge.
  - **PC-1c (defence in depth — the cross-side delete invariant).** The delete-time re-check **refuses** to delete a message whose task row still exists and satisfies the preserve predicate; and the boot asserts the post-condition *"no surviving non-terminal task points at a vanished `message_queue` row"* (PC-1c, §1.1). PC-1c also covers the ∃-asymmetry (PC-1a) in the dangerous direction. **Revision 3: the refusal test is keyed on the task-wipe's published outcome (a monotone floor), not on a re-evaluated existence predicate — see §1.1 PC-1c and §1.5(a) below.**
  - **The SECOND entry — the row-state TOCTOU window (revision 3 / reviewer M-1).** PC-1b closes *evaluability* divergence. A **second** entry exists and is **not** an evaluability divergence: the delete-time re-check is a **live SQL subquery evaluated at delete time** (`message_queue/repository.py:1627-1633`, spliced into the DELETE at `:1647-1650`, once per chunk at `:1638`), and the shared predicate contains **existence arms that can CLOSE** between the capture and the delete — the JobItem arm (`:99-104`: it closes when the JobItem terminalizes or `deleted_at` is set) and the receipt/event arm (`:107-111`: it closes when the `event` row goes or the task leaves `pending`). The three evaluations are **three separate transactions** (capture `manager.py:1681-1686`; task wipe `manager.py:1818-1820`; deferred DELETE `api.py:299-306`) and **nothing serialises them**. **⇒ The reachable ordering is: T0 capture (the task has no live anchor ⇒ the message is doomed) → T1 the task acquires an anchor ⇒ it survives the task wipe ⇒ T2 the anchor closes ⇒ the re-check's preserve clause no longer excludes the message ⇒ the message is deleted while the task survives non-terminal.** Under the lane the **belt** then fails that task in the same transaction (§0.15) ⇒ PC-1c holds; **without** the belt the task survives pointing at a vanished message ⇒ `task_processor.py:418-422`. **⇒ The design's earlier phrase — "the only way the half-purge can begin" — is OVERSTATED and is withdrawn: there are TWO entries, and PC-1b closes only the evaluability one.** **Boot ordering note:** the ordering of the orphan-JobItem sweep relative to the deferred DELETE is **UNVERIFIED** (the sweep is a separate lane; the deferred DELETE fires at `api.py:299-306`) — the design therefore treats the belt, not the ordering, as the guarantee.
  - **The test (named, required — revision 3 / approver item 1: the previous form was VACUOUS).** A **fault-injection test** that fails the predicate evaluation **at each of sites 1–3 in turn**. **The assertions are now exact, not a disjunction:** **(a) ZERO message rows deleted** on every injected failure; **(b) the BELT's rowcount is 0** (no task was failed by `orphaned_by_boot_purge`); **(c) zero task rows deleted** on the task side; **(d) the PRESERVED set survived** — the exact preserved-message set is still present, not merely the absence of orphans; **(e) PC-1c as an ADDITIONAL assertion only** — no surviving **non-terminal** task (over the daemon's canonical set `{pending, running, paused, processing}`, `daemon/constants.py:1162-1167`) points at a vanished `message_queue` row; **(f)** the belt's reason string is asserted **exactly** (`orphaned_by_boot_purge`), not by substring; **(g)** the belt did **not** fire for a preserved task; **(h)** the belt's documented residual is pinned (it does **not** call `reconcile_turn_mirror` / `_notify_pending_task`, §0.15). **Why the old form was vacuous:** the disjunction *"either zero rows deleted **or** PC-1c holds"* goes GREEN on the very half-purge the design exists to prevent — under the lane the belt converts every pending orphan into a **dead** task, so PC-1c holds **and** the committed work is destroyed; the disjunction cannot distinguish "nothing destroyed" from "destroyed and killed". **⇒ The disjunction is replaced by the exact assertions above.** Plus a **PostgreSQL-backed full-cycle test** (capture → task wipe → deferred delete) asserting the same, because the unit harness's dialect coverage was not verified by me (§1.4 item 6 / B-3).
- With the lane's L1 fix the probe evaluates on PostgreSQL, so the receipt arm is live on both sides and the PENDING task's message survives with it — **but that is a statement about the predicate's shape, not about the evaluations' agreement** (the reason the previous draft's claim was an overclaim).
- **Additionally — CONDITIONAL ON THE EC-1 BRANCH (revision 3 / minor set: this sentence previously stated a rule the body did not own)**: the boot wipe consults **checkpoint presence** as a *never-doom* signal for a task whose instance is alive **only under a branch that preserves PENDING work** (EC-1.1 re-dispatch, or EC-1.2 park-for-operator). **Under EC-1.3 (drop loudly) or EC-1.4 (keep the receipt rule) the checkpoint signal is NOT consulted** — the task's fate follows that branch's rule, and the "no checkpoint" case is one doomed case among others. A PENDING task on an instance with **no checkpoint** is precisely the "never dispatched" case — there is no turn to lose, but there is also **no evidence the message was ever consumed**. Under PC-2/PC-3 the predicate is still evaluable, so this is a **semantic** decision → **EC-1**.
- **Recommended default (recommendation only):** treat a PENDING task on a **non-terminal instance** as preserved (option EC-1.1) — the message stays, the task stays, and the worker re-dispatches it at-least-once. Rationale: the receipt rule (option EC-1.4) is the rule that produced the incident when the predicate degraded; a rule whose safety depends on a probe is not a preservation contract. The consequence is that pre-checkpoint side effects may repeat — which is exactly the at-least-once trade the Emperor must accept.

#### (b) The capture→DELETE window

**The window (code-proven):** capture in the constructor (`manager.py:1634`) → workers start (`api.py:1214`) → DELETE armed (`api.py:1285-1296`) → fires at +1 s (readyz-green) or +5 s (`api.py:273-291`). During the window a worker can claim a task whose message is in the doomed set.

**Design — three candidate layers. One of them is a ruling, not engineering.**

> **Framing note (revision 1, C-1; tightened at revision 2 / NEW-1).** Layer 1 is a **behaviour change at boot** — it changes what a worker may claim and when. It is therefore **framed as EC-5** (§1.9 / §7) and is **not settled here**. Layer 2 (re-derive at delete time) is engineering and is specified. **Layer 3 (the generation counter) is SPECIFIED here but BUILT only under EC-5.1 or EC-5.2** — it is not an unconditional engineering item, because EC-5.3 ("neither") prices it at zero work.

1. **Eliminate the race — a claim barrier (this is EC-5).** The worker pool would refuse to claim a **PENDING** task while the boot purge is armed and unfired. The barrier is *bounded* (the purge fires at ≤5 s; the barrier releases on fire, on timeout, or on purge-skip). Rationale: a barrier makes the window *empty* rather than *narrow*, and an empty window needs no compensating logic. **Whether to build it is the Emperor's call (EC-5).**
2. **Re-derive at delete time (retained).** The delete-time re-check already re-evaluates the shared predicate per chunk (`message_queue/repository.py:1522-1543` → lane L5). It must additionally re-evaluate **against live task state** *inside* the DELETE transaction — which it does, because the DELETE and the re-check are the same statement. **What the re-check must additionally re-evaluate:** (i) the predicate arms (shared builder), (ii) the **purge generation counter** — see (3).
3. **Generation counter.** The capture stamps a `purge_generation` (a monotonically increasing boot-scoped integer) with the doomed set. Any task **claimed** after the capture bumps its own generation stamp; the delete-time re-check preserves a row whose task generation ≥ the capture generation. This makes the re-check *provably* equivalent to "the row was claimed after we decided it was doomed" — closing the residual that the current re-check leaves (it only rescues rows that became running/paused, and only by accident of status).

> **Implementation note.** Layer 2 (re-derive at delete time) is engineering and is **retained unconditionally**. Layer 3 (generation counter) is **specified but conditional**: it is **defence-in-depth** under EC-5.1 (the barrier) and the *only* thing standing between the window and the race under EC-5.2; under EC-5.3 it is not built. **This document does not choose between EC-5.1 / EC-5.2 / EC-5.3** — it frames them and prices them in §1.9. **PC-1b/PC-1c (§1.1) are independent of this choice**: they close the *evaluability* half-purge and are not conditioned on EC-5.

#### (c) Messages whose tasks are gone or terminal at boot

- **Task terminal (completed/failed/cancelled):** the message is doomed by design — this is the "backlog clear" pruner role, stated in the code (`task/repository.py:5890-5896`) and in the wipe's own docstring (`task/repository.py:5680-5700`).
- **Task gone (no task row at all):** the message is a **task-less orphan**. It can be (i) the residue of a previous boot's purge (it is already the *victim* of a prior purge — deleting it changes nothing), or (ii) a message enqueued outside the task-creation path. It has **no forensic value** in the queue and, per the commission, is a candidate for **quarantine** rather than silent deletion — the semantic choice is **EC-2**.
- **Ordering note (code-proven):** the message capture (`manager.py:1634`) runs **before** the task wipe (`manager.py:1751`), so at capture time terminal tasks still exist and are correctly doomed; but the *message* rows of tasks that the task wipe will delete are also doomed — consistent, no double-count.

### 1.6 The `'processing'` legacy status and the `NULL message_id` trap — two mandatory predicate repairs

1. **`processing` must be preserved.** The predicate's arm 1 currently reads `status IN ('running','paused')` on both sides (`task/repository.py:5869-5872`; `message_queue/repository.py:1411`, `:1524`). The daemon's canonical non-terminal set includes `processing` (`daemon/constants.py:1162-1167`). **Design:** arm 1 must be `task.status IN ('running','paused','processing')` — or, better, `task.status NOT IN (terminal task statuses)` so the vocabulary has one owner. *(This is a correctness repair, not an Emperor choice: the daemon already declares `processing` non-terminal.)* **Pin hazard:** this breaks `test_f4`'s arm-1 literal (branch `:586`) — see §1.4 item 5; land the literal update (or the `NOT IN` re-expression) in the same commit. **Revision 3 (§0.15) — the widening must ALSO widen the orphan belt's status filter:** the belt is `WHERE status = 'pending'` (`message_queue/repository.py:1684`), so a `processing` task that survives on an existence arm and whose anchor closes before the delete would end non-terminal pointing at a vanished message. **The two filters must be widened in the same commit, or the repair opens a new hole where the arm-1 widening closed one.**
   **Consequence question for the Emperor (m-14):** the population of legacy `processing` task rows is **unmeasured** — §8 item 7 asks for `count(*) FROM task WHERE status='processing'`. If that count is zero on this host, this repair is a no-op and can be sequenced freely; if it is non-zero, the repair changes what survives the next boot for every one of those rows.
2. **`NOT IN` must become NULL-safe — on the MESSAGE side, and the consequence is a half-purge, not a no-op.** The message-side predicate must be rewritten from `message_id NOT IN (SELECT message_id FROM task WHERE …)` (`message_queue/repository.py:1406-1416`) to a `NOT EXISTS` shape over `task.message_id = message_queue.message_id` (or `IS NOT DISTINCT FROM` where the NULL-task must be matched). Without this, a single preserved task with `message_id IS NULL` empties the **message** doomed set — **while the task-side wipe still deletes** (it has no `NOT IN` subquery: `task/repository.py:5867-5874`). **⇒ The outcome is not "the purge silently no-ops"; it is that the boot leaves *task-less messages* behind** (§0.11). The lane records the trap and does not fix it.

### 1.7 The never-dispatched RUNNING husk (the `375b80f3` shape)

- The husk is a **RUNNING instance with no durable work**: no task row, no message row, no active JobItem, no watcher, no non-terminal descendant. The classifier scores it by recency (`task/repository.py:1810-1830`): age < 1 h ⇒ **class 2**; 1 h ≤ age < 24 h ⇒ **class 3**; age ≥ 24 h ⇒ class 1a/1b (proven dead).
- Classes 2 and 3 are **surface-only, never mutated** (`task/repository.py:106-109`).
- The boot-continue pass selects **RUNNING task rows** only (`find_auto_continue_candidates`, `task/repository.py:1324-1418`) — a husk has no task row, so the pass never sees it. The orphan sweep (`auto_continue_boot_pass.py:1119-1145`) handles the *inverse* case (checkpoint present, no task row) by minting a synthetic `work_id` and driving a resume.
- **The husk is invisible to both the resume machinery and the purge** — it is neither preserved nor doomed; it is simply stranded, and it stays class 2 → 3 → (24 h) 1a.
- **Design:** the husk needs a **recorded outcome**, not a resurrection. §4's ledger records `stranded_class` as an outcome dimension: **1a/1b ⇒ `lost`; 2/3 ⇒ `unknown`**. A class-2/3 husk must **never** be recorded as lost. Whether the Emperor wants the husk *reaped* at some age is a semantic choice in its own right — it is **EC-18** (§1.9 / §7). *(Revision 1, N-1: the previous draft mis-filed it under EC-9, which is the launcher burst-guard choice — a different subject entirely.)*

#### **EC-1 — What happens to a PENDING task's message at boot (the `0d54db6d` shape)?**

*Question:* A task is PENDING (never dispatched) and its message row is a purge candidate. May the boot delete it?

| Option | Semantics | Consequences | Work shape |
|---|---|---|---|
| **EC-1.1 Re-dispatch (at-least-once)** | A PENDING task on a non-terminal instance keeps its message; the worker re-dispatches it after boot | Work is not lost; **pre-checkpoint side effects may repeat** (a turn that had already emitted output before dying may emit it again); the boot backlog grows to whatever was pending | One new predicate arm + **whichever EC-5 option is ruled** (the claim barrier under EC-5.1/EC-5.4; the generation counter under EC-5.2; neither under EC-5.3 — and under EC-5.3 the arm alone leaves the residual race open). §1.5b. ~1 release. |
| **EC-1.2 Park for operator** | The message and task are kept, the task is made **unclaimable**, and it is surfaced for a human | No loss, no duplicates; **the queue stalls** until a human acts; needs a new parked state + a surface + a release path | New task state or a separate parked table + surface + operator tooling. ~1–2 releases. |
| **EC-1.3 Drop loudly** *(what the in-flight lane's orphan belt does)* | The message is deleted; the task is failed with `orphaned_by_boot_purge` | Deterministic, visible, cheap — **work is lost** and the sender must re-send; the loss is recorded, so it is *auditable* loss. **BUT the belt is a raw `UPDATE`, not a transition: the lane's own comment says it "deliberately does NOT route through `TaskRepository.fail_task`, so it skips `reconcile_turn_mirror(work_id)` and `_notify_pending_task()`" (branch `message_queue/repository.py:1661-1669`). ⇒ a failed-by-belt task does not notify its parent ⇒ the parent can be left in `WAITING_CHILDREN` on a child that will never report ⇒ a **parent wedge** (mitigation: the `WAITING_CHILDREN` hang watchdog, `daemon/config.py:2608-2629` — its compensation is UNVERIFIED by me)** | Already implemented in the lane (L8), **but the belt must be routed through `fail_task` (or carry a labelled waiver for the wedge)** — otherwise the option buys "lost work" with "wedged parent" (revision 2 / round-2 F5-NEW-4). ~0.25 release on top of the lane. |
| **EC-1.4 Keep the receipt rule** *(status-quo intent)* | Only a JobItem-anchored or receipt-backed PENDING task is preserved; receipt-less paths are pruned by design | One rule for both sides; **but the rule's safety depends on a probe that failed on PostgreSQL** — the exact failure that produced the incident. #### **EC-2 — What happens to messages whose task is gone or terminal?**

*Question:* The task row is terminal (completed/failed/cancelled) or absent. Delete, quarantine, or re-create the task?

| Option | Semantics | Consequences | Work shape |
|---|---|---|---|
| **EC-2.1 Delete (current)** | All such messages are deleted | Cheapest; **no forensic value retained**; a task-less message may itself be the victim of a prior purge, so its deletion is invisible | 0 work |
| **EC-2.2 Archive then GC** | Rows are archived (to a durable table/file) and GC'd on a schedule | **Reconstructable** ("what did we drop?"); costs a table/archive + a GC job + a retention policy | New storage home + GC job + policy. ~1 release |
| **EC-2.3 Re-create the task** | The task is re-minted so the message can be delivered again | Delivers again — but **re-delivers old messages** unless deduplicated; risk of double-processing old work | Dedupe key + task minting path. ~1–2 releases |
| **EC-2.4 Delete terminal-only, quarantine task-less** *(narrowest unambiguous target)* | Messages of **terminal** tasks are deleted; messages with **no task row** are quarantined (kept, flagged, surfaced) | Exactly the pruner role is preserved; the ambiguous population becomes visible instead of vanishing; quarantine needs a retention/GC rule eventually | Quarantine marker + surface + GC rule. ~1 release |

**Team's recommended default (recommendation, NOT a decision): EC-2.4.** It is the narrowest target that is unambiguous, keeps the backlog-clear pruner role intact, and stops the "task-less message" population from being silently destroyed — which is the population that makes the 1096/161 counts unexplainable.

#### **EC-3 — What does an unevaluable predicate do at boot?**

*Question:* The predicate cannot be evaluated (probe error, SQL error, dead connection).

| Option | Semantics | Consequences | Work shape |
|---|---|---|---|
| **EC-3.1 Abort boot** | The daemon refuses to start | Maximum safety; **the daemon is down** — a DB blip becomes an outage | ~0 extra work (raise past the call site) |

#### **EC-5 — May the boot block worker claims of PENDING tasks while the purge is armed and unfired?**

*Question:* The purge's DELETE is armed **after** the workers start (`daemon/api.py:1214` vs `:1285-1296`) and fires at +1 s (readyz-green) or +5 s (wall clock). In that window a worker can claim a PENDING task whose message is in the doomed set. May the boot block those claims until the purge has fired, been skipped, or timed out?

| Option | Semantics | Consequences | Work shape |
|---|---|---|---|
| **EC-5.1 Claim barrier** | The worker pool refuses to claim a **PENDING** task from arming until the purge fires / is skipped / times out. Bounded by the purge's own 5 s floor; releases on **all three** exits. | The window becomes **empty**, not narrow — no compensating logic, no residual race. Cost: a bounded claim latency at boot (≤ 5 s), and the barrier must be **provably released** — a leaked flag parks every PENDING task forever, so the release needs a watchdog of its own | A `boot_purge_armed` flag + a claim-gate check + three release paths + a release watchdog + a test per exit. ~1 release |
| **EC-5.2 Generation counter only** | No barrier. The capture stamps a generation; a task claimed after the capture is stamped; the delete-time re-check preserves a row whose task generation ≥ the capture generation. | No claim latency. **The residual race survives** for anything the generation does not cover (a claim that has not yet stamped; a claim in the same tick). Defence-in-depth, not a fix | A generation column + two stamps + the re-check arm. ~0.5 release |
| **EC-5.3 Neither** | Accept the race; rely on the delete-time re-check and the orphan belt. | Zero work. **The race is the incident** — a surviving PENDING task whose message was deleted | 0 |
| **EC-5.4 Bounded barrier variant** | As EC-5.1, but the barrier also releases on the first claim attempt that has waited > N ms, and the wait is logged | Bounded by construction; the log makes the residual race **measurable** instead of invisible | As EC-5.1 + a wait budget + a log line |

**Team's recommended default (recommendation, NOT a decision): EC-5.1**, with **EC-5.2 as defence-in-depth** (it is cheap and it makes the re-check *provably* correct rather than *accidentally* correct). The barrier is a behaviour change at boot and is therefore a **ruling**, not engineering — this document prices it but does not choose it.

*Question:* A husk is a RUNNING instance with **no durable work** — no task row, no message row, no JobItem, no watcher, no non-terminal descendant. | Option | Semantics | Consequences | Work shape |

### 2.2 The recommended contract — **pending EC-6 / EC-11** *(revision 2 / round-2 F2)*

> **SP-1 (One declared budget).** There is exactly **one** number that says "how long the daemon may take to stop". Call it `B`. It is declared in the daemon's config (`DAEMON_SHUTDOWN_BUDGET_SECONDS`), it is what the daemon's own shutdown sequence is *designed to fit inside*, and every other bound is **derived** from it:
>
> - the daemon's internal deadline = `B`;
> - **the derivation, named (revision 2 / F12(b) — the previous text said "B-derived" without saying how).** `B` is the **whole daemon-side stop**, so it must be *divided*, not shared:
>
>   | Slice | Symbol | Value |
>   |---|---|---|
>   | uvicorn's request drain | `D` | `DAEMON_GRACEFUL_SHUTDOWN_TIMEOUT_SECONDS` |
>   | the lifespan's pre-manager steps (P1) | `P1` | the service-stop band (tool-usage flusher 10 s + joins + db-offload) |
>   | the manager's MUST set (P3/P4) | `M` | the sum of the reserved per-step budgets |
>   | the manager's MAY set (janitorial) | `J` | the deferred sweep — **0 in the stop** under EC-7.2, the janitorial slice under EC-7.1 |
>   | **the total** | `B` | `D + P1 + M (+ J)` |
>
>   With `J = 0` (the EC-7.2 branch): `D + P1 + M ≤ B`. With `J > 0` (EC-7.1): `B` must additionally absorb `J`, i.e. **`B` grows** — see the EC-7 branch in §2.6.
>   > **REVISION 3 — the inequality is UNSATISFIABLE as currently proposed (approver item 5).** `D` alone (`DAEMON_GRACEFUL_SHUTDOWN_TIMEOUT_SECONDS`, default **60**, `daemon/config.py:595-596`) **exceeds** the recommended `B = 55` (EC-11.1/11.2) **before a single MUST step is counted** — so the recommended default and the recommended derivation cannot both stand. The **bounded** MUST steps alone sum to **≥ 90 s** (the two worker-pool stops are **sequential**: `pool_orchestrator.py:733` iterates `pools_snapshot`, `:742` `pool.stop(timeout=30.0)` ⇒ **60 s** inside the `to_thread` at `manager.py:17734`; plus `wait_inflight` 10 s and the snapshot drain 10 s), and P1 adds the flusher's 10 s — see §0.14. **⇒ Either `D` must be re-derived from `B` and shrunk, or `B` must be raised to `D + P1 + M` and the launcher's bound moves with it. EC-11's number is a PROPOSAL with an arithmetic hole in it; the Emperor must be shown the hole before ruling.**
>   The launcher derives `CHILD_STOP_WAIT_S = B + margin` and the unit derives `TimeoutStopSec = B + margin + slack`; **no number is hand-typed twice**.
> - **`B` covers the whole daemon-side stop — uvicorn's request drain + the lifespan's P1 + the manager's MUST set.** The launcher's clock starts at **signal receipt** (`launcher.sh:4371-4397`), while the daemon's own shutdown code can be entered **60 s into** that clock: uvicorn owns SIGTERM (`daemon/__main__.py:856-858`) and its `timeout_graceful_shutdown` (`:973`; default 60, `config.py:595-614`) bounds a drain that runs **before** the lifespan shutdown. Therefore **`DAEMON_GRACEFUL_SHUTDOWN_TIMEOUT_SECONDS` must be `B`-derived**, not an independent number. *(Revision 1, M-8.)*
> - the launcher's `CHILD_STOP_WAIT_S` = `B + margin` (margin ≥ 10 s to cover the launcher's own SIGTERM→child-forward and reap);
> - **the transport:** the launcher reads `DAEMON_SHUTDOWN_BUDGET_SECONDS` from `INSTALL_DIR/.env` — it already loads that file (`launcher.sh:4599`), and `stop-ensemble.sh:383` is the precedent for reading a daemon knob from exactly that file. Then it derives its bound. No hand-typed 70 anywhere. *(Revision 1, m-4.)*
> - the unit's `TimeoutStopSec` = `B + margin + slack` (the systemd-side bound must be **strictly larger** than the launcher's, or systemd kills the launcher before the launcher kills the daemon);
> - `stop-ensemble.sh`'s **real bounds** are `STOP_SCRIPT_BUDGET_S = 120` (the `systemctl stop` call, `:794`) and the unit's `TimeoutStopSec` (90, `scripts/systemd/ensemble-daemon.service:115`); its `WAIT_S` is only the **post-stop verification poll** (`:810-818`). `WAIT_S` should still be `B + margin`, but it is not the kill bound. *(Revision 1, m-9.)*
> - `LAUNCHD_DRAIN_BUDGET_S` = `B + margin`.
>
> **SP-2 (Must-complete set — split by re-derivability).** *(Revision 1, M-7: the earlier draft had one MUST class; "skip a MUST step" would have destroyed non-re-derivable output.)* The sequence is partitioned into **three** classes:
>
> | Class | Steps | If it exceeds its budget | Re-derivable if skipped? |
> |---|---|---|---|

>   - **If EC-8.2 (clean = 0, partial = a dedicated exit code):** a **second** distinct code is needed for the partial stop, and it must not collide with the crash space `classify_exit` already owns. **EC-8.2's "a distinct exit code classified by `classify_exit`" is NOT deliverable via the daemon's process exit alone** on the current code: the daemon's exit status is already consumed by the signal-death convention (143 = SIGTERM), and the launcher is the only component that sees the raw code. **⇒ EC-8.2 is deliverable only with a launcher-side mapping** (`launcher.sh:4395` → `:4453`) — which is why `launcher.sh` is in B-5's file set and `daemon/__main__.py` is the alternative site.
>
>   - **If EC-8.3 (partial = 0, always journaled):** the exit code carries no completeness information and the skip-record is the only signal; **and the clean stop still needs its 143 handled** (translated or accepted as clean) for the burst budget to stay honest.
>
>   **Common to all three branches (engineering, not a ruling):** a **requested stop is not a crash** — the burst budget, `classify_exit` and the unit's `SuccessExitStatus` must all agree on that, whichever branch is ruled. **The previous revision's text ("a clean stop exits 0 … a stop that had to skip MUST steps exits non-zero with a distinct code") was EC-8.2 verbatim and is withdrawn.**

### 2.4 The orphaned cgroup processes — what is in the cgroup, who should kill it

**The unit's shape (verified):** `Type=simple` (`ensemble-daemon.service:104`) ⇒ `MainPID` **is the launcher** (`ExecStart=__LAUNCHER__`, `:107`); `KillMode=mixed` (`:112`); `TimeoutStopSec=90` (`:115`); `SuccessExitStatus=143` (`:111`); `RestartPreventExitStatus=78` (`:110`); `Restart=on-failure` (`:108`); `RestartSec=10` (`:109`). The template's own rationale states the `KillMode=mixed` reason: TERM to the main process (launcher) only; SIGKILL to the remaining cgroup members after the timeout — explicitly **not** control-group, because "a cgroup-wide TERM would trip uvicorn's force_exit (crash-equivalent teardown — the r-f82e shape)" (`ensemble-daemon.service:51-57`).

**Who is in the cgroup** (the daemon's own children, all of which inherit the cgroup but *not* the process group):

| Population | Created where | Escapes the daemon's `killpg`? | Reaped by the daemon today? |
|---|---|---|---|
| proc-tool children | `proc_tools.py:1671` — `start_new_session=True` ⇒ **new session AND new process group**, same cgroup | **Yes** (group kill misses them) | Partly — `cleanup_all` kills each tracked group (`proc_tools.py:2253-2301`); the code documents "Truly-detached orphans … setsid … will not be reaped by this sweep" (`:2263-2267`) |
| bash-tool children | `bash.py:1396` — `start_new_session=True`; the durable row is the reach (`bash_spawn_reaper.py`) | Group-killable via the durable registry | RAM tier + durable tier (`bash.py:602-708`) |
| `service_start` services | `daemon/tools/service_spawner.py:203` — `start_new_session=True` | **Yes** — a detached session survives the group kill and the cgroup is the only backstop | **No** — no stop-all path found (**UNVERIFIED: I did not exhaustively search for a stop-all**) |
| MCP stdio children (npx/node servers) | MCP service | Yes | Only via `close_all_connections` (`connection_manager.py:401-420`) — unbounded, and the *child process* teardown is not obviously in that path |
| code-server | `vscode_server_manager.py:405-469` | `VSCODE_STOP_GRACE_S = 5` then SIGKILL | Yes — `api.py:5397-5404` |
| D-state tasks, zombies whose parent died | OS | Not signalable | Nothing can kill them — only the cgroup sweep or the reaper can collect them |

**The design:**

1. **`setsid` is a process-group escape, not a cgroup escape.** `start_new_session=True` gives a new session + process group, but the child stays in the **same cgroup** — so systemd's `KillMode=mixed` SIGKILL sweep *does* reach it, but only **after** the timeout. This is the mechanism behind both the "3x Unit process … remains running after unit stopped" notices and the "Failed to kill control group … Invalid argument" message (**the origin of the EINVAL is NOT determinable from this repo — UNVERIFIED**; it is a systemd-internal message and the cgroup-kill call path is outside the repo).
2. **The daemon should own what it spawned; systemd should own the residue.** Today the daemon owns the RAM tier (groups) and partially the durable bash rows, and does **not** own `service_start` services. The design adds a **stop-all for `service_start` services** to the MUST set (it is cheap: the service registry knows its pids) and makes the durable bash rows a **boot** responsibility — **that half is CONDITIONAL ON THE EC-7 RULING** *(revision 2 / BLK-2: the previous draft answered EC-7 here, in the body, while EC-7 was still open)*: **under EC-7.2** the durable rows are a boot responsibility (SP-2's MAY set) and the cgroup sweep becomes the backstop for escapees rather than the primary mechanism; **under EC-7.1** the stop must close the durable rows itself ⇒ they move into the MUST set ⇒ **`B` grows**; **under EC-7.3** they are left to the cgroup sweep. The `service_start` stop-all is engineering under every branch.
3. **The exit-code shape.** Today: launcher SIGKILLs the child at 70 s ⇒ `wait` returns 137 ⇒ the launcher exits 137 (`:4394-4395`, `:4453`). `137 ∉ SuccessExitStatus=143` ⇒ systemd records `Result=exit-code` for the stop job. The stop was **explicitly requested**, so `Restart=on-failure` correctly does not fire, and `stop-ensemble.sh` treats a failed unit as not-running (`_unit_stopped`, `stop-ensemble.sh:745-763`) and exits 0, so the promote proceeds. **That is the correct *systemd* behaviour and the wrong *semantics*: a stop that was killed mid-durability is recorded as a failure.**
4. **A clean stop must record itself — PENDING EC-8 (revision 3 / approver item 8 + reviewer M-3).** With SP-2/SP-3 in place the daemon reaches the end of its MUST set **before** the launcher's bound; the daemon then exits **143** (the code-proven clean-stop status — §0.12) and the launcher propagates it verbatim (`launcher.sh:4448-4449`, `:4453`). **The shape is a three-branch conditional:** **under EC-8.1** the 143 must be translated to 0 (daemon-side by overriding `capture_signals`, or launcher-side at `:4395`/`:4453`) and a partial stop exits non-zero like a crash; **under EC-8.2** a partial stop carries a **dedicated** code, deliverable **only via a launcher-side mapping** (§0.12 / SP-4), and `classify_exit` (`launcher.sh:4243-4250`) must be taught both 143 and the new code; **under EC-8.3** the exit code carries no completeness information and the skip-record is the only signal. **In every branch** `SuccessExitStatus` (`scripts/systemd/ensemble-daemon.service:111`, today `143`) must cover whatever the daemon is understood to exit with, so that systemd records a *requested* stop as a success and a *partial* stop is visibly distinct from a crash. **The previous revision's text here stated EC-8.2 and pre-empted the ruling; it is withdrawn.**

### 2.5 What the launcher's counters SHOULD mean

**What is wrong today (verified):** `crash_count` is a **lifetime residue** of the last burst that was counted, with a `window_start` epoch that is only meaningful relative to *now*. The file is written **only on child-exit paths that are not shutdown requests** (`launcher.sh:4461`, `:4518`, `:4535`, `:4558`; the shutdown branch exits at `:4453`), so:
- a healthy daemon that has been up for days leaves the file frozen at whatever the last crash left;
- a graceful stop leaves it frozen;
- the operator sees `crash_count=5` with `BUDGET_MAX_CRASHES=5` and reads "one short of halt" — **even though the window is 3 days stale and `budget_tick` would reset it** (`launcher.sh:4320-4327`);
- the display layer has no window age (`upgrade_tools.py:1119-1121` renders `last_exit crash_count window_start last_backoff last_uptime` with no age and no interpretation).

**The burst guard itself is sound and must not be weakened:** `BUDGET_MAX_CRASHES=5`, `BUDGET_WINDOW_S=600`, `BUDGET_UPTIME_RESET_S=600` (`launcher.sh:57-59`), enforced by `budget_tick` (`:4312-4334`) and the halt at `:4529-4540`. The design changes **what the file means**, not the guard.

**Recommended semantics (design, not a semantic Emperor choice — see EC-9 for the operator-visible variant):**

> **Revision 2 / BLK-4 — the reset-on-stop writer behaviour is ENGINEERING, not a ruling.** The previous draft kept "reset the burst window on a requested stop" as a framed Emperor choice (EC-9.2) while simultaneously asserting it in the body as engineering. **That is resolved in favour of engineering**: the invariant *"a requested stop is not a crash"* is not a matter of taste — it is the same invariant the **exit-code contract** carries (SP-4, whose three branches all carry it: a requested stop is not a crash) — **and revision 3 sharpened it: the code fact is that the clean stop is 143 and `classify_exit` (`launcher.sh:4243-4250`) classifies 143 as a crash today (§0.12), so the reset-on-stop writer change and the `classify_exit` change are the same defect seen from two sides.** **⇒ EC-9.2 is retired as a choice** (the identifier is kept only so cross-references do not dangle); the reset-on-stop writer behaviour is **specified here as engineering** and lands in **(b)** because it changes the launcher's shutdown path. The **remaining** EC-9 question is only about how the *state* is interpreted — see §2.6.

- **The file becomes a *burst-window* record, not a *lifetime* record.** Every write stamps `window_start` **and** `window_end`/age, and `crash_count` is explicitly scoped to that window. A reader can compute "N crashes in the last M seconds" without reading the epoch.
- **A healthy start stamps the file.** The launcher writes a **start/health stamp** when it launches a child (`started_at`, `boot_id`), so "the daemon is up" is recorded without waiting for the child to exit. This is the honest fix for "a healthy daemon never rewrites the file, by construction": the *counter* should still only advance on crashes, but the *file* should record liveness.
- **The residue problem is a display problem.** `upgrade_tools._launcher_state` (`upgrade_tools.py:1105-1121`) should render the window age and classify the state: `fresh burst` / `stale (window expired)` / `healthy (running since …)`. The operator must never see a bare `crash_count=5` with no age.
- **A stop resets the burst window explicitly — engineering, not a choice** *(revision 2 / BLK-4; this bullet was previously framed as EC-9.2 and is now decided here as engineering, so the body no longer pre-empts an open ruling)*. A requested stop is not a crash; the launcher's shutdown branch writes `last_exit=0` (or a dedicated `stopped` verdict) with `crash_count=0` and a fresh `window_start`, so the next boot starts from a clean burst window. This is a **behaviour change on the shutdown path** and therefore lands in the next release, not the staged one (§6.2, B-6).

### 3.4 The launcher-side 96 KiB disarm — made explicit

- The launcher mirrors the size guard: `SWEEP_JOURNAL_SIZE_GUARD_BYTES=98304` (`launcher.sh:145-146`), applied on both the flipped branch (`:3567-3585`) and the pre-flip branch (`:4141-4145`).
- Above the guard the launcher **declines to act** on a stale promote txn: "no launcher rollback and no commit-and-continue … a stale flip transaction in a ≥98304B journal is left to the daemon-side closer; the txn is left OPEN" (`launcher.sh:4142`).
- **⇒ The launcher's automatic sweep is silently disarmed on a growing journal.** This is a *safety* disarming (the daemon-side closer is the in-process path) but it is **invisible**: nothing reports "the launcher sweep is disarmed".
- **Design (JT-5):**
  1. the status surface reports the journal size, the guard value, and **armed / disarmed** explicitly;
  2. the disarm is **alerted** (an anomaly / a status field) the first time a boot observes it, so it cannot be discovered by accident;
  3. a **retention + archive** policy bounds the journal so the guard is not reached by default (see EC-12);
  4. the daemon-side closer's capability to dispose a stale flipped txn is then a **single point of failure** — the design should state that explicitly and give the closer a budget.

### 3.5 EMPEROR CHOICES — §3

#### **EC-12 — Journal retention and compaction**

*Question:* The journal grows without bound (Investigator A measured `releases/state.json` ≈ 142 KB / 529 rows, ≈ +118 KB in 7 days — **UNVERIFIED, live journal not opened**). What is the retention policy?

| Option | Semantics | Consequences |
|---|---|---|
| **EC-12.1 Operator-manual trimming (today)** | No code; an operator edits the journal | Nothing breaks; the launcher sweep stays disarmed; **the journal keeps growing until a human acts**; the size guard becomes a permanent condition rather than an exception |
| **EC-12.2 Bounded retention with an archive, ceremony-time** *(recommended)* | At promote time, under the pipeline lock, the journal is compacted: keep the last N terminal runs + **all** `halt`/`rollback`/`sweep_rollback`/`refusal` rows; archive the rest to `state.json.arc.<date>` with a sha256 recorded in the journal | Bounded size ⇒ the launcher sweep stays armed; the archived tail is still recoverable; **the compaction is a write during a ceremony** and must be crash-safe and idempotent (the archive write must precede the truncation). **NOT exclusive against the daemon writer (revision 1 / M-11):** `upgrade_journal.journal_history_append` (`daemon/tools/upgrade_journal.py:751-766`) does a read-modify-write with atomic replace (`journal_write` `:691-716`) and takes **no** `rollback.lock.d` claim — it is the writer of the `pending_op` reconcile row. A racing compaction can **drop that row or be undone** (restoring pre-compaction history and re-arming the size-guard disarm). **Exclusion rule required:** the daemon writer claims the pipeline lock, **or** compaction is compare-and-swap (re-read + verify a hash/mtime immediately before the atomic replace, abort on change) |
| **EC-12.3 Daemon-side GC** | The daemon compacts the journal periodically | No ceremony-time write; but the daemon and the promote pipeline then both write the same file ⇒ a concurrency hazard the mkdir-lock was designed to avoid; the daemon-side closer already writes it (`upgrade_journal.py:2774`) |
| **EC-12.4 Archive without truncation** | Copy to an archive, keep everything live | Zero risk to the live path; **does not bound the size** ⇒ does not re-arm the launcher sweep |

**Team's recommended default (recommendation, NOT a decision): EC-12.2**, with EC-12.4 as the cheap first step (archive-only, no truncation — it cannot break the live path). The Emperor should be told that **EC-12.4 alone does not fix the disarm**; only truncation (EC-12.2) does.

## 4. THE RESUME ACCOUNTING

### 4.1 The question, and why it is currently undecidable

The commission asks: after the fact, **did this turn survive the restart?** Today it cannot be answered, because:

- The deferred set is **RAM-only**: `_DEFERRED: dict[str, list[DeferredCandidate]]` and `_COUNTERS` (`promote_txn_hold.py:130-131`); `DeferredCandidate` carries `seam`, `payload`, `deferred_at` — **no id column, no outcome, no DB row** (`promote_txn_hold.py:112-126`).
- The published snapshot is `{deferred, per_seam, counters, reason, driver_running, false_reads}` (`promote_txn_hold.py:353-369`) — counters are **lifetime-per-process**; `per_seam` is **currently parked**. After a restart `per_seam` restarts at 0 while `counters` also restarts at 0 (both are process-local) ⇒ **the readyz number is not comparable across boots**.
- The **drop paths are numerous and unrecorded**:
  - **process death** — `shutdown()` cancels the driver and leaves the candidates parked, with the comment "the next boot's pass owns them" (`promote_txn_hold.py:534-552`). That is true for `boot_continue`/`orphan_sweep` (re-derivable from task rows / checkpoints) and **false for a `runtime_resume` whose trigger was an HTTP request** — that request does not survive the restart. **REVISION 3 (approver item 13 / §0.17): the premise is TRUE FOR THE HTTP SOURCE ONLY.** The resume trigger is entered from **four source classes** — HTTP (`manager.py:15511`, `:15552`), the boot-consistency reconciler (`boot_consistency_reconciler.py:323`, invoked at `:546`/`:583`, re-running at every boot via `daemon/api.py:4094`), the boot_continue/orphan_sweep release handlers (`auto_continue_boot_pass.py:362`, `:428`, re-running at every boot via `api.py:4020`/`:4025`), and a **fourth** source the design did not list (`daemon/services/question_pause_set.py:1196` → `:1211`; re-derivability **UNVERIFIED**). **The reconciler and boot-lane sources ARE re-derivable at the next boot ⇒ for them "the trigger did not survive" would be a FALSE record.** ⇒ The ledger row gains a `trigger_source` field and the reason string is scoped to `http` (§4.2).
  - **release refusal** — `_release_candidates` removes the candidate from `_DEFERRED` **before** invoking the seam handler (`promote_txn_hold.py:488-497`); a handler that refuses internally (the boot_continue handler's refusal path logs "RELEASED-but-refused" and continues) leaves the candidate **gone**; `_release_runtime_resume_candidates` swallows exceptions internally (**UNVERIFIED — I did not open `manager.py:15988-16040`**), so `_release_candidates` sees success and the candidate is dropped.
  - **no handler registered** — dropped **loudly at WARNING** (`promote_txn_hold.py:499-506`, disclosed as "advisory A8" in the **shipped source text** at `promote_txn_hold.py:499-505` — **not** a lane note (§0.20 / §5.6).
  - **live-txn re-defer** — a release that lands while the txn is still live converts `boot_continue` → `runtime_resume`; the original candidate is already removed ⇒ the work_id survives only as a seam-2 payload and one log line.
  - **the bounded release timeout is unreachable while the predicate reads live** — the driver `continue`s at `:427-429` **before** reaching the expired-candidate branch at `:443-446`; `RELEASE_TIMEOUT_S = 900` (`promote_txn_hold.py:81`) is therefore a crash backstop only when the predicate is *not* live.
- The **id trail is lossy — but NOT for the seam-2 ids** *(revision 2 / BLK-5; the previous claim "the runtime_resume log carries no work id at all" was FALSE and is corrected here; the lines were opened this revision)*. The *deferral* logs truncate ids to 8 chars (`auto_continue_boot_pass.py:683-689`, `:1139-1144`; `manager.py:16550-16554` — the `DEFERRED` line carries only `instance_id[:8]`). Full ids survive in exactly three places: (i) the pass-summary log line (`api.py:4023`), (ii) the **file boot record** (`api.py:4048-4067` → `wedge_capture/boot_record.py:325-342`), whose `result_to_dict` keeps untruncated `deferred_work_ids`, and — **new at revision 2** — (iii) the **unconditional** scheduling log line `daemon/manager.py:16518-16521` (`"[RESUME] instance=… scheduling background processing against target_work_id=<FULL id>"`), which is emitted **before** the defer branch (`:16531-16561`) and is therefore **not** truncated, plus the reconciler's `resume=%r` lines (`daemon/services/boot_consistency_reconciler.py:552-557`, `:589-594`) which print the deferred dict verbatim. **The seam-2 (`runtime_resume`) deferrals still appear in neither (i) nor (ii)** — 8 of the 15 deferred items are invisible in the *file record* — **but their ids are recoverable from the log** (§4.7).

### 4.2 The record — fields, identities, outcomes

> **RA-1 (A durable ledger row per deferral).** Every deferral — on every seam — writes one durable row, at the moment of deferral, in the same transaction as whatever durable state the deferral corresponds to.
>
> **RA-2 (Outcome recorded, not inferred). — *the vocabulary is engineering; ONE mapping is EC-17* (revision 2 / BLK-3).** Every ledger row reaches exactly one terminal outcome, drawn from the vocabulary `resumed` / `dropped` / `superseded` / `lost` / `unknown`. **The names are specified engineering; which name a given drop path maps to is a specification for every path except the `runtime_resume`-dies-with-the-process path, which is EC-17's ruling** (see §4.2's drop-path table and §4.6). A row with no outcome is `unknown` — **never** `lost` (the "never `lost`" floor is engineering and is not contingent on EC-17).
>
> **RA-5 (A named owner closes every open row — revision 2 / N-h).** An outcome vocabulary without an owner is a permanent `unknown`, which is precisely the undecidability the commission asks to remove. **⇒ Every ledger row left open by a previous boot is closed at the next boot by a NAMED owner**: the **boot pass** (`daemon/api.py`'s boot-sequence owner — the same pass that writes the boot record at `:4048-4067`) writes the terminal `outcome` + `last_reason` + `resolved_at` for every row whose `boot_epoch` is older than the current one, in the same boot transaction that publishes the boot record. The §4.4 readyz roll-up reads the **ledger**, never the RAM counters. The concrete mechanism follows EC-15 (a dedicated table ⇒ a repository method; the `event` table ⇒ an additive `kind`). **Owner: the boot pass, named here because §4.2 previously had no owner at all.** **REVISION 3 (minor set): the closure MUST NOT block the boot.** The RA-5 closure is a write in the boot pass; if it fails (a DB blip, a lock, a schema mismatch), the boot must **continue** with the rows left open and the failure recorded (an ERROR plus a durable skip-record), **not** abort — an unbootable daemon is strictly worse than an unreconciled ledger row, and the next boot's pass retries. **This is engineering, not a ruling.**
>
> **RA-3 (Stranded class is an outcome dimension).** `1a`/`1b` ⇒ `lost` (proven dead). `2`/`3` ⇒ `unknown` — **never** `lost` (`task/repository.py:106-109`: classes 2 and 3 are non-mutating).
>
> **RA-4 (The evidence join is standard).** Every row carries `boot_epoch`, `instance_id`, `thread_id` (= `instance_id`), `work_id`, and the `checkpoint_ts` observed at defer time, so the question "did the turn exist?" is answerable by joining the ledger to `checkpoints`.

### 4.3 Home options and the trade-off matrix

| | **H1 — the `event` table (additive `kind`, JSON `data`)** | **H2 — a new dedicated table + `.sql` migration** | **H3 — extend the file boot record** |
|---|---|---|---|
| **Complexity** | Low — `Event.kind` is a plain `str` (`daemon/repositories/event/models.py:112`), `data` is TEXT JSON (`:115`), no schema change | Medium — new SQLModel table + a new `daemon/migrations/versions/*.sql` file (the house rule: one `.sql` per new table) + repository + writer | Low — the file record already carries `deferred_work_ids` (`boot_record.py:325-342`; `api.py:4048-4067`) |
| **Scalability** | Medium — the `event` table is **effectively append-only in production**: `cleanup_old` lives at `daemon/repositories/event/repository.py:176` (not `models.py` — corrected, revision 1 / M-4) and its **only callers are tests** (`tests/message_queue_redesign/test_event_repository.py:301`, `tests/message_queue_redesign/test_event_bus.py:462`); **no production caller** — so a ledger homed there would grow forever | Good — a dedicated table can be indexed on `(boot_epoch, seam, outcome)` and queried for "what happened to this work_id" | Poor — 50-file cap, best-effort, post-pass, **and it misses seam 2 entirely today** |

| **Cost** | Low | Medium — one migration + one repository + writer integration | Low |

**Recommended shape (recommendation, NOT a decision): H2 (dedicated table) for the ledger of record, with H1 (the `event` table) as the firehose mirror** for seam-2 and for events that do not warrant a ledger row. Rationale: the commission's requirement is *"make 'did this turn survive the restart?' answerable after the fact"* — that is a **query** ("show me every deferral for boot_epoch X and its outcome"), and a JSON blob in an unbounded append-only table answers it only by full scans. H1 alone is the cheapest and is a defensible answer if the Emperor wants zero schema change in the next release; H3 alone is **not** sufficient (it misses seam 2 and is best-effort).

**Sequencing consequence (non-negotiable):** a dedicated table requires the **house rule** — one `*.sql` file per new SQLModel table in `daemon/migrations/versions/` — and the investigator reports **141 `.sql` files** on `origin/latest` with the newest by name `20261124_093000_add_pok_ledger_gate_chain_unique_index.sql` and the most recent `CREATE TABLE` being `20261124_060000_create_pok_write_gate_ledger.sql` (**UNVERIFIED — I did not open the migration directory**). If H2 is chosen, the migration must land **after** the in-flight lane (the lane touches `manager.py`/`api.py`, which the writer integration also touches).

### 4.4 Readyz semantics

Today the readyz publishes `detail.resume_hold` = the raw snapshot (`readiness.py:706-710`; `api.py:6094`). The design:

- **PENDING EC-16 (revision 3 / approver item 10: this section previously stated EC-16.1's answer as settled).** The surface has three candidate shapes and the ruling is the Emperor's:
  - **Under EC-16.1 (recommended — the Emperor confirms or overrides):** keep the RAM snapshot and **add** the ledger roll-up. Then the surface publishes **three numbers, each named:**
  - `deferred_now` — currently parked (the `per_seam` breakdown, i.e. `promote_txn_hold.py:362`);
  - `deferred_total_this_boot` — lifetime count in this process (the `counters`, `:363`);
  - `deferred_outcomes_this_boot` — the **ledger** roll-up for this `boot_epoch`: `{resumed, dropped, superseded, lost, unknown}` — the number that actually answers "did anything get lost?".
  - **Under EC-16.2:** the RAM snapshot is **replaced** by the ledger roll-up — one number, cross-boot comparable; the live "currently parked" gauge is lost. **REVISION 3 EVIDENCE (§0.20(ii)):** this option's stated downside was that it "breaks any consumer that reads `per_seam`" — **there is no such production consumer** (the only reader in the repo is `tests/unit/tools/test_promote_txn_hold.py:157`, which calls `hold.hold_snapshot()` **directly**; `frontend/src/` has **zero** hits for `resume_hold`/`per_seam`). **⇒ EC-16.2's downside is smaller than the previous revision stated — the Emperor rules on the loss of the live gauge, not on a consumer break that does not exist.**
  - **Under EC-16.3:** as EC-16.1 **plus** an anomaly whenever `lost > 0`. **REVISION 3: the anomaly is now a B-item** (B-7) — the previous revision's B-7 listed only the roll-up and **no item delivered the anomaly**, so EC-16.3 had no implementation at all (§6.2 B-7).
- **Cross-boot comparability.** `counters` and `per_seam` are process-local and restart at 0 (`promote_txn_hold.py:130-131`) ⇒ **they are not comparable across boots and must not be labelled as if they were.** The *ledger* roll-up **is** comparable, because it is keyed by `boot_epoch`. The design therefore makes the ledger roll-up **the headline — under EC-16.1/EC-16.3; under EC-16.2 the RAM counters are gone altogether** — and keeps the RAM counters as a live gauge **under EC-16.1/EC-16.3 only**.
- **`lost` must be visible and bounded.** `lost` is a number an operator must be able to see; it is also a number the Emperor may want bounded (an alarm on `lost > 0`). ⇒ **EC-16**. *(Revision 1 / N-2: the earlier xref pointed at EC-15, the ledger-home choice.)*
- The `readyz` field stays **advisory** (it never gates readiness) — consistent with the current contract (`readiness.py:706-708`: "CONTEXT ONLY — never arming preconditions").

### 4.5 The never-dispatched husk, in the ledger

The husk (§1.7) has **no deferral** — it was never deferred, because there was nothing to defer. It is stranded by the classifier. Under RA-2/RA-3 it must still produce a ledger row, because "we found a stranded instance and did nothing" is exactly the answerable question the commission wants:

| **EC-16.1 Publish the RAM snapshot as today; add a ledger roll-up field** *(recommended)* | `detail.resume_hold` keeps `deferred`/`per_seam`/`counters` (live gauge) and gains `outcomes` (the ledger roll-up, cross-boot comparable) | No consumer breaks; the honest number is present; `lost` is visible but not alarmed |
| **EC-16.2 Replace the RAM snapshot with the ledger roll-up** | One number, cross-boot comparable | Cleanest; **breaks any consumer that reads `per_seam`**; loses the live "currently parked" gauge |
| **EC-16.3 Publish the roll-up and alarm on `lost > 0`** | As EC-16.1 plus an anomaly on a lost turn | A lost turn becomes an operator event; the alarm must be tuned (a lost turn may be legitimate after a `1a` retirement) |

**Team's recommended default (recommendation, NOT a decision): EC-16.1**, with EC-16.3's anomaly **raised for `lost` rows only** (not for `unknown`) — `unknown` is the honest default for a class-2/3 husk and must not become alert fatigue.

#### **EC-17 — Is a `runtime_resume` deferral that dies with the process `lost` or `unknown`?**

*Question:* A `runtime_resume` deferral is an in-flight resume request. **If the process dies before it is released AND the trigger was an HTTP request**, the trigger does not survive — nobody asked for it any more (the HTTP request is gone). **REVISION 3 (approver item 13 / §0.17): the premise is TRUE FOR THE HTTP SOURCE ONLY.** For the reconciler and boot-lane sources the work IS re-derived at the next boot, so the honest answer is "re-derivable" — not "lost", and not "the trigger did not survive", which would be a **false record**. **⇒ EC-17's scope is narrowed to `trigger_source = http`; the other sources map to `unknown` / `re-derivable-at-next-boot` and are NOT in scope of this ruling.**

| Option | Semantics | Consequences |
|---|---|---|
| **EC-17.1 `unknown`** *(recommended)* | We cannot prove the request was abandoned; the operator may still be waiting | Honest; the row stays open and is reconciled at the next boot as "trigger did not survive" |
| **EC-17.2 `lost`** | The request is gone; the work never happened | A crisp number; **but it conflates "the user gave up" with "we lost it"** — and the user's next message may re-issue the same work anyway |
| **EC-17.3 `superseded`** | A later request for the same instance supersedes it | Needs a supersession rule (same instance + same target work?) — brittle |

**Team's recommended default (recommendation, NOT a decision): EC-17.1**, with the boot-time reconciler marking the row's `last_reason=trigger-did-not-survive` **— for `trigger_source = http` only** (§0.17) — so the operator can see the distinction. **For the reconciler / boot-lane / question-pause sources the row is written `unknown` with `last_reason=re-derivable-at-next-boot`; the Emperor is not asked to rule on a record the code would make false.**

**Summary of §4's choices:** EC-15 (ledger home), EC-16 (readyz surface + alarm), EC-17 (`runtime_resume` drop semantics). The **outcome vocabulary** — the *names* `resumed` / `dropped` / `superseded` / `lost` / `unknown` (RA-2) — and the stranded-class mapping (RA-3) are specified engineering, **and only the names are**. *(Revision 2 / BLK-3: the previous draft said "the outcome vocabulary (RA-2) … [is] specified engineering, not choices" three lines below framing EC-17 as an open choice — the body pre-empted the ruling. The vocabulary is engineering; **which** outcome a `runtime_resume` death maps to is EC-17.)* The field set (§4.2) and the owner rule (RA-5) are engineering.

### 4.7 The historical 15 — what can and cannot be reconstructed

**The recovery procedure for the 8 `runtime_resume` ids** *(revision 2 / BLK-5 — the approver asked for the actual procedure; every step cites a line opened this revision)*:

1. **Anchor the window.** Take the two boot epochs from the readyz snapshots (§8 item 1) — the boots whose `detail.resume_hold.deferred` was 15 (7 + 8).
2. **Harvest the candidate ids.** In the live daemon log for those windows, grep the **unconditional scheduling line**: `[RESUME] instance=… scheduling background processing against target_work_id=…` (`daemon/manager.py:16518-16521`). Every hit carries the **full, untruncated** `target_work_id`. (This line is emitted for *every* resume, deferred or not — it is a superset.)
3. **Narrow to the deferred ones.** A candidate is deferred iff the same window contains the `DEFERRED: reason=pipeline-busy` line for the same instance (`daemon/manager.py:16550-16554`) — that line carries only `instance_id[:8]`, so the join is by **instance prefix + timestamp window**.
4. **Take the authoritative list from the reconciler.** The boot-consistency reconciler's `[BOOT_RECOVERY_RESUME_REFUSED] … (resume=%r)` lines (`daemon/services/boot_consistency_reconciler.py:552-557`, `:589-594`) print the returned dict verbatim: `{'instance_id': …, 'job_id': <full target_work_id>, 'message_id': …, 'status': 'deferred', 'reason': 'pipeline-busy'}`. **This is the authoritative id list FOR THE RECONCILER-ORIGINATED DEFERRALS** — it is the dict the daemon actually returned for that source (the `_drive_resume` call at `boot_consistency_reconciler.py:316-333` returns `manager._schedule_explicit_handle_resume(...)`, the same function that defers at `manager.py:16531-16561`). **REVISION 3 (minor set): it is NOT authoritative for the whole population** — `_schedule_explicit_handle_resume` has **four** caller classes (§0.17), so the reconciler is authoritative only for the deferrals it originates. **The load-bearing part of this procedure is the SUPERSET grep in step 2** (the unconditional `[RESUME] … target_work_id=…` line), which covers every source; the reconciler's list narrows it for the reconciler source only.
5. **Derive the outcome.** For each recovered id the outcome is still `unknown` unless the release evidence exists: a `[BOOT_RECOVERY] … dispatched` / resume-released line, **or** a terminal task row for that `work_id` (the task table is the ground truth for "did the turn finish"), **or** the resume terminalizer's `complete_task` + marker clear (`daemon/manager.py:16862-16891`).
6. **Write the rows.** One row per recovered id: `seam=runtime_resume`, `work_id` = the recovered id (**known**), `instance_id`, `boot_epoch`, `outcome` = `unknown` unless step 5 proves otherwise, `last_reason` = `recovered-from-resume-log`, `closed_by` = `recovery-<date>` (RA-5).

**Two consequences for the schema:**

1. **The ledger's `work_id` must be NULLABLE — but not because the 8 historical rows are id-less.** *(revision 2 / F8 + BLK-5.)* The §4.2 field table said `work_id | text`; it is `text | null`, and the reason is the **§4.5 stranded-surfacing rows** (a husk has no work_id). The 8 `runtime_resume` rows **do** carry a recovered id (§4.7), so they are **not** the justification for nullability — the previous draft's "count-only rows have no id to carry" was wrong on both counts.
2. **A backfill must never be presented as an accounting.** The 7 `boot_continue` reconstructed rows carry `outcome=unknown` unless independent evidence (the §8 item 1 readyz payload, the `[BOOT_CONTINUE] RELEASED` log lines) proves a release; the 8 `runtime_resume` rows carry a **known id** with `outcome=unknown` unless the §8 item 5 evidence proves a release. The ledger's job is to make *future* boots answerable, not to retroactively explain this one.

**Also forced by this:** the §4.5 stranded-surfacing rows have the same nullable-`work_id` shape (a husk has no work_id), so the nullability is not a special case — it is the honest representation of "we know there was work, we do not know which".

**What the ledger must hold for the 15 (the commission's requirement-4 answer, restated):**

| | `work_id` | `instance_id` | `boot_epoch` | `outcome` | Provenance |
|---|---|---|---|---|---|
| **7 × `boot_continue`** | known (the boot record's `deferred_work_ids`) | known | known | `unknown` unless release evidence | `reconstructed-from-boot-record` |
| **8 × `runtime_resume`** | **known (recovered per the procedure above)** | known (the deferred dict) | known | `unknown` unless release evidence | `recovered-from-resume-log` |
| **every future boot** | known at deferral time | known | known | written at the deferral site | the ledger row itself (RA-1) |

**⇒ "Did this turn survive the restart?" is answerable after the fact for all 15 — the ids are known, the outcomes are `unknown` until the release evidence is applied, and no row is ever silently `lost`.**

## 7. OPEN QUESTIONS FOR THE EMPEROR — the framed choices, collected

Each entry is self-contained: question → options → consequence of each → what the work looks like → the team's **recommended default** (a recommendation, not a decision). The work around each choice is designed and ready to land; what is missing is the ruling.

### Preservation contract

**EC-1 — A PENDING task's message at boot: may the boot delete it?**
1. **Re-dispatch (at-least-once)** — keep the message; the work re-runs; **pre-checkpoint side effects may repeat**; the pending backlog drains at boot. *Work:* one new predicate arm (gated OFF until ruled) + **whichever EC-5 option is ruled** (the claim barrier under EC-5.1/EC-5.4, the generation counter under EC-5.2, neither under EC-5.3).
2. **Park for operator** — keep it, make the task unclaimable, surface it; no loss, no duplicates; **the queue stalls until a human acts**; needs a parked state + a surface + a release path. *Work:* a new state/table + surface + operator tooling.
3. **Drop loudly** *(the in-flight lane's orphan belt)* — delete the message, fail the task with `orphaned_by_boot_purge`; deterministic and visible; **the work is lost** and the sender must re-send. **BUT the belt is a raw `UPDATE`, not a transition:** it deliberately does **not** route through `TaskRepository.fail_task`, so it skips `reconcile_turn_mirror(work_id)` and `_notify_pending_task()` (lane `message_queue/repository.py:1661-1669`) ⇒ **a failed-by-belt task does not notify its parent ⇒ the parent can be left in `WAITING_CHILDREN` on a child that will never report ⇒ a parent wedge** (mitigation: the `WAITING_CHILDREN` hang watchdog, `daemon/config.py:2608-2629` — its compensation is **UNVERIFIED**). **⇒ The belt must be routed through `fail_task`, or carry a labelled waiver for the wedge** — otherwise the option buys "lost work" with "wedged parent". *Work:* **already implemented in the lane (L8)**, **plus** the `fail_task` routing or the labelled waiver — **~0.25 release on top of the lane**, not zero. The belt also covers `status='pending'` only (`:1684`), so the widening in §1.6(1) must widen it too.
4. **Keep the receipt rule** *(status quo)* — preserve only with a JobItem or a receipt; **the rule's safety depends on the probe that failed on PostgreSQL** — one evaluation defect dooms the whole set. *Work:* none. **Status quo is the defect.**
**Recommendation: 1**, keeping 3 as the belt for rows whose message was deleted anyway.

**EC-2 — Messages whose task is terminal or gone: delete, archive, re-create, or quarantine?**
1. Delete all *(today)* — cheapest; no forensic value; a task-less message may itself be a prior purge's victim. 2. Archive then GC — reconstructable; costs a table + a GC job + a policy. 3. Re-create the task — delivers again; **re-delivers old messages** without dedupe. 4. **Delete terminal-only, quarantine task-less** — the pruner role survives; the ambiguous population becomes visible. *Work:* quarantine marker + surface + GC rule.
**Recommendation: 4.**

**EC-3 — An unevaluable predicate at boot?**
1. Abort boot — maximum safety, **the daemon is down**. 2. Skip the purge, ERROR log only *(the lane)* — the daemon is up; **the condition is invisible**; the backlog grows with no signal. 3. **Skip the purge + surface (ERROR + metric + readyz degraded + anomaly)** — the daemon is up and the operator is told. 4. Delete with the degraded predicate *(pre-lane)* — **data loss under a fault**. *Work:* option 3 = the PC-3 surfaces (B-2).
**Recommendation: 3** (option 1 contradicts the shipped doctrine at `message_queue/repository.py:29-34` on the lane). **REVISION 3 — option 2 is NON-COMPLIANT with the commission's fail-loud floor** (approver item 2): EC-3.2 leaves the condition invisible to operators, so the backlog grows with no signal; the work that meets the floor is **B-2**, and **B-2 exists only under EC-3.3**. **⇒ The Emperor rules with that asymmetry in view: EC-3.2 is the lane's shipped behaviour and it does not meet the commission's requirement.**

**EC-4 — A backing table genuinely absent (legacy schema): absence vs failure?**
1. Degrade with WARNING *(the lane)* — the daemon boots, but **the legacy predicate dooms PENDING-task messages on that host permanently**. 2. Treat as unevaluable ⇒ skip the purge — safest, but **the backlog is never cleared** on such hosts. 3. **Degrade to the provably-safe target** — terminal-task messages only; never a PENDING-task message. *Work:* a second predicate shape + a kill-switch.
**Recommendation: 3.**

**EC-5 — May the boot block worker claims of PENDING tasks while the purge is armed and unfired?**
1. **Claim barrier** — the worker pool refuses to claim a PENDING task from arming until the purge fires / is skipped / times out (bounded by the purge's own 5 s floor, released on all three exits); the window becomes **empty** rather than narrow; needs a provable release (a leaked flag parks every PENDING task forever). 2. **Generation counter only** — no claim latency; the residual race **survives** for anything the generation does not cover. 3. **Neither** — zero work; **the race is the incident**. 4. **Bounded barrier variant** — as 1, plus a wait budget and a log line that makes the residual race measurable.
**Recommendation: 1**, with **2 as defence-in-depth.** This is a behaviour change at boot, hence a ruling — the document prices it but does not choose it.

**EC-18 — May the boot reap a never-dispatched RUNNING husk at some age?**
1. **Never reap — record only** — the husk stays running; the ledger records it as `unknown` with its stranded class. 2. **Reap at the existing 24 h / class-1a bound** — frees the instance list; **irreversible**, and it rests on the zero-checkpoint proof. 3. **Reap at a shorter, Emperor-chosen age** — frees the list sooner; **destroys instances that may still be waiting on a human** (a `waiting` instance is alive by definition).
**Recommendation: 1** until the stranded-class evidence justifies 2.

### Stop path

**EC-6 — What is the stop contract?**
1. Reorder only — smallest change; the unbounded MUST steps can still eat the budget. 2. Longer bound — no code risk, but the number is a guess and the failure mode is deferred, not removed. 3. **Deadline-driven budget (one declared `B`, MUST set with reserved budgets, MAY set deferred to boot, skip-with-record, derived bounds)** — the stop time becomes `B` by construction; a partial stop becomes visible. 4. Boot does the cleanup — every stop becomes a boot; the boot already pays the same 60 s reconcile.
**Recommendation: 3.**

**EC-7 — May a stop leave durable work for the boot?**
1. No — the stop must close everything ⇒ the durable-row steps move from MAY to MUST ⇒ **`B` grows** ⇒ every promote stop gets slower. 2. **Yes for durable rows, no for live children** — bulk-kill what is cheap (RAM tier, proc groups, `service_start` services), leave the durable row bookkeeping to the boot reconcile with a "kill requested" marker. 3. Yes for everything — simplest, but leaves the cgroup sweep as the primary mechanism (the exact "exit-code" shape we are removing). *Conditional on* the boot-reconcile budget being fixed in the same release.
**Recommendation: 2.** *(Revision 2 / BLK-2 — the body is written as conditional on this ruling: SP-2's MAY class, §2.4(2) and B-5 each state what they do under each branch, and none of them answers the question. If option 1 is chosen, `B` grows by the janitorial slice `J`.)*

**EC-8 — How is a partial stop represented?**
1. Partial = crash — the launcher would count a requested stop as a crash. 2. **Partial = a dedicated exit code, classified as neither crash nor clean, and included in `SuccessExitStatus`** — visible, and the burst guard is untouched. 3. Partial = 0 but always journaled — simplest; invisible in the exit code.
**REVISION 3 — the premise all three options share, and the deliverability caveat.** **A clean stop is 143, not 0** (§0.12): uvicorn re-raises the SIGTERM, the launcher propagates it, and the unit already declares `SuccessExitStatus=143`. **So every option presupposes that the clean stop's own status is handled** — a 143 translation (daemon-side `capture_signals` override, or launcher-side at `:4395`/`:4453`) **and** a `classify_exit` fix (`launcher.sh:4243-4250` classifies 143 as a crash today). That handling is **engineering, not a fourth axis**. **Option 2's dedicated code is NOT deliverable via the daemon's own exit status** (that status is already consumed by the signal convention) ⇒ it needs the **launcher-side mapping**, which is why `launcher.sh` is in B-5's file set.
**Recommendation: 2.**

**EC-9 — The launcher counters.** *(revision 2 / BLK-4 — option 2 is retired as a choice; it is now engineering, specified in §2.5 and shipped in §6.2.)*
1. **Keep the guard; fix the display only** — the operator sees the window age and a classification. 2. *(retired — engineering: a requested stop resets the burst window, because a requested stop is not a crash.)* 3. Make the window purely time-bounded at read time — no writer change; the file still *displays* a scary number to a naive reader.
**Recommendation: 1** (display), with the reset-on-stop writer behaviour shipping as engineering in §6.2 (B-6). *(The writer change touches the launcher's shutdown path ⇒ §6.2, not §6.1.)*

**Recommendation: 1 now, 3 as the observability add-on.**

**EC-11 — The shutdown budget knob and its default.** *(revision 2 / N-h — a parameter of EC-6.3, not an independent axis: under EC-6.1/EC-6.4 there is no single `B` and this question is moot.)*
1. Config-only, default 55 s (so `B + 10 ≤ 70`, today's launcher bound). 2. **Env-overridable with a clamp** — the same default, plus operator control; the clamp keeps `B + margin ≤ CHILD_STOP_WAIT_S`. 3. `B` = 45 s — tighter MUST set, more launcher headroom, less time for long turns.

### Journal

**EC-12 — Journal retention and compaction.**
1. Operator-manual trimming *(today)* — the journal grows until a human acts. 2. **Bounded retention with an archive, ceremony-time under the lock** — keep the last N terminal runs + all `halt`/`rollback`/`sweep_rollback`/`refusal` rows; archive the rest with a sha256; the archive write precedes the truncation. 3. Daemon-side GC — no ceremony-time write, but the daemon and the pipeline then write the same file (a concurrency hazard the mkdir-lock exists to prevent). 4. Archive without truncation — zero risk, but **does not bound the size** and therefore does **not** re-arm the launcher sweep.
**Recommendation: 2**, with **4 as the cheap first step** — and the Emperor should be told explicitly that 4 alone does not fix the disarm.

**EC-13 — How is a run's outcome derived?**
1. Keep "newest terminal-class row wins" *(today)* — **a committed promote is displayed as "swept (orphaned pre-flip txn cleared)"**. 2. **Prefer the authoritative terminal event across the history** — fixes the display without changing the bytes; format-free; A-1 already implements it. 3. **Scope by `run_id` and pick that run's authoritative event** — fully correct for a multi-run journal, **but it is a journal FORMAT change (M-3)**: history entries are `{ts,event,detail}` with **no `run_id` field**, and a manual operator promote carries no `run_id` anywhere. **REVISION 3 — the authoritative set is now DEFINED (JT-3, §0.16): 9 names** — `commit`, `rollback`, `halt`, `sweep_rollback`, `quarantine`, `refusal`, `executor_exit`, `boot_sweep_commit_and_continue`, **`serving_green_commit`** — **plus a 2-name fallback** (`txn_sweep_preflip`, legacy `sweep`) for a run closed by a pre-flip sweep with no authoritative row. **The previous revision's eight-name list omitted `serving_green_commit` and would have regressed a serving-green close.** The `run_id` scoping (**option 3**) remains **PENDING** and is not assumed by A-1.
**Recommendation: 2 as the floor**; 3 only if the Emperor accepts the journal format change. (Revision 1 / M-3: the earlier draft recommended 3 without pricing the format change.)

**EC-14 — Where do refusal records live?** *(revision 2 / N-h — a placement detail inside JT-1, not a semantic choice: the fact must be recorded either way.)*
1. Narrative log only — not durable, not queryable. 2. **A `journal_append_refused` row in the journal plus a sidecar when the journal itself is the thing that failed** — durable in both cases. 3. Sidecar only — the journal stays clean, but the status view needs a second read path.
**Recommendation: 2** — *and the placement is confirmed or overridden here, not assumed:* the design's recommendation is **EC-14.2 (a `refusal` journal row + a sidecar when the journal is the thing that failed + the narrative line)**, and JT-1, §3.3(c) and B-10 are all written to it. **The Emperor confirms or overrides, and the three sites change together.** (The `refusal` event class already exists — `daemon/tools/upgrade_journal.py:2563`, written by `daemon/tools/upgrade_tools.py:1268` — so the journal row needs no new vocabulary. **The sidecar does not exist today**: `grep -rn "refusals.ndjson"` returns one hit, this document — so EC-14.2's sidecar half is NEW work in B-10.)

### Resume accounting

**EC-15 — Where does the resume ledger live?**
1. The `event` table (additive `kind`, JSON `data`, **no migration**) — cheapest; but it is effectively append-only in production (`cleanup_old` at `daemon/repositories/event/repository.py:176` has **no production caller** — only tests) and every query is a JSON parse. 2. **A new dedicated table + a `.sql` migration (house rule)** — typed, indexed, cross-boot comparable; costs a migration and must land **after** the lane. 3. The file boot record — best-effort, post-pass, 50-file cap, **misses seam 2 entirely**; insufficient alone.
**Recommendation: 2 + 1** (the ledger of record is the dedicated table; the `event` table is the firehose mirror), with **1 alone as the "no schema next release" fallback**. Option 3 is not sufficient.

**EC-16 — The readyz surface and the `lost` alarm.**
1. **Keep the RAM snapshot and add a ledger roll-up** — no consumer breaks; `lost` is visible but not alarmed. 2. Replace the RAM snapshot with the roll-up — cleanest, but breaks consumers reading `per_seam` and loses the live gauge. 3. As 1, plus an anomaly on `lost > 0` — a lost turn becomes an operator event. **REVISION 3 — the evidence on option 2's stated downside (§0.20(ii)):** **there is no production consumer of `detail.resume_hold.per_seam`** (the only reader in the repo is `tests/unit/tools/test_promote_txn_hold.py:157`, which calls `hold.hold_snapshot()` directly; `frontend/src/` has zero hits). **⇒ Option 2 breaks no production consumer — the Emperor rules on the loss of the live gauge, not on a break that does not exist.** Option 3's anomaly is **now a B-item** (B-7); the previous revision had no implementation for it.
**Recommendation: 1**, with the anomaly raised for `lost` rows only (**not** for `unknown` — a class-2/3 husk must not become alert fatigue).

**EC-17 — A `runtime_resume` deferral that dies with the process: `lost` or `unknown`?**
1. **`unknown`** — we cannot prove the request was abandoned; the operator may still be waiting; reconciled at the next boot with "the trigger did not survive". 2. `lost` — crisp, but **conflates "the user moved on" with "we lost it"**. 3. `superseded` — needs a brittle supersession rule. **REVISION 3 — the scope is narrowed to `trigger_source = http` (§0.17):** the premise "the trigger does not survive" is **true only for the HTTP source**. For the boot-consistency reconciler and the boot_continue/orphan_sweep lanes the work IS re-derived at the next boot, so a `trigger-did-not-survive` record would be a **lie**; those rows are written `unknown` with `last_reason=re-derivable-at-next-boot`. **The Emperor is not asked to rule on a record the code would make false.**
**Recommendation: 1.**

## Appendix A — Design summary in one page

**§1 Preservation.** One predicate, one carrier (`boot_wipe_preserve_predicate_sql` on the lane) — but **three LIVE evaluation sites** (capture / task wipe / delete-time re-check) **and one dead** (the message-side `clear_all` has no production caller), so the contract now also carries **PC-1b** (one evaluation *outcome* per boot, published and sticky) and **PC-1c** (the cross-side delete invariant, keyed on a **monotone floor**). **REVISION 3: the lane's orphan belt changes the consequence** — the belt fails the orphaned PENDING task **in the same transaction as the DELETE** (§0.15), so a half-purge destroys committed work **through the belt**, not through the `ValueError`; the belt is conditional, covers `pending` only, and skips `fail_task`'s notifications. PC-1b closes the **evaluability** entry; a **second, row-state TOCTOU entry** exists (§1.5(a)). Safe default PRESERVE; unevaluable ⇒ delete nothing + ERROR + metric + readyz degraded + anomaly (**PC-3 exists only under EC-3.3**). The lane delivers the carrier and the fail-closed guards; it does **not** deliver the fail-loud surfaces, the NULL-safe rewrite, the `processing`-status arm (in either the predicate or the belt), the claim barrier, the durable manifest, or the evaluation discipline. The semantic rulings are EC-1…EC-5 plus EC-18 (husk reaping) — **all PENDING**.

**§2 Stop.** The 70 s is spent on a 60 s **janitorial** sweep that is scheduled *before* every durability step and is non-fatal by its own contract — **and the sweep is on the stop path TWICE: the unbounded per-instance leg (`bash.py:650`) and the bounded lane leg (`manager.py:17716`)** (§0.13). **REVISION 3: a clean stop is 143, not 0** (§0.12), and **the recommended budget cannot contain the MUST set** — `D` alone (60 s) exceeds the proposed `B` (55 s), and the bounded MUST steps alone are ≥ 90 s (§0.14). The recommended contract (pending EC-6/EC-11) must become: one declared budget `B` with a **named derivation** (`B = D + P1 + M (+ J)`); a MUST set (durability) with reserved budgets; a MAY set (janitorial) deferred to boot reconcile **— conditional on EC-7**; a monotonic deadline; skip-with-record; and the launcher/unit/stop-script bounds **derived** from `B` (today there are six primary hand-synced bounds plus seven more). **The exit shape is a three-branch conditional on EC-8**, and the recommended budget's default carries an arithmetic hole the Emperor must be shown. The launcher's counters are residue by construction; the reset-on-stop writer behaviour is **engineering**, the display is EC-9. The rulings are EC-6…EC-11 — **all PENDING**.
