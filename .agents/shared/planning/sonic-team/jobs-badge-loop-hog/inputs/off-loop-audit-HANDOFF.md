## CPU-betterment beyond offloading (deliverable 2)
- **Two different goals.** (a) OFF-LOOP (threads) frees the LOOP — works for I/O-bound waits (DB, files, network) because the GIL is released while waiting; LLM calls are I/O-bound in the wait phase, threads fine. (b) TRUE CPU parallelism for pure-Python/GIL-held work (pydantic schema builds, tiktoken pathological encodes, deep-size walks, big JSON encodes) — threads add NO CPU throughput; only a process pool or C-accel path does. Offloading GIL-held work to a thread moves the stall from "loop blocked" to "loop AND worker both starved" — partial fairness win, no throughput win.
- **Evidence says: go algorithmic before parallel.** The top blockers are WASTED work (schemas rebuilt per assembly; token counts repeated 13×+20 iterations; encoder re-fetched per call; unbounded pathological inputs). Caching/bounding eliminates the work entirely; parallelism merely distributes it.
- **Executor topology for 16 vCPU (after bridges):** keep db_offload (6 workers) for sync DB — PG manager pool is 15, so 8–10 workers is safe headroom; SPLIT the default pool: dedicated LLM-invoke pool (16–32 workers — long network waits), short-IO pool for file/subprocess helpers; ONE bounded process pool (workers ≤ ~8, spawn-on-demand) reserved for residual GIL-bound hot units (coarse-grained only — pickling cost rules out per-request chatter; checkpoint blobs must never cross it). Extend the metrics vocab so every pool has occupancy series (today: manager/checkpoint only).
- **Where the 15 idle cores actually come from:** after rows 1–4 land, cores get used by db_offload threads (I/O), the LLM pool (I/O waits), PG itself, and process-pool bursts. Before that, most "idle CPU" is unreachable because the loop serializes everything and the default pool is small + held by LLM waits.
