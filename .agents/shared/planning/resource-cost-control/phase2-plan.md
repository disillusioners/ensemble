# Phase 2 — Attribution + PID Registry

**Commission:** resource-cost-control · **Spec:** `architecture-recommendation.md` §2.2 (hybrid attribution), §2.3 (pid→instance mapping, bash success-path exit-mark) · **Slice:** 2 of 8

## 1. Goal

Make cost *attributable*: cheap always-on charge seams + per-pid exact subprocess reads + one bounded deep-scan reconcile per tick, plus the generalized `service_tracking`-style pid registry (live RAM dict + `resource_pid_map` history) with PID-recycle defense and the bash success-path exit-mark fix. Publish the per-instance table with honesty columns (`estimated`, `unattributed_kb`, `coverage_pct`) surfaced — not buried — in the API.

**Attribution is partial by physics — both councilors flagged it independently, the plan treats the residual as a first-class output (§2.2 🔴 block): per-byte in-process RAM attribution is impossible (Python-object counters typically 40–80 % of anon RSS); per-instance in-process CPU is not measurable (only children are exact); MCP RAM is server-scoped (shared pools, `DEFAULT_POOL_SIZE=1`).**
