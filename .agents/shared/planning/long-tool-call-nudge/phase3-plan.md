# Phase 3: Parent Tuning Tool (`set_instance_tunable`) + Agent Exposure + Docs

## Objective

Ship a parent-facing tool that lets a parent instance (leader / planner / developer) **write a per-child threshold override** into the child's `instance_metadata["long_tool_call_threshold_seconds"]` JSONB column. The detector built in Phase 1 / 2 reads this key on its next scanner tick (no daemon restart). The tool is the operator-facing surface of the long-tool-call-nudge feature; without it, parents cannot tune per-child behaviour and the only lever is the global default (900 s).

## Coupling

- **Depends on**: Phase 1 (detector reads `instance_metadata["long_tool_call_threshold_seconds"]`) and Phase 2 (config validation pins the canonical default 900 / hard max 1800 constants the tool reuses).
- **Coupling type**: tight on the metadata-key contract; loose on the scanner runtime — the tool writes a key, the scanner reads it on the next tick (no shared lock, no shared module).
- **Shared files with other phases**:
  - `daemon/config.py` — Phase 2 owns `LongToolCallNudgeConfig` (default 900, max 1800). Phase 3 imports the ceiling constant `HARD_MAX_THRESHOLD_SECONDS` from `daemon.services.long_tool_nudge` (canonical home per synthesis AD-30 — NOT from `daemon.config`, and the symbol is NOT named `MAX_THRESHOLD_SECONDS`).
  - `daemon/repositories/instance/repository.py` — Phase 3 uses `set_metadata(instance_id, key, value) -> Instance | None` (`:2099`) as the **sole** write path (NEVER `update_instance`, which rejects `instance_metadata` at `:1094-1121`).
  - `agents/{leader,planner,developer}/meta.json` — exposure changes are Phase 3 only (no Phase 1 / 2 ownership of `tools.allow`).
- **Shared APIs / interfaces**:
  - **Metadata key name** `"long_tool_call_threshold_seconds"` is the single contract with Phase 1 — phase 3 must use the **exact** spelling (snake_case, units in the name) so the scanner's lookup hits. Lowercasing, abbreviating (`"ltct"`), or renaming the unit (`"_minutes"`) silently disables the override.
  - **Effective-value formula** = `min(stored-or-default, 1800)` — Phase 2 owns the formula; Phase 3 must echo this value back to the caller so the parent sees what the scanner will actually use.
  - **Tool category** `"instance"` (existing) — reuses the same `@register_tool_category` registration seam and the same `tools.allow` taxonomy as `spawn_instance` / `terminate_instance` / `send_message`. No new category, no new allow-list convention.
- **Why this coupling**: the metadata key is the only handoff between Phase 3 (write) and Phase 1 / 2 (read). If the spelling or the JSONB column choice diverges, the detector falls back to the global default and the override is a silent no-op — the exact "doesn't work but doesn't error" failure mode this feature is most exposed to.

### Constraints (do NOT violate)

- **NO spawn-time threshold kwarg chain** in v1 — runtime-set only via the new tool + `set_metadata`. Spawn kwarg chain = documented alternative (Decision D1 below).
- **NO auto-kill / pause / terminate** on threshold breach — this feature is **advisory nudge only** (per spec non-goal).
- **NO system-prompt changes** to any agent — `meta.json` `tools.allow` is **CONFIG**, not prompt. Distinction justified in Open Decisions.
- **NO modification of Phase 1 / 2 file surfaces** — Phase 3 ships the write-side tool; Phases 1 / 2 own detection + delivery.
- **NEVER call `update_instance` with `instance_metadata`** — the tool must go through `set_metadata` (raises `ValueError` otherwise).
