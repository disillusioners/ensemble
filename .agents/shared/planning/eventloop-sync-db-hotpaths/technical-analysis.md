## Question

## Context Summary

Two defect families, cleanly separated by the baseline's on-loop attribution (BASELINE §2): (a) the instances/work/defer-blocked/missions shapes issue **every** SQL round-trip synchronously ON the event loop (100% on-loop rts; sync repo calls directly inside `async def` handlers — all 250 router handlers are `async def`, the threadpool is never used by handlers, and repositories are 100% sync `with Session(engine)`); (b) the `/api/jobs` badge shapes issue **zero** on-loop rts — their enrichment runs via `asyncio.to_thread` and lands on the DEFAULT executor, which saturates (up to 5/12 workers inside repo statements, BASELINE §5) and pays 1,439–1,874 rts/request, of which **92.3% of statement TIME is orphan-id `_lookup_instance` singles** (BASELINE §6). The sibling db-pool-idle-txn lane (v0.27.13, staged) fixed leaks, pool hardening and F8 no-txn-across-await, and explicitly recorded that the DWELL/OCCUPANCY class — "sync DB work on the event loop and the BFS depth-loop span" — is NOT removed (`daemon/persistence.py:316-334` honesty comment; decisions.md A12(i) names this lane's defect "a dwell multiplier, not a cosmetic latency defect"). This lane builds on that clean pool: the manager engine is 5+10 (capacity 15, D-57 equality-pinned), `pool_timeout=30` (D-15), `pool_recycle=3600`, `pool_pre_ping=True` (D-14), zero sites hold a txn across await (F8), and the engine-level idle-in-txn backstop ships DISABLED (D-47).

## §2 Implementation strategy per site-class

Mechanism vocabulary (Q3): **A** = query-shape batch (N statements → 1), **C** = off-loop bridge (sync code executed on a dedicated executor thread). Async-native is §3 and is NOT this lane's mechanism.

### 2.0 The bridge seam (shared infrastructure for every C site)

**In-repo precedents (verified verbatim):** `daemon/services/job_queue_service.py:1732` `return await asyncio.to_thread(work_resolver.resolve_work, work_id)`; `:1831-1837` `return await asyncio.to_thread(work_resolver.list_work, project_id=…, status=…, kind=…, root_only=…)`; `daemon/services/instance_messaging.py:6045` `await asyncio.to_thread(self._manager._instance_repository.get, instance_id)`; `:6080` `await asyncio.to_thread(self._queue_repository.get_stats, instance_id)`. These four are the house pattern; this lane extends it.

**Executor-selection discipline (binding):** NONE of these C sites may use `asyncio.to_thread`'s default executor. The default `ThreadPoolExecutor` (`min(32, cpu+4)` = 12 workers on the 8-core host) is the saturated pool the jobs badge already degrades (BASELINE §5: 5/12 workers inside repo statements; sibling architecture-recommendation A7: 1,351 `to_thread`/`run_in_executor` call sites daemon-wide share it). Land a **dedicated module-level executor** for DB bridging, following the existing dedicated-pool precedents: `daemon/services/plane_sync_service.py:253` `_plane_sync_executor = ThreadPoolExecutor(max_workers=2)`, `daemon/services/question_pause_set.py:137` `_MERGE_EXECUTOR` (max_workers=1, whole read-modify-write serialized), `daemon/services/upgrade_journal_sweep.py:233` `_waitpid_executor`. **Reuse verdict:** none of the three is reusable (task-specific contracts: plane-sync registry, question-pause merge serialization, waitpid reaping) — create one new `daemon/services/db_bridge.py` (new file, additive) exposing `await run_db(fn, *args)` implemented as `loop.run_in_executor(DB_BRIDGE_EXECUTOR, contextvars.copy_context().run, functools.partial(fn, *args))`.

- **Sizing:** 4 workers. Rationale: worst case = the four T-tier/C-core bridged endpoints firing concurrently; 4 ≤ the manager engine's overflow headroom (capacity 15, D-57) so full bridge concurrency cannot alone exhaust the pool (§8 risk 4). Make it an env-overridable constant in `daemon/constants.py` (config-only — no migration; §7).
- **Shutdown semantics:** daemon-lifetime module-level pool; no explicit shutdown needed (the three precedents shut none of theirs down); document atexit behavior.
- **Contextvars:** `run_in_executor` does NOT propagate context; the `copy_context().run` wrapper preserves logging/request tags (the baseline harness attributes statements to the loop thread via the daemon's own `LoopLagProbe` `loop_thread_native_id` — bridge-thread statements are correctly attributed OFF-loop by construction, which is exactly what the N2/N4 gates measure; BASELINE §Instruments).
- **Error contract:** the bridge must propagate the SAME exception types the sync path raised (HTTP error shapes byte-identical); degradation contracts inside callees (`_lookup_instance` catches `SQLAlchemyError` → logs warning → returns None, `work_resolver.py:2004-2010`) survive bridging verbatim because the callable is the unchanged sync function.
- **Forbidden:** never bridge a callable that participates in `WriteGuardSession` or holds anything across the bridge boundary (F8 analog — D-33/D-34 three-phase shape); every C site here is a pure read facade.

### 2.1 C-1 — instances children N+1 (A + C)

**Query-shape change (A):** replace the per-row loop at `instance_lifecycle.py:5115` with ONE `SELECT instance_id, parent_id FROM instances WHERE parent_id IN (<page ids>) ORDER BY parent_id ASC, instance_id ASC` (new repo method, e.g. `list_child_ids_for_parents(parent_ids)`, in `daemon/repositories/instance/repository.py` beside `list_child_ids_permanent` at `:417`), regrouped into `dict[parent_id, list[instance_id]]` and merged in PAGE order so `info["children"]` assembly order is untouched.

**ORDER BY choice (Q3 requires it named):** `parent_id ASC, instance_id ASC`. The grouping key MUST lead (regrouping requires it); `instance_id ASC` makes the per-parent child order deterministic. **Byte-identity hazard, stated plainly:** today's per-row query (`repository.py:432-436`) has NO ORDER BY — the current `children` array order is whatever PostgreSQL's plan returns (heap order ≈ insertion order in practice, unspecified by contract). HEAD's order is deterministic; BASE's is not guaranteed to equal it. The tester's BASE-vs-HEAD byte-diff gate must therefore adopt ONE of: (i) a disclosed normalization rule for `children` arrays (sort-before-compare), or (ii) an empirical BASE order pin proving the fixture's natural order coincides with ascending id. This is a test-design input the plan MUST carry (§8 risk 1) — it is the single most likely false-red in the whole lane.

**Layer:** repository (new batch method) + `instance_lifecycle.py:5107-5120` (loop → dict merge). `get_instance_info`'s single-instance fetch at `:5143` stays as-is (1 rt, not an N+1).

**Why bytes stay identical, field-by-field:** the `children` field of each `InstanceInfo` is the list of `instance_id`s whose `parent_id == row.instance_id`, from the same `instances.parent_id` permanent record (comments at `repository.py:421-428`: includes completed children; NOT the transient `instance_hierarchy` working set). The IN-query selects exactly the same predicate over the same column; same rows, same completeness (children completed AND children on other pages are both included — the IN-set is the PAGE's ids, and children are fetched regardless of their own page membership, exactly as today). No pagination interplay: children were never paginated. The unconditional-children property is preserved (baseline evidence 3: `include_descendants=false` does NOT suppress the fetch; Shape E rejected — consumers include the agent-facing `list_instances` tool at `daemon/tools/instance.py:6165` and the e2e pins).

**C:** wrap the whole `manager.list_instances(...)` call at `daemon/routers/instances.py:476` in the bridge (`instances_data, total, truncated = await run_db(manager.list_instances, …)`). The BFS row-loading (levels loop, `repository.py:1434-1645`) then also runs off-loop WITHOUT any change to its statement sequence — which is precisely why §6 stays frameable and unfixed. The prefs merge at `instances.py:495-496` (`[moved]` dispatch said :496; the comprehension is at `:495`, `prefs_map = …get_all(instance_ids)` follows) may stay on-loop (1 rt IN-query) or ride the bridge; recommendation: leave on-loop to minimize moved code, disclose the 1 residual on-loop rt.

**Projection:** flat(10) 13 rts → ≤6 (count + page + 1 children-batch + 2 prefs), 0 on-loop; BFS(100) 248 rts → ~8 (count + page + 3 level SELECTs + 1 children-batch + 2 prefs), 0 on-loop. p50 59 ms → single-digit ms; 859 ms → ~50–80 ms; the flat badge leg's loaded p95 914 ms (§3) collapses because the loop is no longer held by anyone.

### 2.2 C-2 — `/api/work` (A + C)

**(a) Task-branch batch (Q1-i):** mirror `:1421-1424` exactly at the Task branch: collect `{t.instance_id for t in tasks if t.instance_id is not None}` → `instances_by_id = self._batch_instances(instance_ids)` (helper exists at `work_resolver.py:2368`) → loop passes `instance=instances_by_id.get(t.instance_id)` into `_task_to_record` at `:1397-1404`. Byte-identity: `_task_to_record(task, instance=...)` with the SAME row is provably identical to `_lookup_instance` returning the same row — the helper's docstring (`:1543-1553`) documents this exact pre-fetch contract. Same single-snapshot caveat as §4.

**(b) Orphan-miss closure (decision item D-B — needs explicit plan adoption):** in `_job_to_record`'s fallback (`:1846-1849`), the per-row `self._lookup_instance(job.instance_id)` runs even when the caller already batch-fetched and the miss is AUTHORITATIVE (the batch SELECT `WHERE instance_id IN (...)` proved absence). Mechanism: give the batched call sites a way to mark the miss authoritative — e.g. `_job_to_record(..., instance_missing=instance_ids_batched and j.instance_id in batched_ids)` or pass `instances_by_id` plus a `miss_is_authoritative: bool` — so a batched-miss skips the doomed SELECT and keeps `instance=None`. Equivalence: `_lookup_instance` on a batch-proven-absent id returns None (row does not exist); skipping returns None. Response bytes identical in every non-race execution. **Race disclosure (the one semantic delta):** today, a row committed between the batch statement and the fallback statement WOULD be found by the fallback; after closure it would not (the batch's snapshot becomes authoritative). Each repo call opens its OWN session/transaction today (`with Session(engine)`), so this observation window already exists between batch and fallback; closure narrows it to the batch snapshot. Probability ≈ 0 in practice (an instance deleted then re-created with the same id mid-request); disclose, don't engineer. This single change is what moves the jobs-page/`/api/work` numbers: 92.3% of statement TIME (BASELINE §6) and ~1,250–1,860 singles per request are exactly these doomed lookups.

**(c) Bridge (C):** `work.py:181` `records = resolver.list_work(...)` → `records = await run_db(resolver.list_work, …)`. This is the same call the existing facade already bridges at `job_queue_service.py:1831` — `/api/work` simply calls the resolver directly today and skips the facade; bridging the direct call is the minimal delta (do NOT re-route the router through the service facade; that changes the DI surface for zero benefit).

**Population stays unbounded (no server-side default cap — Q1 spirit):** the endpoint gains no limit; the enrichment population remains "everything matching". The fix removes the PER-ROW cost, not the population. Projection: 1,873 rts → ~6–10 (task SELECT + instance batch + jobs SELECT + instance batch + 3 auxiliary batches), 0 on-loop; p50 8,112 ms → tens of ms. Residual risk: the population itself scales with total work rows (statement count bounded, row transfer unbounded) — that is the FE-poll-shapes follow-up's territory (Q2), not this lane's.

### 2.4 C-4 — Q1 resolver work

**(i)** = §2.2(a). **(ii) limit propagation at `jobs_crud.py:912`:** pass `limit=limit` into `service.list_work(...)` ONLY when the caller explicitly sent one (endpoint signature gains `limit: int | None = None` semantics or a `Request.query_params` check — plan's choice; the ruling forbids a server-side default cap, so "not sent" MUST keep today's unbounded enrichment). `list_work`/`resolve` gain an optional `limit` that applies at the final assembly (SQL LIMIT or slice — plan's choice; byte-order is `created_at DESC`, per the `work.py` docstring "ordered newest first").

**The coverage hazard the plan MUST resolve (decision item D-C):** the enrichment exists to source `work_records_by_id` for the RESPONSE page. The page comes from `service.list_jobs(...)` with its own filters (`job_types`, `mission_id`, `queue_id`, `include_deleted` — several of which are NOT passed to `list_work`, so the enrichment population is deliberately BROADER than the page). ## §3 The architecture question, framed (ARCHITECT-DECIDABLE)

**Option 1 — to_thread bridge on a dedicated executor (this analysis's recommendation).** Sync repositories unchanged; C-class call sites wrapped at the router/service facade; one new `db_bridge` executor (§2.0).
- Correctness risk: LOW — the callable is the unchanged sync function; exception classes and degradation contracts survive; no new driver, no new engine.
- Txn/session semantics: UNCHANGED by construction — every repo call already opens its own short session; F8 (no txn across await) is trivially preserved because nothing is awaited inside a session scope; the bridge callable completes its sessions before returning.
- F4-A interplay: bridge concurrency is bounded by the executor (4 workers ⇒ ≤4 concurrent additional borrowers, inside the 15-capacity envelope with existing headroom); `checkedout()` shapes change (concurrent instead of serial) but the derived-capacity guard (`decisions.md` D-57, refusal only on proven exhaustion) is occupancy-based, not thread-based — no regression path identified; §8 risk 4 carries the watch item.
- Code motion: ~6 site-groups + 1 new module + 2 repo methods. Days, not weeks.
- Rollback risk: LOW — additive wrapper; revert = unwrap call sites.
- vs D-47/R-9 positioning: exactly the "near-term bridge" — async-NATIVE execution stays D-47-gated follow-up territory (decisions.md D-58/R-9: the asyncpg adapter gets a dedicated DSN with `server_settings` knobs under the same enablement gate). This lane does not touch DSNs or drivers.

**Option 2 — async-native (async SQLAlchemy / asyncpg on a dedicated engine + DSN).**
- Correctness risk: HIGH-short-term — ZERO `create_async_engine`/`async_sessionmaker` usage exists in `daemon/` (verified by grep; the only async DB code is the checkpoint saver's psycopg `AsyncConnectionPool` at `persistence.py:316-334` and the asyncpg adapter pool at `:353-362`, neither SQLAlchemy). Repositories are 100% sync; an async layer means either a parallel repo implementation (drift class: two repo truths) or rewriting repositories (blind mass motion). Driver deltas are real: asyncpg has different parameter binding/type mapping and historically requires `text()`-query care vs psycopg3.
- Txn/session semantics: NEW class of hazards (session-per-transaction discipline across awaits re-opens exactly the F8 class the sibling just closed, D-33/D-34); `ConnectionPoolManager`/pool topology must be re-derived; D-47/F4-A/F7 fingerprints all recalibrate (new pool = new census).
- F4-A interplay: a second engine splits occupancy across two pools; the capacity-equality pin and the leak predicate's oracle (P2 saver pool is the LEAK-SIGNAL oracle, sibling C4) would need re-anchoring.
- Code motion: weeks; every touched endpoint needs a parallel test surface.
- Rollback risk: HIGH — engine swap is not unwrap-able.
- Positioning vs D-47/R-9: this IS the D-47-gated end-state, but gated on a trustworthy measurement campaign that does not exist yet; landing it as a side effect of a latency lane inverts the gate's purpose.

**Option 3 — hybrid (recommended): A-batches + C-bridge now; async-native deferred.** Every query-shape improvement of Option 2's eventual win (statement-count collapse) is captured by A; every loop-latency win is captured by C; the deferred async-native lane later lands on FEWER, cleaner call sites (the bridge seams are exactly where an async repo call would slot in, making Option 2's eventual code motion smaller, not wasted).

**Recommendation: Option 3** (mechanically identical to Option 1 for this lane's scope, plus the explicit statement that A-batches are permanent wins an async lane inherits). **Rationale:** byte-identity is a hard gate of this commission; Option 1/3 keeps every response byte-identical with unwrap-able changes, lands inside 3 review cycles, and adds zero new driver/engine classes to a system that just stabilized its pool (v0.27.13). Option 2 wins on the far horizon (native non-blocking IO end-state) but buys nothing for THIS incident class that the bridge doesn't already buy, at ~10–50× the code motion and with a fresh correctness surface. **Assumptions:** the default executor stays shared (A7) — if a future lane makes `asyncio.to_thread` default-executor usage bounded system-wide, the bridge's dedicated pool remains correct; greenlet/asyncpg versions already in-tree (sqlalchemy 2.0.48, asyncpg 0.31.0, greenlet 3.3.2 — `uv.lock` verified) keep the Option-2 door open without new dependencies. **Reversibility:** bridge seams are the async seams — switching later = replacing `run_db(...)` wrappers with awaits; batches carry over untouched.

## §4 Session/txn semantics preservation (per mechanism)

1. **F8 no-txn-across-await (D-33/D-34):** preserved trivially by C — the bridge callable is fully sync; by A — batching happens INSIDE one sync function. The lane must add the static negative: no bridged callable opens a scope it awaits across (pin in the F8-a style: enumerate the bridged callables; sibling precedent F8-a names expected sites so a fourth is a deliberate failure).
2. **Autocommit read-shape equivalence:** every touched read is a short implicit-transaction session today (`with Session(engine)` / `with engine.connect()`); A-batching merges N implicit transactions into ONE statement in ONE implicit transaction. For pure reads under READ COMMITTED the response-equivalence holds (§2.1/§2.2); the ONE narrowed observation window is §2.2(b)'s orphan closure — disclosed above, accepted.
3. **Isolation observations:** (a) children set (C-1): today's children arrive from N snapshots across the request duration; batched = one snapshot ⇒ the returned tree is MORE internally consistent, never less. (b) `/api/work` (C-2): tasks/jobs branches already read in separate snapshots today; batching does not widen any window; D-B narrows one (disclosed). (c) BFS rows (bridged, not restructured): the level-by-level loop keeps its single-session span (`repository.py:1434`) — identical isolation behavior, now off-loop.
4. **Connection-hold duration budget (defer-blocked, the R-1 comment at `queues.py:652-662`):** conn #1 (`engine.connect()` at `defer_block_resolver.py:306`) is held idle-in-transaction-adjacent across the whole WS2 probe loop today, ON the loop. C-3 moves the whole `resolve()` to a bridge thread: duration UNCHANGED (~729 ms wall), pool-occupancy fingerprint UNCHANGED (F7's `xact_age_s` budget and occupancy-returns-to-baseline assertions unaffected), loop UNBLOCKED. The dwell itself remains owned by R-1/R-2 (the routed comment stays true; this lane does not close it — the in-source comment at `:652-662` should be updated by the developer to say "moved off-loop by wi-3f5bea95, dwell still routed" — a comment-only edit, plan item).
5. **Bridging vs pool_timeout:** a bridged request that finds the pool exhausted waits `pool_timeout=30` (D-15) on an executor thread instead of blocking the loop — same outcome for that request (slow/503 per existing shapes), but the loop and every OTHER request stay healthy. This is the incident-class inversion this lane exists to make.
