## 6. The enablement mechanism (D-47 — restated for the implementer)

`MANAGER_ENGINE_IDLE_IN_TXN_TIMEOUT_MS` ships **DEFINED BUT NOT APPLIED**:

1. The constant exists in `daemon/constants.py` with its precedent citation and a **DISABLED** status comment.
2. The rendered connect-args template **OMITS** the `idle_in_transaction_session_timeout` clause while disabled.
3. The boot path logs: `MANAGER_ENGINE_IDLE_IN_TXN_TIMEOUT_MS DISABLED — no trustworthy Phase-0 measurement`.
4. **Enablement** = applied **iff** `BASELINE.md` (or a successor measurement) records a **trustworthy** measurement of the max legitimate hold (the constant is then set from it; the post-F8 re-measurement — F8-b's BASE-vs-HEAD comparison — is the figure to use, DR-11). Enablement is a one-edit change: append the clause to the template with its value taken from the imported constant; the F2 pins already assert the STRUCTURE (clause present ⇒ value == constant; order pinned), so enablement does not rewrite the pin.
5. **Why not applied now (the measured derivation):** the max legitimate hold is model-injected (1059.877 ms — `raw/t1_mr3_hold.py:281-282`) or 114.502 ms un-injected (L3, n=30); 4× = 4.24 s ⇒ the 30 s floor dominates and **coincides with the legitimate `pool_timeout` wait**; the server **TERMINATES** the backend on this timeout (`raw/t2_stat_activity.out:137-140`) — a behavioural change with no measured safety margin.
