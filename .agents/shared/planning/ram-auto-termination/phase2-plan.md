## Objective

Build the `daemon/services/ram_guard/` substrate that answers one question — "how
much RAM is this process tree using **right now**, and what is the **deciding**
value?" — with **no tool wiring at all**, plus the envelope producer, the event
**hook**, the **two guard threads**, and the kill ladder that the bash lane
(Phase 3) and the proc lane (Phase 4) both consume.

**Boundary (discharged from the approver's sweep note):** this phase's objective is
*"no tool wiring at all"*. Two rev-2 tasks straddled that line and are corrected
here — **T9** now owns the substrate-side unit discipline only (the bash-lane
bytes→KB conversion is Phase 3 T10), and **T15** now owns the guard-side release
API + the liveness sweep only (the enumeration of the six bash exit paths is
Phase 3 T8). The **DQ6 consumer-gate artifact** lives here as a **pins-only**
artifact (no tool wiring) and is referenced, never re-derived, downstream.

**Rev 2 said "summed RSS against a ceiling". That is falsified** (arch §1.1 P7,
DQ1): summed RSS over-counts a fork-without-exec tree by ≈ the member count
(**measured 8.9×** on a 9-member tree). The substrate implements the **ruled
hybrid**: a cheap RSS trigger per tick and a **mandatory one-shot PSS confirm**
at breach that is the **deciding** value — with the **bounded** over-count
re-arm (§4.1a).
