# Does the ensemble already have the multi-layer tool idea? — writing-block.md vs our architecture

> Tree caveat: analyzed at `bf4bfde6e`, 678 commits behind `origin/latest` — the live daemon (v0.31.10) is a superset, incl. the `room_*` privileged category (#23) not visible in that tree.

**Headline: PARTIALLY — and where it matters most, we have it in different clothes.** Tier 1 we have **stronger than the doc asks** (frozen, ordering-stable, zero mid-conversation mutation). Tier 3 we have **as registries, but they violate the doc's core requirement** (MCP mutations *do* change model-facing schemas, because every MCP tool is individually bound). Tier 2 is **half-present**: `tool_help` is the doc's `list_tools(category)`; a local `call_tool(name, arguments)` **does not exist** — the only one in the tree dispatches to *remote machines*. The doc's actual motivation (prompt-cache) is, bluntly, **not a problem our tool layer currently has** — our real prefix-busters are four non-tool mechanisms.

## 1 — Tier-by-tier mapping

**(a) Tier-1 semantics — EXISTS, stronger than the doc.** Definitions come from per-agent `meta.json` allow/deny (`daemon/registry.py:109-144`, populated `:701-707`) resolved through a single choke point (`_apply_tool_filter`, `daemon/tools/instance.py:7715`, membership-only `:7840`); construction is `create_instance_tools` (`instance.py:3245`, literal seed `:6634`, ~50 ordered `tools.extend` calls, `tool_help` appended `:7708`) with **only two call sites daemon-wide** — spawn (`daemon/services/instance_lifecycle.py:2144`) and cold restore (`:4846`). Binding is **once per graph build** (`daemon/graph.py:10679`, `:10697-10698` — only 3 real `bind_tools` calls in the daemon) on a cached compiled graph. **Text and order are stable**: deterministic source order (not sorted, not set/dict iteration — **no PYTHONHASHSEED hazard**), docstrings preserved verbatim (`instance.py:2367`); the prompt-cache key itself pins the MCP tool set on the same freeze axis (`daemon/loader.py:1300-1308`). **Mid-conversation mutation: NONE FOUND** — `load_skill` injects content only (`instance_messaging.py:4626-4634`); `ask_questions` is a build-time structural gate (`instance.py:7327`); MCP add/remove invalidates only the *schema* cache, the per-instance tools cache is sticky (`mcp_service.py:736-739`); eviction never touches active instances (`manager.py:7432-7497`). **The one real divergence from the doc:** our tier-1 split criterion is *category + static allow-list*, never *frequency* — no usage signal exists anywhere (`evidence-internal.md:61`, `:65`; per-project narrowing DOES NOT EXIST). The doc's "frequently used direct / rarely used dispatched" split has no input data — which is exactly what ENSEMBLE-37 phase 1 is now measuring.

**(b) Tier-2 generic dispatchers — HALF-PRESENT.** `list_tools(category)` ≈ **`tool_help`** (`daemon/tools/help.py:164-165`): stable, appended last, category-scoped — but it returns *documentation of the agent's own allowed set*, not a discovery catalog of the registry. `call_tool(name, arguments)` — **ABSENT for our own 261-tool surface**: `mcp_rpc_command(tool, arguments)` (`daemon/tools/mcp_rpc_tools.py:255`) is *literally* the doc's shape but dispatches to **remote machines** only (`daemon/services/mcps_gateway/service.py:2367`, `:2490-2495`), forwarding arguments **verbatim** — "THE ARGUMENTS ARE NEVER AUDITED VERBATIM" (`mcp_rpc_tools.py:31`); validation happens remote-side. Permissions *are* server-side, four layers (agent gate `{"ari","leader"}` `:82`; privileged category `_tool_registry.py:470`; gateway kill-switch default OFF `service.py:593`; machine allowlist `service.py:2347-2360`) — so the doc's security line (`writing-block.md:54`) is already satisfied *there*. **MCP tools do NOT ride a dispatcher**: `create_lazy_mcp_tools` mints one `StructuredTool` per remote tool with the remote's **full JSON schema** (`daemon/mcp/tool_adapter.py:520-556`), joined into the model-facing array (`instance.py:7694-7695`). Plugin ports likewise: **one Port = exactly one individually-bound tool** (`plugin_tool_factory.py:201`, `:298-307`); no generic plugin dispatcher (0 hits). Delegation analog exists (`job_create` `job_queue.py:1401-1412`, `spawn_instance(task=, auto_dispatch=)` `instance.py:3320`) but that's mission delegation, not tool dispatch.

**(c) Tier-3 dynamic registries — EXISTS as registries, FAILS the doc's core requirement.** The `mcp_servers` table is a genuine backend registry (`repositories/mcp_server/models.py:15-46`; routers create/update/delete/reset-builtin `routers/mcp_servers.py:764/1099/1191/1253`), with schema-heal (`manager.py:3550-3567`), boot sweep (`:3754-3792`), and quarantine. **But:** a row change is invisible to running instances (frozen array) and lands **only for instances created after the mutation — and for those it DOES alter model-facing schemas**, because each MCP tool is individually bound. "Register without touching model-facing schemas" (`writing-block.md:31-39`) is therefore **not satisfied for MCP**. Plugins are closer: the `od.*` tool set comes from the Python `build_default_port_registry()` (`plugin_tool_factory.py:330-331`), and editing `MANIFEST.yaml` does *not* change the tool array — but that's still code-driven, not runtime-dynamic. The categories/vocabulary machinery (`CATEGORY_MODULES` 64 keys, `_tool_registry.py:1240`; `KNOWN_TOOL_NAMES` 261, `:1650`; `DYNAMIC_TOOL_NAMES` 114, `:26`) is a build-time registry; the vocabulary version is a **metrics constant** (`checkpoint_metrics.py:279`), not model-facing.

## 2 — The cache angle (the doc's motivation)

Tools are serialized into **every** request (bound once at `graph.py:10697-10698`, converted to function-schema once at bind, merged per payload `langchain_openai base.py:1512`); no per-turn tool kwargs at any invoke site (`graph.py:9431`, `:9489`, `:9896`, `:9925`). The (system + tools) prefix is **stable across turns within a graph** 🟢.

**But the blunt finding: the daemon has ZERO provider prompt-cache awareness** — repo-wide grep for `cached_tokens|cache_read_input_tokens|cache_control|prompt_cache_key|CachePoint` → **0 hits in `daemon/`**; the only provider-cache acknowledgement in the tree is a prose aside ("Reloading the persona invalidates provider prompt caches — accepted", `prompt_reload.py:349`). **And the Emperor's cache-affinity invariant (same model → same provider → warm prefix) is NOT recorded anywhere in the ensemble** — not in `evidence-internal.md` §G, not in `report.md`/`decisions.md`. It lives with you and the proxy; the metering authority is explicitly outside the repo (`decisions.md:71`).

**Violations of "static interfaces":** tool-list churn *between turns* — **NONE FOUND** 🟢. Between sessions/rebuilds, two **text**-drift channels only: plugin `od.*` descriptions recomposed at build (`plugin_tool_factory.py:256-262`, deterministic), and `_tool_metadata` overwritten every build (`_tool_registry.py:1219-1232` — affects `tool_help` output only, not the schema array). **The real prefix-busters are four non-tool mechanisms:** (1) 🔴 auto-load skill sweep — a `RemoveMessage` at **position 0** of the persistent block rewrites the head right after the system prompt (`instance_messaging.py:5038-5047`); (2) 95% pre-call compaction rebuilds the message list (`graph.py:9386-9402`); (3) loop-breaker repair rewrites history (`graph.py:9270`); (4) 🔴 **sticky failover** — `swap_to_backup()` mutates `base_url` on the *long-lived* client (`llm_error_classifier.py:674-683`, sticky-on-success `:621-633`): during an outage one invoke is served wholly by a different upstream = provider-side cache miss, unaccounted. (Premise correction: the main turn path uses `FailoverController`, not `invoke_raw_with_failover` — that facade lives at `llm_failover.py:700` and serves skill/memoir/snapshot/OD lanes only.)

## 3 — The tension with R3

The numbers first: the PM measurement is the only token split at the bind point in the tree — **tool schemas were 51,218 of 60,635 tokens (84%) over 223 tools (~230 tokens/tool); post-narrowing 19,933 over 74** (`plane-pm-issue-tools/task3-evidence/fc9_baselines.json:125`, `:159`). So yes — tool schemas dominate, and *any* per-request fixed cost argument is really a tool-array argument. But the two shapes optimize different things:

- **R3 pruning** (per-project *dynamic* narrowing) buys token cost per request and **pays cache-affinity**: a per-project tool list means a per-project prefix → cache re-warm on every project switch — and per-project narrowing **doesn't exist today** (`evidence-internal.md:61`), so the churn risk is prospective, not current.
- **writing-block** (static list + dispatcher) buys **cache-maximality** and pays a hop + degraded ergonomics: the model must *discover* (`list_tools`) then *guess arguments* (`call_tool` with no schema in context) — accuracy cost on exactly the rare tools where the model has least practice.

**They are complementary, and the complement has a precise shape: prune the tail INTO a dispatcher rather than deleting it.** Keep each agent's directly-bound array small and *static per agent* (cache-safe, schema-rich where it matters); route the long tail through a stable generic dispatcher so nothing is *lost*, only one hop away. Our architecture already has every ingredient except the dispatcher itself — and, critically, the usage data to decide *what's tail* is exactly what ENSEMBLE-37 phase 1 is collecting now.

## 4 — VERDICT

**Partially the same idea — and mostly already had, in different clothes.** Tier 1: **have it, stronger** (frozen + ordering-stable + no mid-conversation mutation; the doc's split *criterion* — frequency — is the only thing we lack, for want of usage data). Tier 3: **have the registries but not the property** — MCP is the one place we genuinely violate "register without touching model-facing schemas," because every remote tool is individually schema-bound. Tier 2: **half-have it** — `tool_help` ≈ `list_tools`; **the local `call_tool(name, arguments)` is the one genuinely missing piece**, and it is small: a privileged-gated generic dispatcher over the native registry (the `mcp_rpc_command` pattern, pointed inward instead of at remote machines), which would let per-agent allow-lists shrink without losing access — the cache-safe version of R3.

**Possible commission (named, not adopted — ENSEMBLE-37 stays parked):** one generic `call_tool`/`list_tools` dispatcher over the native tool registry, `mcp_rpc`-style server-side authorization (agent gate + privileged-category strip), default-OFF until ENSEMBLE-37 phase-1 data says which tail belongs behind it. Sequenced strictly **after** that data lands — building it before knowing the tail is a solution seeking a measurement.
