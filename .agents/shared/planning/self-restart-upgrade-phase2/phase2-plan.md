# Phase 2 (P2.2): Agent-Facing Restart & Upgrade Tools

> **⛔ HARD CONSTRAINT (user directive — VERBATIM, applies throughout this phase):**
> NEVER touch the live/production ensemble environment — it is the running environment of Ari and all live agents (~/agents-ensemble, port 9797, prod DB, ENSEMBLE_DEPLOY_LIVE are out of bounds; live pids must remain untouched). ALL work/testing/drills in dev and demo only. If any plan step would require touching live, mark it as USER-GATED and design it as an explicit user-confirmed action. Sandbox instances (own port + throwaway PG) are fine.

**ADR basis:** ADR-015 (agent-facing tooling), extended by deviations #1/#2/#3 (see `plan-overview.md` §6): `system_restart` is NEW; the env-target permission model is NEW; ari-only by default (jober deferred — flagged to user, Q1).

**Prerequisite:** P2.1 shipped (pipeline scripts + journal are the ONLY execution surface these tools may invoke).

## Objective

Ari gains four tools in a new `system_upgrade` category — `system_restart`, `system_upgrade`, `release_info`, `upgrade_status` — [tool count corrected by architect 2026-08-22 per architecture-recommendation.md FA2/A1] that make restart and upgrade conversational while every action routes through the P2.1 deterministic pipeline (health-gated; **never a raw kill**), with a runtime env-target permission model (demo/dev/sandbox free; **live requires runtime user confirmation and is USER-GATED at the execution level by this initiative's own ruling**), daemonized process execution that survives daemon death, and result delivery that works across process death via the journal.

**Exit in one sentence:** in a sandbox/demo, Ari end-to-end performs (a) `system_restart` → daemon restarts via launcher semantics and Ari's next turn observes the completed restart via `release_info`/journal; (b) `system_upgrade` to a staged same-or-newer version → pipeline runs, gate passes or auto-rolls-back, Ari reports the terminal state correctly — with live-target attempts refused at the gate in every test.

## Verified Starting Point (do not re-derive)

- `daemon/tools/upgrade_tools.py` **does NOT exist** (confirmed). Registration requires **all three** steps: (1) `@register_tool_category("system_upgrade")` on the module; (2) `CATEGORY_MODULES` entry (`daemon/tools/_tool_registry.py:423-457`); (3) `tools.allow` expansion resolution (`daemon/tools/instance.py:284-289`) — **plus the known gotcha: the tool must ALSO be appended to the tools list in `create_instance_tools()` or it is silently invisible** (code precedent for the append-to-list pattern: `daemon/tools/instance.py:1895-1993`; category expansion consumers at `:284-289`).
- Ari's `meta.json` allow-list: 14 entries incl. `bash` (jober: 9). `meta.json` lookups must use `get_version()` w/ `get_resolved()` fallback (version-tag resolution convention).
- **No tool survives process death** (all in-process). Bash tool precedent: `BashProcessRegistry` + SIGTERM→5s→SIGKILL teardown (daemon/tools/bash.py:138-150) — meaning a tool-launched child process must be **daemonized** (double-fork + `os.setsid` + `execv`) to survive both the daemon's death and the tool harness's teardown. **Phase-1 lesson: nohup'd children orphan under the tool harness.**
- Restart semantics: tasks stay `PROCESSING` on crash; LangGraph checkpoints at node boundaries; resume `is_retry=True` from `resume_target_turn_id`; `StaleTaskRecovery.recover_on_startup` sweeps stale RUNNING >15 min (daemon/services/stale_task_recovery.py:637-795); `ReportDeliveryRecoveryService` is periodic-only 300s (reports deliver ≤~10 min late after restart); `MessageQueue` is EPHEMERAL (`clear_all(preserve_in_flight=True)` at startup); **a tool call in-flight at stop is LOST (not re-executed)** (pause-tool-result-fix deferred); `has_instance_busy` (task/repository.py:523) canonical busy-check; **deferred-pause pattern** (graph node sets marker, post-graph callback runs OUTSIDE the task identity guard, wrapped in `asyncio.shield()`) is the candidate seam for restart-after-turn-completes.
- User-origin signal: `MessageQueue.type` HUMAN/AGENT/SYSTEM (`daemon/repositories/message_queue/models.py:49`) is the strongest existing origin discriminator; **no trigger-marker mechanism exists** (parent OQ9 open). Question-tool plan has SSE + POST-answer confirmation pattern (NOT implemented).
- ADR-015 gate (inherited): `system_upgrade` requires BOTH `user_confirmed: true` param AND a server-side user-originated trigger marker; LLM never decides go/rollback. R10: an agent could fabricate `user_confirmed` — hence the marker.

## Design Decisions (this phase)

**D1 — Tool set [SUPERSEDED 2026-08-22, reviewer-ratified: the 4-tool set of architecture-recommendation.md D-FA2.1 wins; the original fold rationale below is retained for the record only — ~~`release_info` absorbs status: its result includes current/previous versions, `in_flight` txn, `rollback_window_count`/cap, `cooldown_until`, quarantined list, and the last N `history` events — all journal reads. Justification: a fourth tool doubles the confirmation-gated surface for zero capability gain (the pipeline's journal IS the status); fewer tools = smaller `tools.allow` review surface; ADR-015's two-tool shape is preserved in spirit~~]. Final tool set: `system_restart` + `system_upgrade` + `release_info` + **`upgrade_status`** (separate 4th tool — run-id correlation across process death is the load-bearing feature; fallback clause if ever re-folded: `release_info(section=journal, run_id=...)` MUST carry the run-id filter + journal tail).** `release_info` keeps its full journal/state read surface; `upgrade_status` is the run-scoped poller (§2.4 of `tool-api-design.md`: `run_id` filter, journal tail, phase/terminal states).

**D2 — `system_restart` returns "scheduled", executes post-turn via the deferred seam; the journal + probes carry the result across death.** The tool does NOT restart inline (a restart inline kills the daemon mid-tool-call → the tool result is LOST — verified semantics — and the turn is orphaned). Instead:
1. Tool validates (env-target gate, no in-flight upgrade txn, optional busy-check advisory) and writes a **restart intent** into a durable location the daemon reads at boot: the install dir's journal (`state.json` gains a `pending_restart` marker — P2.1 journal contract extension) **plus** the standard pipeline route: it spawns (daemonized, D4) `scripts/upgrade/restart.sh` which waits for turn completion signal or bounded timeout, then performs stop-ensemble.sh + launcher start.
2. The tool returns immediately: `{"status": "scheduled", "restart_at": "...", "result_how": "next turn: release_info"}`.
3. Ari's NEXT turn (post-restart, instance revived via the standard revive path or session re-entry) reads the outcome via `release_info` (journal `history` `restart` event + `/livez` `uptime_seconds` + `version`).
**Justification vs. inline restart:** inline is observably lossy (tool call lost at stop, verified) and races the tool harness teardown; deferred matches the proven deferred-pause pattern (marker outside identity guard, cascade outside task); journal-read result delivery needs no new messaging machinery and works even if the daemon dies twice. **Trade-off flagged:** the "wait for turn completion" is bounded (e.g. 120s) — if the turn overruns, the restart proceeds anyway (courtesy-not-correctness framing; in-flight turn freezes at node boundary and resumes — safe by Phase-1 semantics).
⟪SEAM: exact post-turn trigger mechanics — ⟫ **[RESOLVED 2026-08-22: **deferred-pause marker + post-graph callback** (`graph.py:3359-3520` precedent, `asyncio.shield`'d, marker pop OUTSIDE the identity guard) fires the daemonized executor at exact turn-end; the restart.sh bounded waiter remains ONLY as the fallback trigger (daemon died before the callback). Additive consumer of the existing post-graph path — e2e full-gate re-assessment avoided IF implementation stays additive (PR-time confirmation required). See architecture-recommendation.md FA1/D-FA1.4.]** The contract stands: tool returns before any stop signal is sent.

**D3 — `system_upgrade` runs the P2.1 promote script daemonized; the tool polls the journal, not the process.** The tool (after gate checks) spawns `scripts/upgrade/promote.sh <env> VERSION=<v>` via double-fork + `os.setsid` + `execv` (D4), writing its own PID into the journal `in_flight.owner_pid`. The tool returns `{"status": "launched", "txn": {...}}` — **it does NOT block on the gate** (the promote takes 3–8+ min: stop+flip+gate+soak 300s). Ari tracks progress by calling `release_info` (journal reads: `in_flight` → `commit`/`rollback`/`halt` terminal events). If the daemon dies mid-promote (e.g. Ari upgrades the daemon it runs on), the daemonized promote **survives**, completes the gate, and the outcome is in the journal for the post-restart turn. The ADR-012 sweep is the backstop if the promote itself dies (T7, P2.1).

**D4 — Daemonized execution spec (both actor tools):** double-fork + `os.setsid()` + `execv` (NOT `subprocess.run` in-process, NOT `nohup` under the tool harness — Phase-1 orphan lesson); child's stdio → install-dir log file (`data/upgrade.log`); child NOT registered in `BashProcessRegistry` (must not be SIGTERM'd at tool teardown); parent (tool) exits after successful spawn; PID recorded in journal.

**D5 — Env-target permission model (orchestration side; enforcement mechanics in sibling `tool-api-design.md`, W2).** Every actor tool takes `target_env: "sandbox" | "demo" | "dev" | "live"`. Rules:
- `sandbox`/`demo`/`dev` → **free per the user directive ("Demo/dev actions may proceed freely per normal flow")** — guarded ONLY by env-derivation (install-dir/port/DB triple) + the self-match rule (D6); **no human-confirmation gate on non-live targets** (the 3-factor gate is LIVE-only — see D6 and ADR-017).
- `live` → requires the 3-factor runtime confirmation (D-FA3.1: `user_confirmed` param + HUMAN-origin marker + action-binding nonce — W2's design) **and remains USER-GATED at execution level by this initiative's ruling** (hard constraint): even with confirmation implemented, this initiative's validation NEVER exercises live; the tool's live branch refuses when the marker/nonce is absent.
- **How Ari asks (orchestration contract):** Ari relays the confirmation request as a normal chat message; the user's reply arrives as a HUMAN-origin message (`MessageQueue.type=HUMAN`, models.py:49) — the strongest existing origin discriminator. The tool call must be issued in a turn **whose trigger message is HUMAN-origin** (interim marker semantics, Q5/OQ9); the full server-side marker design is W2's. **How the answer is verified:** server-side check of the trigger message origin + `user_confirmed: true` param (both required — fabricating the param alone is insufficient, R10 mitigation). **What happens across daemon death:** the confirmation is bound to the *tool-call turn* (journal `in_flight` records `confirmed_by_human: true`); a post-death re-execution of the same txn does not re-ask — the journal is the authority.

**D6 — Gate matrix per tool:**

| Tool | target sandbox/demo/dev | target live |
|---|---|---|
| `release_info` / `upgrade_status` (reads) | free (self-resident target only) | **self-match + U4 per-request approval** — a live-resident Ari may read live under explicit per-request user approval; a demo/dev/sandbox-resident Ari **cannot address live at all** (cross-env read refused `env-self-match` — reviewer ruling 2026-08-22, consistent with `tool-api-design.md` §3.1) |
| `system_restart` | **free (env-derivation + self-match guard only)** — restart is recoverable-by-design via Phase-1 semantics; no human-origin gate on non-live targets (user directive: demo/dev proceed freely) | **refused by this initiative's tools** — live restart is USER-GATED (design: the refusal message points the user to the manual procedure; a future opt-in extends the same 3-factor gate) |
| `system_upgrade` | **free (env-derivation + self-match guard only — user directive: demo/dev proceed freely; journaled + lock-protected like every action)** | **3-factor LIVE gate** (user_confirmed + HUMAN-origin marker + action-binding nonce — D-FA3.1, `tool-api-design.md` §4) — **and USER-GATED: never executed by this initiative; validation asserts REFUSAL paths only** |

**D7 — Auto-rollback + cap surfaced to Ari.** `release_info` returns cap state (`rollback_window_count` vs 3/24h), `cooldown_until`, `quarantined`, and terminal events incl. `sweep_rollback` (ADR-012) and `halt` — so Ari can answer "am I safe to upgrade?" and report "upgrade rolled back, quarantined, cooldown until T" without shell access. On `halt` (cap exhausted), P2.3's alerting fires an SSE notification (NotificationBroadcaster) — the tool surface reports it read-only.

**D8 — Observability contract (what Ari reports back):** every actor-tool result + `release_info` includes: journal `history` tail (events with timestamps), `/livez`+`/readyz` states at call time (via the target port), and for actor tools the txn ID. No raw log streaming (the daemonized child's log lives at `data/upgrade.log` on the install dir — `release_info` exposes its tail as text, bounded, e.g. last 50 lines).

**All objectively verifiable in sandbox/demo:**

1. **Registration:** 4-step checklist test green; Ari exposes exactly `system_restart`+`system_upgrade`+`release_info`+`upgrade_status`; jober/other agents expose none (default-deny).

6. **Packs:** tool unit pack + registration pack green; full e2e suite run IF the seam touched queue/turn code (per `ensure.md:44-53` blast-radius rule — see `test-strategy.md` W3).
