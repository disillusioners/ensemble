# Phase 1 — Watchdog core, triggers, capture pipeline, migration, boot record

Phase objective: build the **instrument itself** — a thread-based watchdog that detects the three wedge
shapes, captures bounded evidence to disk, persists one additive metadata row over its **own** connection, and
records the effective AutoContinue mode per boot epoch. Nothing in this phase is user-visible yet (read-back
lands in Phase 2), and nothing in this phase changes daemon behaviour beyond additive logging.

Authoritative tree: `/home/nea/ensemble-src-wt-wedge-capture` (base `639b7129b`).

---

## 1. Objective

A `threading.Thread(daemon=True)` watchdog, started from the lifespan after `setup_worker_pool()`
(`daemon/api.py:780`) and after the boot passes, that:

1. samples process CPU, per-thread CPU and event-loop lag **once per second** from OUTSIDE the event loop;
2. fires a capture on **any** of three sustained triggers (process CPU, loop lag, thread concentration);
3. writes a bounded, file-first capture directory with **no dependency on the saver pool**;
4. writes one row into a new additive `wedge_captures` table over its **own one-shot connection**;
5. records, per boot epoch, the **effective** AutoContinue mode exactly as the boot pass read it — and
   extends the existing `[BOOT_CONTINUE]` lines with that mode (BC-1).

## 2. Decisions

| ID | Decision | Rationale (cite research file:line / in-tree anchor) | Rejected alternatives |
|----|----------|---------------------------------------------------|------------------------|
| D1 | The watchdog is a **dedicated daemon thread** (`threading.Thread(daemon=True)`), started/stopped from the lifespan. It is **never** a coroutine and never awaits anything. | A starved event loop cannot run a coroutine — that is the entire premise. The house precedent is `ReportDeliveryRecoveryService` (`daemon/services/report_delivery_recovery.py:526-559`: `self._stop_event = threading.Event()`, `threading.Thread(target=self._run_loop, name=..., daemon=True)`, idempotent `start()`) and the resource-monitor sampler (`daemon/services/resource_monitor/sampler.py:294-297`, whose docstring states "**ONE** `threading.Thread(daemon=True)` sampler … NOT an asyncio task"). | (a) An asyncio task + `loop.call_later` — dies with the stall it must observe. (b) A `multiprocessing` supervisor — needs IPC and a separate process lifecycle; far heavier for a 1 Hz sampler. (c) A `signal.setitimer`/SIGALRM handler — signal handlers run on the main thread, which is exactly the thread that may be starved. |
| D2 | **Three independent triggers, all shipped:** sustained process CPU, sustained event-loop lag, sustained single-thread CPU concentration. Any one firing captures. | H1 manifests as CPU peg + loop lag; H2 manifests as lag/stalls **with NO CPU peg** (incident 2026-10-22 07:09–07:45Z, three ~181s stalls). A CPU-only trigger would miss H2 entirely; a lag-only trigger would still catch H1 but with no attribution of the burning thread. | CPU-only (misses H2 — unacceptable); lag-only (loses the H1 discriminator); "one composite score" (unfalsifiable — the instrument must be able to falsify H1, so the signals must be separable). |
| D3 | **Canonical trigger reasons** (shared with the sibling matrix §9): `sustained_cpu`, `sustained_loop_lag`, `thread_concentration` (plus `manual` for an operator drill — see Phase 2 D38). Threshold defaults and sustain windows: **process CPU ≥ 95% of ONE core for 30s**; **event-loop lag ≥ 5.0s for 15s**; **single-thread CPU concentration ≥ 85% of process CPU for 30s**; **sample interval 1.0s**; **cooldown 300s**; **capture deadline 20s**. | CPU 95% of one core: the incident observed **95–107% of ONE core** (not multi-core) across 04:58–05:31Z — the threshold is set just under the observed floor so the shape is caught, not just its extreme tail. 30s sustain: the S1 window was ~33 minutes; a 30s sustain rejects sub-30s compiler/GC bursts. Lag 5.0s: normal loop lag is sub-second; 5s is >5× normal and far below the observed 181s stalls, so the trigger fires early enough to be useful. 15s sustain: shorter than the 30s CPU sustain because a stall that has lasted 15s is already actionable, and the H2 stalls lasted ~30 minutes. Concentration 85%: in H1 the loop thread held essentially the whole process CPU, so 85% separates "one thread is the problem" from "two threads are both busy" without being so tight it misses a 2-thread shape. Cooldown 300s: the incident's 5 boots spanned ~33 minutes ⇒ ~6 windows; 300s keeps ≤1 capture per boot storm without losing episodes. Sample 1.0s: matches the existing resource-monitor sampler cadence (`sampler.py:168` `sample_seconds`), and 1s detects a 5s lag in ≤6 samples. Deadline 20s: a capture must finish long before the operator's 5-minute cooldown elapses, and long enough for a 10s DB connect timeout + file writes. | (a) CPU 100% — the incident's *floor* was 95%, so 100% would MISS the S1 shape. (b) Lag 30s — would miss the 181s stalls' onset (no early capture). (c) Cooldown 60s — would produce ~30 captures across the incident. (d) Sample 0.25s — 4× the `/proc` sweep cost for no detection gain at these thresholds. |
| D4 | **Lag probe mechanics — AMENDED by A1 (binding annex §3 A1).** The watchdog thread schedules a heartbeat on the loop via `loop.call_soon_threadsafe(...)` every sample tick; the callback stamps `time.monotonic()` into a shared float slot. **A1(a) Initial state:** the stamp slot starts **UNSET**; the first tick emits **NO** numeric sample and sets `probe_state="initializing"` — an unset slot is never rendered as a number, never as healthy, and **never evaluated by the trigger**. **A1(b) At-most-one-outstanding:** post `loop.call_soon_threadsafe(probe_cb)` ONLY when no probe is outstanding; slots `outstanding_posted_at: float\|None` and `last_exec_at: float\|None`; `probe_cb` (on the loop) clears `outstanding_posted_at` and sets `last_exec_at = monotonic()`. At tick T: if `outstanding_posted_at is not None` → `lag_s = T − outstanding_posted_at` (true lower bound of loop delay); else post, set `outstanding_posted_at = T`, and sample `lag_s = T − last_exec_at`. **One-post-per-tick is REJECTED** (unbounded ready-queue growth during a wedge, burst-on-unblock, racy peak — AC4 is not reliably satisfiable under it; RK-21). **A1(c) Never-fired = a SAMPLE, not a skip:** a tick with no loop execution yields a sample valued at the elapsed time since the last observed execution — never skipped, never 0. A fully starved loop yields a monotonically growing series and the sustain window **accumulates** across it. **A1(d) Histogram:** `lag.json` carries `samples / max / p95 / p50 / overflow_count / loop_unresponsive_s` (the current outstanding duration at capture) with an explicit top/overflow bucket — values are **CLAMPED into it, never dropped**. **A1(e) Degraded/stopped:** `manager._loop is None` or `loop.is_closed()` → `unknown` / `stopped`, never a number, never a crash; `call_soon_threadsafe` raising `RuntimeError("Event loop is closed")` → mark the probe `stopped`, stop posting, and **do NOT inflate `missed_samples`**. **A1(f)** `watchdog_tick_delay_s` stays a secondary GIL-contention signal, **never a trigger input**. | The loop reference is captured from the running process (`manager._loop`, set at `daemon/manager.py:3357` inside `InstanceManager.initialize()` — def `:3336` — which `daemon/api.py:727` awaits). A1's mechanics exist because a naive "skip when no callback ran" implementation would **silently disable the lag trigger on a fully starved loop — the exact H2 shape** (RK-16). The "never-fired = a sample" rule is what makes the H2 shape detectable at all. | (a) Measure the watchdog's own tick delay — that measures **GIL contention**, not event-loop lag; recorded as a *secondary* signal, never a trigger input. (b) `loop.time()` polling from the thread — same GIL dependency, no better. (c) A `run_in_executor` heartbeat — consumes a pool worker that the stall may itself be starving. (d) One post per tick — unbounded ready-queue growth during a wedge (RK-21). |
| D4b | **NEW (A1): the sustain test is WALL-TIME.** The sustain test = elapsed wall time from the first to the last consecutive at/above-threshold sample ≥ `sustain_s`. | Behaviour is then **identical at 1 s or 5 s tick cadence**, and the fully starved case fires **deterministically** (the series grows monotonically, so the elapsed time between the first and last over-threshold sample is well-defined even when the loop never executes). A sample-count-based sustain would fire early at a fast cadence and late at a slow one — and would be wrong precisely in the starved case. | (a) Sample-count sustain — cadence-dependent, and wrong in the starved case. (b) A sliding-window mean — a single spike would be averaged away, hiding the H2 shape. |
| D5 | **CPU measurement** uses `/proc/self/stat` (process `utime+stime`) and `/proc/self/task/<tid>/stat` (per-thread `utime+stime`) **deltas** between consecutive ticks, normalised to "percent of ONE core" (i.e. the value may exceed 100). | The tree already reads `/proc` + cgroup v2 (`daemon/services/resource_monitor/proc_readers.py:209` `read_cgroup_snapshot`, `:284` `_read_proc_stat`, `:245` `_parse_proc_stat`, `:338` `read_daemon_snapshot`). Per-core normalisation (not "percent of all cores") is required because the incident metric was "95–107% of ONE core". | `os.times()` (process-only, no per-thread breakdown — fails the H1 attribution requirement); `psutil` (not a dependency — `pyproject.toml` has no psutil). |
| D6 | **Thread attribution** maps OS tid → Python thread via `threading.get_native_id()`, with the raw `/proc/self/task/<tid>/comm` name recorded for **every** thread so the mapping is auditable even if the assumption is wrong. | `threading.get_native_id()` is documented (3.8+) to return the OS thread id on Linux. **This tree has ZERO precedent for `native_id`** (E1/E2 flagged it) — hence the comm-name column is mandatory, not optional: if the mapping is wrong, the capture still names the burning thread by `comm` (`MainLoopBridge` / `WedgeCaptureWatchdog` / `ReportDeliveryRecoveryService` / `psycopg` worker names). | (a) `threading.enumerate()` + `thread.name` only — cannot attribute CPU (no per-thread times). (b) `faulthandler`'s per-thread frame dump as the attribution source — it gives stacks, not CPU. |
| D7 | **Thread-concentration definition — AMENDED by F-06 (an ABSOLUTE-CPU floor gates the ratio).** One OS thread accounts for ≥ 85% of the process's CPU over the sustain window, measured as `thread_cpu_delta / process_cpu_delta` (a ratio, not an absolute) — **but the ratio is evaluated ONLY when `process_cpu_delta` ≥ 5% of ONE core over the window** (the absolute floor). Below that floor the trigger **does not fire** (the ratio is trivially ≈1.0 for a near-idle process — e.g. a single short-lived helper thread — so an unfloored ratio manufactures false positives on a quiet daemon). | A ratio is robust on an N-core host: it says "the work is concentrated", which is the H1 claim, independent of core count. The absolute 85% line mirrors the process-level CPU threshold. **The 5% floor** is the fix for the degenerate case: below it there is not enough CPU for concentration to mean anything, and the trigger must stay silent (the CPU trigger at 95% remains the signal for a genuinely busy process). | Absolute per-thread CPU (breaks on multi-core hosts where the process may legitimately spread work); "top thread > 50%" (too loose — normal background work can reach 50% on a quiet daemon); an unfloored ratio (F-06 — trivially true on a near-idle process). |
