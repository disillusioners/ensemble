# Phase 2: Secondary Fix — `_prepare_enqueued_message` Race Guard (Marker-Only)

## Objective

Close the deferred-pause race window for **Paths 1 and 5** (user/sibling messages arriving during `_deferred_question_pause`). Add a source-side Task-creation guard at `daemon/services/instance_messaging._prepare_enqueued_message:1070` that uses **marker-only logic** (NOT the dual check used in Phase 1):

- **Marker set (in-window race case)**: skip the `Task(task_type=PROCESS_MESSAGE)` row. The `MessageQueue` row (lines 1187-1199) is still created (so the message is the durable input). **Caveat: the user message in the in-window case is NOT delivered on resume** (see "Verified Delivery Path" below). Log a `WARNING` and reference the follow-up.
- **Marker empty + DB==PAUSED (post-cascade case)**: STILL create the PENDING `Task`. The existing `claim_pending_task` SQL pause gate (`daemon/repositories/task/repository.py:646-671`, `WHERE instance_id NOT IN (SELECT instance_id FROM instances WHERE status IN (paused, terminated))`) defers the claim until resume. **Message IS delivered on resume.**
- **Marker empty + DB==RUNNING (normal case)**: create the `Task` as today. WorkerPool claims it normally.

## Context

- The race window: same as Phase 1. The in-memory marker is set synchronously by `question_pause_node` (`daemon/graph.py:3160`); the DB row still shows `RUNNING` until `_pause_cascade_db_sync` commits.
- During this window, a user message (Path 1) or sibling message (Path 5) calls `enqueue_message`, which calls `_prepare_enqueued_message` (via `asyncio.to_thread` at `daemon/services/instance_messaging.py:1390`). Currently this method unconditionally creates a `Task(task_type=PROCESS_MESSAGE, status=PENDING)` at line 1211. The WorkerPool claims this Task and drives a graph turn on the (about-to-be-paused) instance. **This is the bug.**
- **Function signature check**: `_prepare_enqueued_message` is a **synchronous `def`** at line 1070. The function already has a `session` (a `WriteGuardSession`) open via `with WriteGuardSession(Session(self._manager.engine), self._manager.write_guard) as session:` at line 1185 and uses `session.get(Instance, instance_id)` at line 1253 to handle the existing status-flip branch. **The fix uses the same `session` to read the instance's status synchronously** — `await asyncio.to_thread(...)` would be a `SyntaxError` in a sync function. (The original sketch used `asyncio.to_thread`; that was wrong and is corrected here.)
- **The fix is to check the in-memory marker BEFORE creating the Task**:
  - If marker is set (in-window race case): skip Task creation. The `MessageQueue` row is preserved (durable input). The `Task` is the dispatch primitive — skipping it is what avoids the spurious worker claim.
  - If marker is empty: read DB status (defensive, for the post-cascade case). If DB is PAUSED, STILL create the Task (the existing `claim_pending_task` SQL gate defers it). If DB is RUNNING, create the Task normally.

- **Open question #2 resolution (the design decision for this phase)**: the check gates ONLY the `Task` insert, NOT the `MessageQueue` insert. Justification: the `MessageQueue` row is the durable record of "user wanted to send this message" and must be preserved (it is the source of truth for message content + ordering + READY status). The `Task` is the dispatch primitive — skipping it is what avoids the spurious worker claim. On resume, the resume flow re-creates the Task (via `enqueue_message` from the child-resume path, or via `_resume_processing_background` from the root-resume path which bypasses `enqueue_message` entirely). The `MessageQueue` row's READY status is processed normally on the next claim **when the Task is created (post-cascade case)**. The orphan-MessageQueue risk for the in-window case is a known limitation (see "Verified Delivery Path" below).

- **Why marker-only (NOT dual check like Phase 1)**: see plan-overview.md "Why the asymmetry". The key difference is that `ReportInjection` has a verified drain path on every LLM call (`daemon/graph.py:2566-2590`), so Phase 1 can skip the Task and rely on the report-injection row. `MessageQueue` rows in READY status have NO equivalent drain path:
  - The resume cleanup at `daemon/manager.py:4937-4940` filters to `[PENDING, PROCESSING, RETRYING]` only — READY is excluded.
  - No code path drains a skipped READY row on resume.
  - Root resume (`manager.py:5077-5093`) bypasses `enqueue_message` entirely and passes the answer straight to `_process_message_with_tracking` (line 5155) with a fresh `message` parameter.
  - Child resume (`manager.py:4895`) calls `enqueue_message` with a fresh `message_id` UUID; the old skipped row is never claimed.

- **Why the post-cascade case uses the existing SQL gate** (the marker-only design choice): when marker is empty + DB==PAUSED, creating the Task is safe because the existing `claim_pending_task` SQL gate at `task/repository.py:646-671` (the pause gate `instance_id NOT IN (SELECT instance_id FROM instances WHERE status IN (paused, terminated))`) will exclude the instance from any claim. When the user resumes, the cascade flips DB to RUNNING, and the Task becomes claimable. **Message is delivered.** This is the current behavior pre-fix, preserved by Phase 2.

- **Verified Delivery Path Analysis (BLOCKING Issue #2 from the original review)**:

  - **Normal case (marker empty, DB==RUNNING)**: Task created → claimed → message processed. ✅
  - **Post-cascade case (marker empty, DB==PAUSED)**: Task created → SQL gate defers claim until resume → on resume, cascade flips DB to RUNNING → Task claimed → message processed via `_process_message_with_tracking`. ✅ **Message delivered.**
  - **In-window case (marker set, DB==RUNNING, Task SKIPPED)**:
    - The MessageQueue row is in READY status with no Task.
    - On resume:
      - The resume cleanup at `manager.py:4937-4940` filters to `[PENDING, PROCESSING, RETRYING]` only — READY is **excluded**. No drain.
      - Root resume (`manager.py:5077-5093`) bypasses `enqueue_message` entirely and passes the **answer** (a fresh `message` parameter) to `_process_message_with_tracking` (line 5155). The skipped MessageQueue row is **NOT** consulted; it is a stale/audit row.
      - Child resume (`manager.py:4895`) calls `enqueue_message` with a fresh `message=message` parameter — the resume message, NOT the skipped MessageQueue row's content. A new MessageQueue row is minted with a fresh UUID; the old skipped row is never claimed.
    - **VERDICT**: the in-window skip DOES lose the user message in the skipped READY MessageQueue row. The race window is narrow (~10-100ms), so the probability is low. This is a **known limitation** of the in-window skip. The fix prevents the worse bug (spurious turn on a paused instance) at the cost of a rare message loss in the narrow race window.
  - **Recommended follow-up** (out of scope for this plan): materialize the in-memory `_deferred_question_pause` marker to a DB column (e.g., `instances.pause_pending BOOL`) so the existing `claim_pending_task` SQL gate can check it. This would close the in-window race for Phase 2 without losing any messages, by allowing the Task to be created and the SQL gate to defer it. Mirrors the approach already documented as a future work item in the technical analysis (see "Technical Debt" section). The same materialization is also the future fix for the multi-node concern. The fix site must log a `WARNING` on in-window skip and reference the follow-up.

- **Path 5 (sibling message) coverage**:
  - The marker is on the ROOT instance (the one whose `question_pause_node` fired), not on the sibling. For the sibling, the marker check sees an empty set → does NOT skip.
  - The DB check sees the sibling's DB status. If the cascade has committed (DB==PAUSED), the Task is created but the SQL gate defers. If the cascade has NOT yet committed (in-flight), the DB check sees RUNNING → Task is created → SQL gate admits → spurious turn.
  - **This is a known partial-coverage case** — Path 5 in-flight is not fully covered. The fix catches the post-cascade case; the in-flight case for the sibling is residual. Flag for future tightening (e.g., cascade pre-flags all tree members in the marker set, not just the root, or materializes the marker to DB so the SQL gate can check it).

- **Why the post-cascade skip is safe (Phase 2)**: the existing `claim_pending_task` SQL gate (`daemon/repositories/task/repository.py:646-671`) excludes PAUSED/TERMINATED instances. The Task is created in the same transaction as the MessageQueue row. On resume, the cascade flips DB to RUNNING, the Task becomes claimable, and the message is processed normally. The resume cleanup's ANTIPHANTOM-RACE-FIX at `manager.py:4949-4995` re-arms PENDING tasks for claim after the cascade.

- **Reference fix sketch**: this phase adapts Phase 1's `session.get(Instance, ...)` pattern to the `_prepare_enqueued_message` call site. The pattern is identical (synchronous `session.get` on the existing `WriteGuardSession`); the guard logic is marker-only.

## Risks (phase-specific)

- **In-window message-loss (Q5 / Risk #6)**: a user message that arrives during the race window is lost because the Task is skipped and the MessageQueue row is in READY status (no drain path). This is a known limitation, accepted because the race window is narrow (~10-100ms) and the fix prevents the worse bug (spurious turn on a paused instance). The integration test (Task 5) verifies the post-cascade case delivers the message; the in-window case is documented in the code comment. The follow-up materialization is the watertight fix. **Log a `WARNING` (not just INFO) on in-window skip to surface this to operators.**
- **False-positive on legitimate child-resume path**: when `enqueue_message` is called from the child-resume path (`daemon/manager.py:4866-4911`), the marker is empty AND the DB is RUNNING. Both branches admit normally. The no-false-positive test (Task 7) catches any future regression. Additionally, the root-resume path bypasses `enqueue_message` entirely (`daemon/manager.py:5077-5093` → `_resume_processing_background`), so the fix is structurally not on the root-resume path — the strongest form of safety.
- **Sibling-tree edge case (Path 5)**: the marker is set on the ROOT instance (the one whose `question_pause_node` fired), not on the sibling. For the sibling, the marker check is empty (does NOT skip). The DB check sees the sibling's status; if the cascade has committed (DB==PAUSED), the Task is created and the SQL gate defers (message delivered). If the cascade has NOT yet committed for the sibling (in-flight), the DB check sees RUNNING → Task is created → SQL gate admits → spurious turn. **This is a known partial-coverage residual risk** — Path 5 in-flight is not fully covered. The fix catches the post-cascade case; the in-flight case for the sibling is residual. Flag for future tightening (e.g., cascade pre-flags all tree members in the marker set, or materialize the marker to DB).
- **Dual-driver compatibility**: same as Phase 1. The DB read uses `session.get(Instance, ...)` (existing pattern, dual-driver). No new SQL.
- **DB check adds an extra read per enqueue_message (Task 1)**: per `enqueue_message` call, one extra `session.get(Instance, ...)` on the PK. ~sub-ms. Negligible. The DB read is gated by the marker check (fast path), so the slow path is only hit when the marker is empty.
- **Pattern drift from Phase 1**: a future change to Phase 1's check (e.g., switching Phase 2 to dual check, or vice versa) could create pattern inconsistency. Code review will catch this; the asymmetric design is the central architectural decision. The two fixes should be **visually similar in idiom (same `session.get` pattern) but explicitly different in guard logic (dual vs marker-only)**.
- **Race-window test reliability (Task 6)**: the controlled-delay test depends on monkeypatching the cascade. The monkeypatch must be safe (no thread-leak, no event-loop interference). Use `unittest.mock.patch` with explicit teardown.
