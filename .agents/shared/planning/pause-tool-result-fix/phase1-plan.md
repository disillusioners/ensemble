# Phase 1: Primary Fix — `child_reports` Race Guard (Dual Check)

## Objective

Close the deferred-pause race window for the **canonical** case (Path 2: child completion during `_deferred_question_pause`). Add a source-side Task-creation guard at `daemon/services/child_reports._process_child_completion_db_sync:1158` that skips creating the `PROCESS_REPORT` Task when the parent is in the in-memory `_deferred_question_pause` set OR has DB `instances.status == PAUSED`. The `MessageQueue` row (lines 1879-1889) and the `ReportInjection` row (lines 1927-1934) remain UNCHANGED — the `ReportInjection` row is the durable fallback delivery path, drained on the parent's first post-resume LLM call via `claim_for_injection` (`daemon/repositories/report_injection/repository.py:162-260`, called from `daemon/graph.py:2566-2590` pre-LLM message prep). Add regression tests for Path 2 AND the **CRITICAL** no-false-positive test for the legitimate resume flow.

- **Independent of**: `pause-resume-redesign` plan (different files, different surface). If the redesign lands later, this fix's marker check will be replaced with a DB-backed `instances.pause_pending` column check; the dual-check pattern remains valid.

## Context

- The race window: between `set_deferred_question_pause(parent_id)` (in `question_pause_node`, `daemon/graph.py:3160`) and `_pause_cascade_db_sync` commit (in `pause_instance_cascade`, dispatched via `asyncio.to_thread` at `daemon/services/instance_lifecycle.py:1805-1812`). Observed window: 10-100ms under normal load; potentially longer under PG lock contention.
- During this window, the in-memory `_deferred_question_pause` set contains the `parent_id`, but the DB row for the parent still shows `status='running'`.
- A child completion during this window calls `_process_child_completion_db_sync` (Path 2). Currently this method unconditionally creates a `Task(task_type=PROCESS_REPORT, status=PENDING)` at line 1893. The WorkerPool's `notify_work()` (lines 2344-2352) wakes a worker, the worker claims this Task via `claim_pending_task`, and the SQL gate (which reads DB and sees `status='running'`) admits it. The worker then drives a full graph turn on the parent via `_process_message_with_tracking` → `graph.astream`. **This is the bug** — a paused instance has just resumed running.
- **Function signature check**: `_process_child_completion_db_sync` is a **synchronous `def`** at line 1158, running on a worker thread via `asyncio.to_thread` from the async caller `_process_child_completion_and_notify_parent:1026`. The function already has a `session` (a `WriteGuardSession`) open via `with WriteGuardSession(Session(self._manager.engine), self._manager.write_guard) as session:` at line 1193 and uses `session.get(Instance, instance_id)` at line 1195 to read the child instance row, plus `session.get(Instance, instance.parent_id)` at line 1938 to update the parent. **The fix uses the same `session` to read the parent's status synchronously** — `await asyncio.to_thread(...)` would be a `SyntaxError` in a sync function. (The original sketch used `asyncio.to_thread`; that was wrong and is corrected here.)
- The fix is to check the parent's pause state BEFORE creating the Task. If paused (marker OR DB), skip Task creation. The `MessageQueue` row (lines 1879-1889) is the audit / handoff record; the `ReportInjection` row (lines 1927-1934) is the durable fallback — it is drained on the parent's first post-resume LLM call.
- **Why the dual check**: the marker check catches the race window (synchronous, in-memory, set before the cascade starts). The DB check catches the user-click-stop case (Path 4) where the marker is NOT set (the cascade runs directly from `routers/instances.py:543`, bypassing `question_pause_node`) but the DB may already say PAUSED. Both checks are needed for full coverage.
- **Why the skip is safe** (Phase 1 specifically): the existing `ReportInjection` row's exactly-once delivery is enforced by `claim_for_injection`'s atomic `UPDATE … RETURNING` (`daemon/repositories/report_injection/repository.py:216-260`). The live `ReportInjectionSlot` drain fires before EVERY LLM call on the parent's first post-resume turn (the `report_injection_slot.drain(instance_id)` call at `daemon/graph.py:2566-2590`). No report is lost.
- **Residual risk (orphaned ReportInjection)**: if the parent is TERMINATED while a PENDING ReportInjection row exists, the row stays forever (no cleanup). The fix site must add a code comment documenting this and reference the follow-up `reconcile_terminal_report_injections` cleanup. Likelihood: Medium.

## Risks (phase-specific)

- **Test fragility (Tasks 4, 5, 6, 7)**: the synchronous `session.get` in the dual check requires a valid engine. Tests must set up an in-memory SQLite engine (existing pattern, see `tests/conftest.py`). PostgreSQL tests should use a test schema or transaction-rollback fixture.
- **False-positive regression (Task 6 is the safety net)**: a future change to `_deferred_question_pause` (e.g., changing it from a `set` to a `dict` with timestamps) could break the marker check. The end-to-end no-false-positive test (Task 6) catches this by exercising the actual resume flow.
- **Dual-driver compatibility**: the DB read uses `session.get(Instance, ...)` (existing pattern, dual-driver). No new SQL. Tests must run on BOTH SQLite and PostgreSQL (project critical note).
- **DB check adds an extra read per child completion (Task 1)**: per child completion, one extra `session.get(Instance, ...)` on the PK. ~sub-ms. Negligible. The DB read is gated by the marker check (fast path), so the slow path is only hit when the marker is empty (i.e., not in a question-pause flow).
- **Structured log line format (Task 3)**: ensure the format is consistent with Phase 2's log line so a future log-aggregator query can correlate. Use a `skip_reason` enum-like value (`marker` / `db_status`).
- **Comment block drift (Task 2)**: the comment block must stay in sync with Phase 2's comment block (asymmetric design noted in both). Code review will catch drift; add a cross-reference in both directions.
- **Race-window test reliability (Task 7)**: the controlled-delay test depends on monkeypatching the cascade. The monkeypatch must be safe (no thread-leak, no event-loop interference). Use `unittest.mock.patch` with explicit teardown.
