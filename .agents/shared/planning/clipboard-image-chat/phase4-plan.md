## Objective

Make the chat composer accept **pasted clipboard images** alongside the existing picker and drag-drop paths, and switch the send pipeline from inline-base64 transport to a **two-stage upload-first** flow: every attached image is POSTed to a new daemon endpoint, the daemon returns a stable server-side URL ref, and only then does the FE POST `/messages` carrying the refs (not data URIs). All three web inputs (paste + picker + drag-drop) route through the same `processFiles` sink and the same upload-then-send pipeline so the UX is uniform and the agent-facing payload is text-only after the image-reader conversion (per design direction).

## Scope

### In Scope

1. **Paste handler on the composer textarea** — `(paste)` binding on `<textarea>` in `message-input.html`; new `onPaste(event: ClipboardEvent)` method on `MessageInputComponent` that walks `event.clipboardData.items`, filters to `kind === 'file'` with a MIME in the existing `ACCEPTED_TYPES` allowlist, and routes the resulting `File[]` through the existing `processFiles()` sink so the preview-strip, MAX_IMAGES=3 cap, MAX_IMAGE_SIZE=10MiB cap, and per-file validation messages are shared with picker/drag-drop. **Text-only pastes MUST pass through untouched** (no `preventDefault()` when no images are present).
2. **Upload-first send pipeline** — new `ImageUploadService` (or `ApiService.uploadImages()` method) that POSTs each `File` (already base64-decoded from the FilePreview's `dataUrl`) to the new daemon endpoint as JSON `{images:[{filename, content_type, data_base64}]}` (canonical §2 batch-of-1 envelope; per decisions.md §2 / architecture-recommendation.md round-2 C1/C3), receives `{uploads:[{image_id, ref_url, content_type, size_bytes}]}` back, unwraps `uploads[0]`, and stitches the refs into `MessagePayload.image_refs`. The composer tracks per-image upload state (uploading / uploaded / failed) and renders the chip state on the FilePreview strip.
3. **Async `handleSubmit`** — refactor `MessageInputComponent.handleSubmit()` (`message-input.component.ts:248-260`) so it awaits the per-image upload(s) for every preview that does not yet have a `refUrl`, populates `payload.image_refs` with the refs (NOT data URIs), then emits `sendMessage`. The chat component's downstream `api.sendMessage(...)` (currently at `chat.component.ts:1372` and `api.service.ts:307-328`) carries the new sibling field: `image_refs` for ref-sends (the SEND leg), `images` for legacy data-URI sends (XOR guaranteed — see Out of Scope note below). The READ-side `message.images` shape is unchanged (the daemon unions refs into wire `images` via `serialize_message` per architect round-2 C1 ruling (b) / amendment #29). Backend `MessageCreate` does NOT need its legacy `images` validator relaxed — the new `image_refs` sibling field has its own validator (XOR with `images`); that is the coupling owned by backend phase 2.
4. **Uniform preview-strip rendering** — `message-input.html:18-38` keeps using `<img [src]="img.dataUrl" ...>` (local preview only); the chip gains a small status pill: ⏳ while uploading, ✓ once `refUrl` is bound, ⚠ on failure with retry. The send button (`message-input.html:94-123`) is `disabled` while any upload is in-flight AND keeps the existing `canSend()` invariant (text OR images present AND not disabled).
5. **Failure modes** — upload-time error per image; choice between **block-send** (refuse the POST if any preview has no `refUrl`) and **send-without-image** (drop failed images, warn inline, continue). Plan adopts **block-send by default** for the URL-ref form because a chat message without its visual reference is a UX regression; document the alternative in Risks. **Block-send default scope is single-user-single-tab** (architect amendment #18) — it is the FE-side mitigation boundary for the phase-2 ordering-inversion accepted-risk; cross-source interleaving (e.g. a Discord message to the same instance) and multi-tab BOTH bypass this mitigation. See Risks row #8 for the full scope pin and the cross-reference to phase 2's ordering-inversion risk row.
6. **Optimistic thumbnail during conversion latency** — `makeProvisionalMessage` (`message-merge.util.ts:84-100`) already forwards `images` through the provisional bubble; under the new pipeline the optimistic bubble renders the `refUrl` immediately so the user sees the thumbnail in their outgoing message list the moment the POST returns, well before the image-reader finishes the text conversion.
7. **Coexistence knob for the web source** — design direction flags "full switch vs coexistence knob for web source" as open for architect. Plan implements the **full switch** (paste/picker/drag-drop all produce refs; the data-URI inline transport is retired from the web path) and explicitly notes the coexistence-knob delta in Risks so the architect can pick.

### Out of Scope

- **Server-side image storage, 30-day cleanup, conversion-to-text agent** — owned by backend phases 1-3. This phase consumes the upload endpoint contract and the ref shape; it does NOT define them.
- **CLI/Telegram/Slack/Discord/chat-source image flows** — only the web (browser) input surface is in scope. Other sources continue to use whatever transport they already use (e.g. the chat-source worker-lane packages images inline per existing chat-source handling).
- **SSE-side whitelist widening** for the new ref form — owned by phase 5. Phase 4 emits ref URLs; phase 5 ensures they survive the live leg.
- **Click-to-popup image viewer** — phase 6.
- **`MessageCreate.images` legacy validator** — UNTOUCHED per decisions.md §2 / round-2 C1 ruling (a). The legacy `data:image/...;base64,...` regex at `daemon/models/message.py:13` is preserved verbatim; the new `image_refs` sibling field carries its own validator (XOR with `images`); relaxing the legacy regex is REJECTED (R8 exposure: a relaxed data-URI regex would lex-accept Discord HTTPS URLs via `adapter.py:1105`). The FE never sends data URIs after this phase, but the contract-level coexistence is preserved indefinitely.
- **`api.service.ts` `sendMessage` signature change** — the method stays backward-compatible; we only add an optional `image_refs?: string[]` parameter (sibling of `images`). XOR is enforced at the Pydantic layer (phase 2 Task 3) — the FE may omit `image_refs` on text-only sends and omit `images` on ref-sends but never carries both.
