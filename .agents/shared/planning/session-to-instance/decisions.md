# Architecture Decisions: Session → Instance Rename

## Decision 1: Migration Strategy
**Decision**: Create a NEW SQL migration file; do NOT modify the initial schema migration.

**Rationale**: 
- The initial schema migration represents historical truth for existing databases
- Modifying it would break any database that was created from the original migration
- A new migration provides a clean upgrade path for existing deployments
- Fresh installs will get the new schema from the ORM models (Phase 1), but the migration ensures existing data is properly renamed

**Alternative Considered**: Modify initial migration + rebase. Rejected because it breaks existing databases.

## Decision 2: Phase Ordering — Bottom-Up
**Decision**: Rename from leaf dependencies (models) up to consumers (API, frontend, tests).

**Rationale**:
- Models are imported by everything else — rename first to establish new names
- Repository layer wraps models — rename second
- Core daemon imports from both — rename third
- API and frontend are the outermost layers — rename last
- Tests validate everything — must be last

**Alternative Considered**: Top-down (API first). Rejected because import errors would cascade unpredictably.

## Decision 3: Accept Broken Intermediate States
**Decision**: Accept that Phases 1-5 will intentionally break imports in downstream files.

**Rationale**:
- It's impossible to atomically rename across 65+ files
- Following the dependency order means breakage is predictable and contained
- Each phase explicitly states which files will break and which phase fixes them
- The codebase compiles cleanly again after Phase 6

**Mitigation**: Each phase includes explicit verification steps. The coder should NOT run the full test suite until Phase 10.

## Decision 4: db_path Filename Change
**Decision**: Rename `sessions.db` → `instances.db` in config.yaml.

**Risk**: Existing deployments will need to manually rename their database file OR the migration script should handle this.

**Mitigation**: Document this in the migration README. Consider having the application check for the old filename and auto-rename on startup (optional enhancement, not part of this refactor).

## Decision 5: Enum Values Unchanged
**Decision**: Keep enum VALUES (IDLE, RUNNING, COMPLETED, etc.) unchanged. Only rename enum TYPE names and string values that contain "session".

**Rationale**: The enum values represent states, not session-specific concepts. An "idle" instance is the same concept as an "idle" session.

## Decision 6: Tool Name `send_message` Unchanged
**Decision**: The `send_message` tool keeps its name — it's a generic messaging concept.

**Rationale**: Sending a message isn't session-specific. The function name doesn't contain "session". Only the parameter types change (session_id→instance_id).

## Decision 7: Job System session_id IS the Agent Instance ID
**Decision**: Rename `session_id` in the job system (job_queue_service, job_lock_manager, job_processor) to `instance_id`. Do NOT introduce a separate "execution_id" concept.

**Rationale**: Investigation revealed that the `session_id = str(uuid.uuid4())` generated by `job_queue_service.py` flows directly into `SessionManager.spawn_session(session_id=...)` and becomes the agent's actual session ID. They are the SAME value, not different concepts. Therefore, all `session_id` references in the job processing pipeline must be renamed to `instance_id` consistently.

**Evidence**: `job_processor.py` line 117-121: `session_id = self._session_manager.spawn_session(agent_id=..., session_id=started_job.session_id)`. The UUID generated for the job IS used as the agent's ID.
