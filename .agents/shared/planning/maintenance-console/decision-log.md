## AM-2 rationale — Why manual composes Op E → Op D (and auto stays D → E)

The auto-cycle's order is Op D → Op E (`maintenance.py:437-480`): first delete excess checkpoint rows, then prune blobs no longer referenced. Reusing that order in the manual execute path **deadlocks the primary operator flow**. The reason is the dry-run's accounting semantics. `prune_unreferenced_blobs` (`checkpoint_prune.py:12-17`) counts blobs via an anti-join: **a blob is counted as "referenced" if ANY current checkpoint row holds its reference**. The dry-run performs that anti-join and reports the byte count the operator echoes back to execute. With excess checkpoint rows present (the common case on a long-lived daemon — `CHECKPOINT_MAX_PER_THREAD=3` after a few manual checkpoints), D-first unreferences blobs the dry-run just counted as referenced: those blob bytes are now "free" but were included in the dry-run's `expected_bytes`. When execute then computes its own post-D anti-join, those bytes are no longer counted as free-to-prune — but the dry-run already committed to them. Result: execute's destructive blob deletes cover LESS than `expected_bytes`, and the server's byte-equality check (`expected_bytes` == stored dry-run's `bytes`, AM-3) refuses the request with 400 `byte_count_mismatch`. Worse, re-running dry-run reproduces the same undercount because the excess rows still exist, so the operator is stuck.

Manual execute therefore composes **Op E → Op D**: first prune blobs no longer referenced (the dry-run's anti-join is now stable — no excess rows yet, so no churn), then drop the now-orphan excess checkpoint rows (their blobs were already pruned; the rows are simple DELETE). The auto-cycle order is **unchanged** (INV-1): it runs on a quiescent daemon with no concurrent manual activity, and D-then-E composes correctly under that invariant (Op D unreferences blobs, but the next auto-tick's dry-run no longer counts them because the rows are gone — internal consistency). **Residual cost of the manual E-first ordering:** blobs referenced only by excess rows survive one extra cycle (conservative under-delete; self-healing on the next manual or auto cycle). The required Phase 1 test is "execute with excess rows present must NOT mismatch" (Phase 1 task 9 case c per AM-16); the same test under the old D-then-E order must deadlock. Cites `architecture-recommendation.md` §Focus Area 2 (AM-2 blocker), §Focus Area 3 (auto-tick losing the lock, single global lane), and `checkpoint_prune.py:12-17, 152-258`, `maintenance.py:437-480`.
## Correction by architect (2026-09-27, at re-stamp)

The **AM-2 rationale paragraph above has the mismatch direction inverted** and must not be used as implementation guidance. It states D-first makes execute's blob deletes "cover LESS than `expected_bytes`" because those bytes "are no longer counted as free-to-prune" — the opposite of the code-verified semantics: Op D only *removes* checkpoint rows, so blobs referenced solely by excess rows become **newly unreferenced (free)**, and D-first execute deletes **MORE** than the dry-run promised (`actual > expected_bytes`), never less.

**Correction to THIS correction [W-1, v3 fix pass 2026-09-27]:** the "authoritative rationale" quoted below was itself still wrong about the GATE BEHAVIOR. Verified mechanism, now canonical in `plan-overview.md` §Manual-execute ordering rationale (AM-2) and `phase1-backend.md` case 57: **under D-first ordering, every server-side execute check PASSES — including check 5** (byte-equality, AM-3), because the gate compares the client's echoed `expected_bytes` against the STORED dry-run row's bytes — two readings of the same row, so they always match. The failure mode is therefore **never a 400 `byte_count_mismatch` refusal**: it is **silent over-deletion beyond the confirmed byte echo** — Op D unreferences the blobs referenced only by the just-deleted excess rows, and the execute's blob pass deletes those extra bytes too. The deleted-extra bytes are exactly the blobs D-first unreferences. This is caught **only** by the regression assertions in cases 44/57 (freed-bytes == dry-run-estimate), **never by the byte-equality gate** — and a post-run actual-vs-expected completion gate must NOT be added to catch it (it would false-refuse benign in-window drift): that prohibition is **INV-13** in `plan-overview.md` §Mandatory Invariants and `phase1-backend.md` §0. The prescription stands (manual composes Op E → Op D; auto-cycle unchanged), and the dry-run must NOT be made to simulate post-Op-D state — the dry-run's blob accounting is the anti-join against **current** rows (`checkpoint_prune.py:12-17`, `:203-217`), and E-first execute enumerates against the same pre-D state.
