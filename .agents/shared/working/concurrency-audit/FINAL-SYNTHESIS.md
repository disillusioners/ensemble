## Methodology

Three parallel audits were conducted against `daemon/repositories/` and `daemon/services/`:
- **Area 1** (row-locking): Grepped for `with_for_update`, `SELECT FOR UPDATE`, `SKIP LOCKED`, `EvalPlanQual`; manually reviewed all 10 repositories and key services.
- **Area 3** (waiting-for/CM): Focused on `waiting_for` counter operations, CM callback paths, and graceful degradation fallback patterns.
- **Area 5** (parallel read-update): Ripgrep + targeted reads for RMW and lost-update patterns under PG READ COMMITTED.

**This cross-verification** read actual source code for all CRITICAL findings and every contradiction between audits, resolving disagreements with concrete evidence.

## Contradiction Verdicts (Source-Verified)

### Contradiction #1: `atomic_transition` — CRITICAL, Not Atomic

**Disagreement:** Area 1 and Area 5 both flagged it CRITICAL; Area 3 called it "Verified OK in the CM-active path."

**Source verification** (`daemon/repositories/job_queue/repository.py:430-489`):

```python
def atomic_transition(
    self,
    job_id: str,
    from_status: str | None,
    to_status: str,
    **extra_updates: Any,
) -> JobItem | None:
    with SQLModelSession(self.engine) as session:
        job = session.get(JobItem, job_id)          # SELECT — no lock
        if job is None:
            return None

        if job.status != from_status:                # Python-side check
            raise InvalidTransitionError(...)

        job_state_machine.validate_transition(from_status, to_status)
        job.status = to_status                      # Python mutate
        for key, value in extra_updates.items():
            setattr(job, key, value)

        session.commit()                             # UNCONDITIONAL UPDATE
```

**VERDICT: CRITICAL. Areas 1 and 5 are correct.** The SQL UPDATE generated by `session.commit()` has no `WHERE status = ?` guard. Under PostgreSQL READ COMMITTED, two concurrent callers both pass the Python check (both see `processing`), both write `completed`, and the second overwrites the first's `result_summary`, `completed_at`, etc. The Python-side `from_status` check provides zero protection under concurrent commits.

Area 3's "Verified OK" referred to the **idempotency contract** of callers (e.g., `_finalize_job` catches `InvalidTransitionError` and logs it at DEBUG) — not to the function's atomicity. The race is real; the consequence is a lost terminal write rather than a crash.

### Contradiction #3: `transition_status_if` — VERIFIED OK

**Disagreement:** Area 1 called it "Verified OK — atomic UPDATE-WHERE-guard"; Area 5 implied similar patterns were Critical (C-4 compared it as a template to fix).

**Source verification** (`daemon/repositories/instance/repository.py:578-613`):

```python
def transition_status_if(
    self,
    instance_id: str,
    new_status: str,
    allowed_from: tuple[str, ...],
) -> Instance | None:
    from sqlmodel import update as sqlmodel_update
    with SQLModelSession(self.engine) as db_session:
        stmt = (
            sqlmodel_update(Instance)
            .where(Instance.instance_id == instance_id)
            .where(col(Instance.status).in_(list(allowed_from)))  # GUARD
            .values(
                status=new_status,
                updated_at=datetime.now(timezone.utc).isoformat(),
            )
        )
        result = db_session.exec(stmt)
        db_session.commit()
        if result.rowcount == 0:       # Detect concurrent clobber
            return None
        instance = db_session.get(Instance, instance_id)
        return self._enrich_instance(db_session, instance)
```

**VERDICT: Area 1 is correct. This is a proper atomic UPDATE-WHERE-guard.** The SQLAlchemy `update()` produces a single `UPDATE ... WHERE instance_id = ? AND status IN (?)` with no separate SELECT. PostgreSQL's EvalPlanQual re-evaluates the `status IN (?)` predicate after acquiring the row lock. `rowcount == 0` detects when a concurrent writer changed the status first. Area 5 correctly identified this as the **template** to fix `atomic_transition` (C-4).

#### C-1: `JobRepository.atomic_transition` — SELECT→Python-check→UPDATE, No Status Guard
**Sources:** Area 1 §2.3, Area 5 §C-4 (both CRITICAL)
**Location:** `daemon/repositories/job_queue/repository.py:430-489`

#### C-2: `JobLockManager.acquire_queue_lock` — SELECT COUNT + INSERT Not Atomic
**Sources:** Area 1 §2.1 (CRITICAL)
**Location:** `daemon/services/job_lock_manager.py:41-80`, `daemon/repositories/job_queue/lock_repository.py:23-29`

**Actual code:**
```python
# job_lock_manager.py:63-79
async with self._lock:                        # asyncio.Lock — in-process only
    current_count = await asyncio.to_thread(
        self._lock_repo.get_lock_count, project_id, queue_id
    )                                          # Round-trip 1: SELECT COUNT
    if current_count >= concurrency_limit:
        return False
    db_lock = JobLock(project_id=project_id, queue_id=queue_id, ...)
    await asyncio.to_thread(self._lock_repo.acquire, db_lock)
                                              # Round-trip 2: INSERT
    return True

# lock_repository.py:23-29

        session.add(lock)                       # Plain INSERT, no ON CONFLICT
        session.commit()
```

**Risk:** The `asyncio.Lock` is bound to a single event loop — it does NOT protect against concurrent calls from different worker threads. Two threads both reading `count=0`, both passing the check, both inserting → queue concurrency limit is silently violated. The `lock_repository.acquire` has no UNIQUE constraint and no `ON CONFLICT` clause.

**Recommended fix:** Single atomic SQL:
```sql

    SELECT COUNT(*) FROM job_locks WHERE project_id=:pid AND queue_id=:qid
)
INSERT INTO job_locks (project_id, queue_id, job_id, instance_id)
SELECT :pid, :qid, :jid, :iid
WHERE (SELECT count FROM lock_count) < :limit
RETURNING *
```
Or add UNIQUE constraint on `(project_id, queue_id)` plus `INSERT ... ON CONFLICT DO NOTHING` with a retry loop.

**Impact:** Queue concurrency cap is violated; LLM rate-limit and sequencing assumptions break.

#### C-3: `SQLModelInstanceRepository.update` — SELECT→Python-mutate→UPDATE, No Lock
**Sources:** Area 1 §2.2 (CRITICAL)
**Location:** `daemon/repositories/instance/repository.py:554-572`

**Actual code:**
```python
def update(self, instance_id: str, **updates) -> Instance | None:
    with SQLModelSession(self.engine) as db_session:
        instance = db_session.get(Instance, instance_id)  # SELECT, no lock
        if instance is None:
            return None
        if 'status' in updates and not InstanceStatus.is_valid(updates['status']):
            raise ValueError(f"Invalid status: {updates['status']}")
        for key, value in updates.items():
            if hasattr(instance, key):
                setattr(instance, value)                    # Python mutation
        instance.updated_at = datetime.now(timezone.utc).isoformat()
        db_session.commit()                                # Unconditional UPDATE
        db_session.refresh(instance)
        return self._enrich_instance(db_session, instance)
```

**Risk:** Most heavily-used update method in the instance lifecycle. Callers passing `status=...` are exposed to lost writes from concurrent pause/resume/terminate/child-completion paths.

**Recommended fix:** For status changes, use `transition_status_if` (the existing atomic primitive at line 578). For non-status fields, add `WHERE instance_id = :id AND version = :old_version` (optimistic concurrency via the existing `version` column).

**Impact:** Pause/resume/terminate races with each other and with child-completion status writes; `waiting_for=0` reset on terminate can be clobbered.

#### C-7: `instance.children` JSON Cache — Four RMW Sites (Architectural)
**Sources:** Area 1 §3.8 (HIGH), Area 5 §C-7 (CRITICAL), Area 5 §D-1 (Critical Design Concern)
**Location:**
- `daemon/services/instance_lifecycle.py:374-389` (spawn: append)
- `daemon/services/child_reports.py:595-600` (complete: remove, site 1)
- `daemon/services/child_reports.py:1287-1292` (complete: remove, site 2)
- `daemon/services/error_reporting.py:246-257` (error: remove)

**Actual code** (spawn site):
```python
# instance_lifecycle.py:375-387
with WriteGuardSession(Session(...)) as session:
    parent = session.get(Instance, parent_id)
    if parent:
        children_list = json.loads(parent.children) if parent.children else []
        if instance_id not in children_list:
            children_list.append(instance_id)
            parent.children = json.dumps(children_list)  # RMW on JSON column
        session.commit()
```

**Critical nuance (D-1):** The `instance.children` column is a JSON **string** field (`Field(default="[]")` at `instance/models.py:64`). However, `_enrich_instance()` (repository.py:67-73) is called on every `update()` / `get()` / `list()` return and **overrides** `instance.children` with data from the `instance_hierarchy` junction table:

```python
def _enrich_instance(self, db_session, instance):
    if instance is None: return None
    with db_session.no_autoflush:
        instance.children = self._load_children(db_session, instance.instance_id)
    return instance
```

This means:
1. The four RMW sites DO race (real DB writes, real corruption of the column).
2. But the corrupted value is **ignored on every read** — `_load_children` always returns the hierarchy table's canonical data.
3. The JSON writes are **persistently useless** (they corrupt the column but no code reads it).

**Recommended fix:** Drop the `children` JSON column entirely. The `instance_hierarchy` junction table is the canonical source. The `children` attribute on the ORM object is already a transient, enriched-from-junction value. This eliminates 4 RMW sites at once.

**Impact:** The JSON column accumulates silently corrupted data. Direct DB reads (bypassing `_enrich_instance`) see wrong values. Cascade pause/resume traversal that ever uses the JSON column would behave incorrectly.

## False Positives (Downgraded)

### Area 5 §D-2: `version_id_col` Not Used — Downgraded to H-8

Area 5 rated this "Critical (architectural)." It is more accurately a **HIGH** (dead code, misleading). The `version` column exists but is never used as an OCC guard — it's incremented but never checked. The risk is confusion and wasted writes, not a silent correctness failure (since `update()` unconditionally overwrites anyway, version increment has no effect).

### Area 5 §C-5: `start_job` Non-Atomic Variant — Subsumed by C-1

Area 5 §C-5 called `start_job` at `repository.py:522` CRITICAL (two-transaction TOCTOU). This is the same root cause as `atomic_transition` (C-1) — once C-1 is fixed, `start_job` calls `update()` which would still be racy, but `start_job_atomic()` (line 555) calls `atomic_transition()` which is the correct path. The non-atomic `start_job` variant should be deprecated in favor of `start_job_atomic()`.

### Area 3 §6.1: `_process_event` cm_pending Check Race — Theoretical, Not Actionable

Area 3 called this CRITICAL (theoretical). The comment at `job_feedback_observer.py:452-459` explicitly acknowledges the race window and states that `atomic_transition`'s idempotency guard catches the second writer. This is a theoretical race that is **already mitigated** by existing idempotency logic. Not actionable without fixing C-1 first.

## New Races Introduced During CM Migration

None confirmed. The CM migration actually **fixed** three previously-known races (Race #1, Race #3 CM-path, Race CM-2/W1) and introduced Phase 4's documented carve-outs. The remaining races were pre-existing, not introduced by the migration.

The one area of concern is the **CM-disabled graceful degradation path** — when CM is None, the `SELECT COUNT(*)` fallback at `child_reports.py:661-670` retains a TOCTOU window. This is documented and accepted (CM must be enabled for production), but any CM-disabled deployment (including tests without CM fixtures) remains exposed.

## Top 5 Priorities for Remediation

1. **Fix `atomic_transition` (C-1)** — Highest blast radius. Rewrites affect every job terminal transition. Single-pattern fix eliminates races at `JobFeedbackObserver`, `JobRecoveryService`, `JobQueueService`, and `MessageJobHandler` simultaneously. Template already exists in `transition_status_if`.

2. **Fix `JobLockManager.acquire_queue_lock` (C-2)** — Cross-process lock violation. Violates the advertised concurrency cap of the queue system. Fixing this enables reliable multi-worker deployments.

3. **Fix task lifecycle (C-4)** — `complete_task` / `fail_task` / `cancel_task` are on the hot path for every task completion. Every worker completion races with recovery. Simple conditional UPDATE pattern mirrors the existing `request_cancel` example already in the codebase.

4. **Drop `instance.children` JSON column (C-7, D-1)** — Eliminates 4 RMW sites with a single architectural change. The junction table is already the canonical source; the JSON column is written by races and ignored on reads. One migration removes a class of bugs.

5. **Route pause/resume/terminate through `transition_status_if` (H-4)** — Most user-visible operations are affected. Three high-impact callers, three targeted fixes. `transition_status_if` already exists and is well-tested.
