## 7. Findings for triage (findings, not fixes)

**F-DR2-1 (runbook defect — the §3 stage line cannot run from the real repo at this HEAD): the untagged-HEAD tag guard blocks the runbook's literal staging path.**
`stage.sh:106-110` requires `git describe --tags --exact-match HEAD == VERSION` — at drill time HEAD `68b54d96` carries **0 tags** (`git tag --points-at HEAD` empty), so the runbook's `bash scripts/upgrade/stage.sh sandbox --version v1 …` exits 78 at the tag guard ("does not match the exact tag at HEAD") before any staging. The runbook never mentions this precondition. The project's own sanctioned workaround is the unit-suite fixture strategy (`tests/test_release_journal.sh:62-101`): real scripts copied byte-identical into a throwaway repo, `git init` + commit + tag, stub payloads — **used here** (with REAL launcher/config/agents/frontend/migrations payloads, so the staged release is a faithful real-launcher install; fixture launcher md5-identical to repo). Triage options: document the fixture strategy in §3, or add a sandbox-scoped tag-guard exemption to stage.sh.

**F-DR2-2 (runbook defect — the §3 launch line presupposes a launcher at INSTALL_DIR root that stage does not produce):** `bash "$SBX/launcher.sh"` requires the launcher at the install root, but `stage.sh` stages `launcher.sh` only inside `releases/<ver>/` — the root copy is promote's `launcher_swap` step (promote.sh:182, lib.sh:1068-1078). DR-2 as written has no promote, so the runbook line fails (`No such file`) unless the swap is performed. **Deviation taken (disclosed):** invoked the real `launcher_swap v1` from lib.sh (cp + chmod, byte-identical result to promote's step) — transcript in `launcher-swap.txt`. Runbook should add the swap step (or note that stage-only sandboxes need it).

**F-DR2-3 (informational — the §3 `rm` line's target is not a binary-resolution candidate on a stage-only sandbox):** post-stage, `current` does not exist (stage never flips) and no flat `ensemble-prod` exists, so the launcher's `resolve_binary` would already refuse with both candidates absent; `rm releases/v1/ensemble-prod` is belt-and-braces on this path (it matters only if a promote had flipped `current → releases/v1`). Executed as written regardless — harmless and it hardens the induction against any layout surprise.

**F-DR2-4 (self-disclosed evidence defect, corrected):** the first observation-window capture's `pgrep-exit`/`lsof-exit` annotations recorded `tee`'s exit code (0), not the probes' — because `$?` followed a pipe. The probe OUTPUTS were correct (both empty); a pipe-free re-assertion at 18:07:00Z captured the true exit codes (1 = no match / nothing listening). Both captures retained in `no-respawn-check.txt`. Lesson: never annotate probe exit codes through a `tee` pipe.

**Carry-over closure statement:** the exit-78 path is now smoke-proven beyond the 63/63 unit coverage — real launcher on a real staged sandbox install, exact exit code, refuse-class log line, zero respawns, zero state ticks, immediate (non-backoff) exit.
