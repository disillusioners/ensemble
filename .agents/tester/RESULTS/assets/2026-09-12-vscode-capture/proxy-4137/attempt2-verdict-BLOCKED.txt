=== HEADER vs META split ===
- HTTP CSP header: allows 'self' for scripts/styles — but only 'self', not virtual hosts
- Meta CSP: only allows ONE specific sha256 OR 'self' for scripts
- Virtual host 'vscode-remote+localhost-003a8079.vscode-resource.vscode-cdn.net' is NOT 'self'
  from either CSP's perspective
- Both layers block the extension's CSS/JS

=== COMPARISON: 4.112.0 vs 4.137.0 meta-CSP ===
4.112.0: script-src 'sha256-nQZh+9dHKZP2cHbhYlCbWDtqxxJtGjRGBx57zNP2DZM=' 'self'
4.137.0: script-src 'sha256-24QqbpzqcqSyIGvg/ZwFRy5pPlhmVBa8CkUREEIUnBw=' 'self'
Both versions ship a restrictive meta-CSP that only allows 'self' + one sha256.
Both versions use the same virtual-host URL pattern (vscode-resource.vscode-cdn.net).
Both versions fail with the same CSP-blocked error.
The bug is structural, not version-specific.

=== VIRTUAL-HOST URL SHAPE ===
URL pattern: https://vscode-remote+localhost-003a8079.vscode-resource.vscode-cdn.net/{absolute-path}
- "localhost-003a8079" encodes port 8079 (the proxy), not the loopback
- The virtual host is supposed to be a rewrite target for /vscode-remote-resource?path=...&tkn=
- But CSP treats this origin as different from 'self' (which is the proxy http://localhost:8079)
- Result: extension's CSS/JS are blocked

=== IN-IFRAME naturalWidth check ===
Result: TIMEOUT (no rendered image, no in-iframe img elements with naturalWidth>0)
- The extension's JS never loads, so it never creates the <img> element in the iframe
- No error dialog appears either (extension JS would normally display it)
- Bug is silent at UI level

=== ROOT CAUSE IMPLICATION ===
The bug is NOT fixed by upgrading code-server. Both 4.112.0 and 4.137.0 have the same
restrictive meta-CSP that doesn't trust the vscode-resource virtual host. The proxy
might or might not be involved; the structural issue is that code-server's webview
CSP doesn't include the virtual host in 'self'.
